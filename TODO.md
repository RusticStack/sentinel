## How to use this backlog

- Work in small runnable increments: take the task named under **Next task**, and connect working pieces rather than waiting for an entire later subsystem.
- `[ ]` means unfinished; `[x]` means implemented and verified. Keep stable task IDs when splitting/reordering work. Mark blocked items with `Blocked by: <ID or concrete prerequisite>`; record why, not a guessed completion date. A run still going is "in progress", never a result.
- Mark a task complete only with its code/docs plus relevant verification. Record the commit and test/benchmark evidence in the completion log. A scaffold, mock, or proposed API alone does not complete behavior.
- Keep this file as the execution tracker; [plan.md](plan.md) remains the design reference. Resolve a design change in both documents before treating it as accepted scope.
- Preserve the separate server/worker execution boundary, tenant ownership, durable transitions, and bounded resource usage as features are added. Introduce crates when useful rather than creating an empty crate for every planned module.
- Add meaningful behavior/failure tests for the contracts being implemented. Run formatting, lint, applicable tests, and changed performance fixtures; do not add implementation-mirroring tests merely to increase counts.
- A finding without a fix goes to [open items](#open-items) under the task that owns it; settled findings are removed. History lives only in the completion log and the [benchmark contracts' revision history](docs/benchmark-contracts.md#revision-history).
- Optional runtime/build-system features in Part 16 require explicit promotion. The [pilot workloads](docs/pilot-repositories.md) (GitHub CLI, ripgrep and gson) adapt to Sentinel through operator-controlled mirrors or forks; their workflows are not v1 release gates.

### RW03 — dispatch, leases and the worker link

- Worker link: the known-source set is memory-only and under Tailcat every peer arrives from loopback; `WorkerEnrollmentRefused` rows grow without bound and one tailnet peer can exhaust enrollment (the limiter caps the rate at 20 per minute, not the total); the descriptor headroom is a fixed 256 and `setrlimit` is process-wide.
- Store and hot path: `Conns::shutdown` can spend about 6 s retrying the loopback self-connect and leave the acceptor detached.
- Hand-offs: GitHub sign-in hand-offs live in controller memory for 60 seconds (at most 1,024), so a restart between the callback and `/auth/github/finish` forces a new sign-in. A hand-off close lost inside the Tailcat tunnel for longer than the 3 s `HANDOFF_RESEND_BOUND` falls back to heartbeat detection (about 20 s); a Tailcat allow-list change costs a connected worker about 3.3 to 4.6 s because the pinned helper has no `--allow` reload.
