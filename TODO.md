## How to use this backlog

- Work in small runnable increments: take the task named under **Next task**, and connect working pieces rather than waiting for an entire later subsystem.
- `[ ]` means unfinished; `[x]` means implemented and verified. Keep stable task IDs when splitting/reordering work. Mark blocked items with `Blocked by: <ID or concrete prerequisite>`; record why, not a guessed completion date.
- Mark a task complete only with its code/docs plus relevant verification. Record the commit and test/benchmark evidence in the completion log. A scaffold, mock, or proposed API alone does not complete behavior.
- Keep this file as the execution tracker; [plan.md](plan.md) remains the design reference. Resolve a design change in both documents before treating it as accepted scope.
- Preserve the separate server/worker execution boundary, tenant ownership, durable transitions, and bounded resource usage as features are added. Introduce crates when useful rather than creating an empty crate for every planned module.
- Add meaningful behavior/failure tests for the contracts being implemented. Run formatting, lint, applicable tests, and changed performance fixtures; do not add implementation-mirroring tests merely to increase counts.
- Optional runtime/build-system features in Part 16 require explicit promotion. Lockwell adapts to Sentinel; its six old workflows are not Sentinel v1 release gates.

### First vertical slice

**Working outcome:** a locally bootstrapped authorized operator submits a pinned fixture pipeline through the CLI; the server durably assigns it to a separately running worker; the worker executes an isolated job; logs and final status are retrievable; cancellation and restart leave truthful state.

Sequence: `F01–F05` -> `C01–C05` -> `A01–A03` -> `W01–W09`. Implement the minimum working scope of these parts first, then complete their remaining cases. Use a dedicated Linux test host/VM for rootless runtime checks; Windows CLI development does not substitute for Linux executor validation.

- API hardening: behind a trusted proxy that sends no `X-Forwarded-For` all clients share one rate-limit key and the login lockout key `(client, account)` is reachable from a few addresses (state the dependency in `docs/api.md`); a trusted-proxy peer is exempt from the per-client body-slot cap and many addresses can occupy all 4 public-body slots for up to 10 s each; `POST /login` has no HTTP-level test; `GET /api/v1/setup` is uncached with no admission budget, and five wrong well-formed tokens lock setup for five minutes (document `admin bootstrap` as the escape).
- Worker link: `BUSY` uses `try_lock` on the mutex the reader thread takes, so a streaming worker can lose the race and have its offer lapsed; the known-source set is memory-only and under Tailcat every peer arrives from loopback; `WorkerEnrollmentRefused` rows grow without bound and one tailnet peer can exhaust enrollment (the limiter caps the rate at 20 per minute, not the total); the descriptor headroom is a fixed 256 and `setrlimit` is process-wide.
- `sentinel-worker` `identity()` deletes a lone surviving `.crt` or `.key` and mints a new identity, changing the fingerprint and breaking pinned workers; it should recover only when the lone file is the key. The keepalive bound is job timeout plus 5 minutes, so an attempt still in prepare at shutdown may create a container afterwards.
- Manual-remote destination policy has no config file or flag (environment only); `git_can_pin` caches a transient `git --version` failure for the process life; each manual-remote resolve spawns a detached thread that stays blocked if the resolver hangs; the worker's bound-access validity window uses the wall clock at receipt.
- Checks and S3: `checks::due` fails the whole read if one row cannot be decoded; only `StoreError::Corrupt` parks a row; `store_fault` counts transient errors toward quarantine; the exhausted-final-check re-arm runs only at lane start; `replicate.rs` `deletes()` relies on an unasserted ordering; the rerequest reset is a CAS on `state_code` only and bypasses the attempt, lease and cancel fences.
- Store and hot path: the deferred-report path has no failure-path test; a deferred Ack does not shield its attempt; a cancel-desired `Pong.stop` taken as confirmation of a deferred verdict can be lost across a controller restart (at most 5 min); a profile-protocol worker reporting disk 0 takes no work with no operator signal; `Conns::shutdown` can spend about 6 s retrying the loopback self-connect and leave the acceptor detached.
- `Objects::materialize` checks symlinks by path and does not hold against a destination changed during extraction; no controller path calls it today, and a caller extracting into shared space needs a descriptor-relative walk first.
- The `private_dir_all` comment in `crates/sentinel-worker/src/lib.rs` says a symlinked directory is left alone, but the code may follow the link and chmod the target; check and fix.
- The three PEM keys in `sentinel-checks` `delivery.rs`, `reconcile.rs` and `sentinel` `intake_e2e.rs` appear to be one test key; if it was ever a real GitHub App key, rotate it.
- GitHub sign-in hand-offs live in controller memory for 60 seconds (at most 1,024), so a restart between the callback and `/auth/github/finish` forces a new sign-in. A hand-off close lost inside the Tailcat tunnel for longer than the 3 s `HANDOFF_RESEND_BOUND` falls back to heartbeat detection (about 20 s); a Tailcat allow-list change costs a connected worker about 3.3 to 4.6 s because the pinned helper has no `--allow` reload.
