# Second factors, step-up and session administration

Implemented in `sentinel-auth::mfa` and `sentinel-auth::sealed`, `sentinel-store::mfa`, the `Authority` type in `sentinel-store::auth`, the account routes in `sentinel-api` (`routes/account.rs`, `github.rs`), and `sentinel admin key|mfa|session`, with metadata migrations **9** (session identifiers), **10** (per-session failure limit) and **32** (per-account second-factor lockout).

A session proves who you are. **Step-up** proves you are still there, just now, with something more than a cookie — before a change that alters who can authenticate at all. It is freshness, not authority: `Authority::require_privileged` demands both a recent stamp and a live platform-admin check, in the same transaction as the change.

## What requires step-up

| Change | Entry point |
|---|---|
| Registration / tenant-creation / installation-binding policy | `registration::set_policy` |
| Granting or revoking super admin | `local_auth::set_super_admin` |
| Suspending or reactivating an account | `local_auth::set_active` |
| Rejecting an account that was already approved (permanent: a rejected account can be neither approved nor reactivated) | `registration::reject` |
| Suspending or reactivating a tenant | `tenancy::suspend`, `tenancy::reactivate` |
| Linking an external identity to an account | `sign_in::link`, over `POST /identities/github/link` |
| Provisioning a local password for an existing account | `local_auth::provision_credential` |
| Removing your own second factor, reissuing recovery codes | `mfa::disable`, `mfa::reissue_recovery_codes`, over `POST /mfa/recovery-codes` |
| Changing your password, **when a second factor is enrolled** (always with the current password) | `local_auth::change_password`, over `POST /password` |
| Creating a service account, allowing it a repository, issuing it a grant — from **anyone**, tenant administrators included | `auth::create_service_account`, `oauth::service::allow_repo`, `oauth::service::issue_service_grant` |
| Creating or revoking an email invitation, or changing a tenant's memberships or repository grants, as a platform administrator who is **not** an administrator of that tenant (also needs a reason) | `auth::set_membership_as`, `auth::set_repo_grant_as` |

Routine administration — approving applications, rejecting a *pending* application, inviting, revoking credentials, binding installations, and a tenant administrator changing their own tenant's members and repository grants — needs platform (or tenant) administration but not step-up. Rejecting reads the account's status in the same transaction: pending is platform administration, approved needs step-up as `set_active` does, so an unstepped credential cannot permanently do what it cannot do reversibly. `Authority::HostLocal` needs no step-up either: holding the database file is already stronger than any proof a session can offer, and every host-local action is audited as such.

A session that lacks a fresh stamp gets `Error::StepUpRequired`, distinct from `Forbidden`, so a client can prompt for a code rather than report a denial. **A bearer credential can never step up**: `Authority::credential` is always unstepped, so an API token or OAuth access token — even one carrying `platform-admin` or `tenant-admin` — cannot make any of these changes. Only a session with a recent proof, or the host-local operator, can. A caller without the administration the change needs still gets `Forbidden`, not a prompt, so a non-administrator learns nothing about proof.

**Freshness is read where the change is made.** A browser session reaches the store as `Authority::Session`, which carries the session's token digest. `Authority::require_fresh` probes that session row inside the writer transaction of the change — not revoked, not expired, stamped, and the stamp inside `Policy::step_up_ms` and not in the future — so a session revoked or whose window closed between identifying the request and the write is refused, rather than trusted from a flag computed earlier. `Identity::stepped_up` in the API is what the interface shows (`GET /me`), not what authorizes. A `Credential` authority with `stepped_up: true` is for fixtures and callers that verified a proof themselves.

Five consecutive failed proofs **revoke the session** (migration 10, `MAX_STEP_UP_FAILURES`): a six-digit code has three valid values per window, and a cookie holder who keeps guessing is not the person it was issued to. A successful proof resets the counter.

The per-session limit alone does not hold anyone who knows the password: they sign in again and keep guessing. So wrong TOTP and recovery-code proofs are also counted **per account**, across every session (migration 32, `mfa_totp.failures`/`locked_until_ms`, counted in the same write as the session counter). Ten consecutive failures (`MAX_FACTOR_FAILURES`) lock the second factor for fifteen minutes (`FACTOR_LOCKOUT_MS`): every proof is refused — a correct code included, and a recovery code is not spent — and every session of the account is revoked in the same transaction, audited as `SessionRevoked` with detail `second factor locked`. The window is not extended by tries during it; once it ends the count restarts at the next failure, as the login lockout does. A successful proof resets the count, and host-local password recovery (`sentinel admin recover`) clears both. That bounds online guessing to ten codes per fifteen minutes per account, whatever the number of sign-ins. The stamp lasts `Policy::step_up_ms` (10 minutes), only ever moves forward, cannot be written onto a revoked session, and is judged against the clock — a stamp in the future is not fresh.

## Issuing credentials

A service account's refresh token (`runs:write`, `secrets:write` and the rest of a grant's scopes, 1 hour to 90 days) outlives the session that asked for it: it survives logout, password recovery and session revocation unless something revokes it. So minting one is a step-up change for everyone, tenant administrators included, and `tenant:admin` on a bearer or OAuth token is not enough: a stolen token cannot mint a longer-lived one. The API surface is `POST /tenants/{slug}/service-accounts`, `PUT …/service-accounts/{usr}/repos/{name}` and `POST …/service-accounts/{usr}/grants` ([API](api.md)). The consequence for the CLI is that `sentinel service-account create|allow|grant` (which authenticate with an OAuth token) get `forbidden` with `details.step_up`; the three changes are made from a browser session that has stepped up (the web interface's tenant administration, section "Service accounts", asks for the step-up and shows the refresh token once; [web interface](web-ui.md#views)) or, for host-local provisioning of an API credential, with `sentinel admin token issue`.

### Service credentials minted by a session

A grant records who minted it, not through which session. When `local_auth::revoke_all` revokes an account's sessions — logout-all, a password change, host-local recovery or logout-all, suspension or demotion, a second-factor lockout — the same transaction revokes every live service grant that account minted since its **oldest unrevoked session began** (`oauth::revoke_minted_since`, reason `account`), and audits one `oauth-grant-revoked` row with the count. A hijacked session's minted credential therefore does not survive the response to the hijack. Grants minted before the window opened are untouched. The window opens at the oldest session **not individually revoked**, expired-but-unpurged ones included, so a hijacked session that has since gone idle is still covered. Revoking one session by name (`local_auth::revoke_session`) does the same for the grants minted since **that** session began, and records them in the same transaction. The cost is that a logout-all or a session revocation by a tenant administrator also revokes service grants minted by their other sessions in the window (at most the absolute session life, 7 days by default); they are reissued after a step-up. A session that expired and was purged is outside the window.

## Platform scope is not data access

A super admin has no ambient access to a tenant's data (see [authorization](authorization.md)), yet `auth::require_tenant_admin` admits a platform administrator as an administrator of every tenant for administration. That reach must not be a quiet way to grant themselves the access. A platform administrator who is **not** an administrator-member of the tenant therefore needs, to change its memberships or repository grants or to mint its service credentials, fresh step-up **and** an explicit `reason` (1–100 characters), and the change fails closed without either: `StepUpRequired` first, then `invalid_request` for a missing, empty or oversized reason. The reason is recorded in a `platform-override` audit row naming the actor, in the same transaction as the change. A tenant administrator is unaffected, and so is a platform administrator once made an administrator of the tenant through that audited path. Naming a person resolves a local sign-in name only among the tenant's existing members (`auth::resolve_member`), so the membership routes are not an oracle for which accounts exist, and adding a non-member takes their `usr_` id. Adding an account that was not yet a member is recorded as its own `member-added` audit row beside `membership-set`: no invitation or acceptance precedes it, the `usr_` id (128 random bits, given by the person) is the only consent signal, and an active non-member succeeding while an unknown or inactive id is `not_found` reveals nothing to anyone who does not already hold the id. Email invitations ([admission](admission.md#email-invitations)) add a person only after they accept; adding an existing account by `usr_` id stays as described. The web interface collects the reason ([web interface](web-ui.md#views)).

## Proofs

- **TOTP** (RFC 6238: SHA-1, 6 digits, 30 seconds, one step of drift) through the maintained `totp-rs` crate; Sentinel's unit tests check its reference vectors. RFC 6238 leaves one-use to the implementer, so `mfa_totp.last_step` records the last accepted step and a trigger refuses to move it backwards: a code seen over a shoulder is worthless within its own window.
- **Recovery codes**: ten 50-bit codes in a look-alike-free alphabet, stored as BLAKE3 digests, each spent once (a trigger refuses to un-spend). Retyping without the separator or in upper case still works. Reissuing a set replaces the old one entirely.
- **Password**, accepted **only when no second factor is enrolled**. Otherwise the weaker proof would stand in for the stronger, which is the opposite of stepping up.

A wrong proof returns `false` and an audited `StepUpFailed`, not an error: the caller renders one response either way. A GitHub-only account has no password to offer, so a GitHub-only super admin must enroll TOTP before any privileged change. Enrollment is therefore reachable without a password, but never with a bare cookie: see [Enrolling a second factor](#enrolling-a-second-factor) for the proof each kind of account gives first.

## The seed is sealed

A TOTP seed is the one credential that must be recoverable to be useful, so it is the one value not stored as a digest. It is sealed with XChaCha20-Poly1305 (RustCrypto) under a 32-byte key that lives **outside the database** — `master.key`, created owner-only by `sentinel admin key create`, which refuses to overwrite. The associated data binds each ciphertext to its account, so a row copied onto another account cannot be opened. A stolen `metadata.sqlite` yields no seed and no ability to mint codes; losing the key loses every sealed value, which is the operator's trade to make and the command says so.

Enrollment is two steps: `begin_enrollment` writes an unconfirmed seed and returns the `otpauth://` URI once; `confirm_enrollment` requires a code from the app, issues the recovery codes once, and stamps the session. Until confirmed, nothing about authentication changes — an abandoned enrollment cannot lock anybody out. A confirmed factor cannot be quietly re-enrolled by a live session; replacing it means `disable` under step-up, which also revokes every session of the account so no stepped-up window outlives the factor.

### Enrolling a second factor

Routes for a **browser session with its CSRF header** ([API](api.md)); a bearer credential or OAuth token, whatever its scopes, can enroll nothing:

1. `POST /mfa/enroll` begins. What the account must show first depends on what it has, so a stolen cookie enrolls nothing on an account whose password it does not know:
   - **An account with a local password** sends it in the body. It is verified as a password step-up (counted against the session, five wrong revoke it, audited `step-up-failed`) and stamps the session on success.
   - **A GitHub-only account** has no password and no factor, so the one proof it can give is the sign-in itself: the session must have been issued within `Policy::step_up_ms` (`Session::signed_in_within`, against the session row's recorded creation time), else the answer is `forbidden` with `details.reauthenticate` and the person signs in again. The trade-off is explicit: within ten minutes of a GitHub sign-in, a hijacked session of a GitHub-only account could enroll its own factor; the audit row, the confirmed enrollment's immunity to quiet replacement, and host-local removal bound what follows.
   - A confirmed factor is `409`; a repeat before confirmation supersedes the earlier seed.
2. `POST /mfa/enroll/confirm` with a code from the app. A wrong code confirms nothing and is counted like any wrong proof — audited `step-up-failed`, five revoke the session — because a pending enrollment has no expiry and the right code yields the recovery codes; the account's factor lockout is not involved until it is confirmed. The confirmed code's time step is recorded, so it cannot be replayed as a step-up. The ten recovery codes are returned once and the session is stepped up.
3. `POST /mfa/recovery-codes` replaces the set; it needs a fresh step-up. `POST /password` and `POST /identities/github/link` are the other two changes this section gates ([local authentication](local-authentication.md#changing-a-password), [GitHub sign-in](github-sign-in.md#linking-from-a-signed-in-session)).

`GET /me/security` reports the state (enrolled, pending, codes remaining) without a seed, a code or an identity subject.

### From the host

The same enrollment exists host-locally for an operator sitting with the person and their device (a GitHub-only super admin on a headless deployment, say). `sentinel admin mfa enroll` prints the `otpauth://` URI alone on stdout, once; `confirm --code` proves the app holds it and prints the ten recovery codes on stdout, once; `codes` replaces the set. Authorization is access to the database file and `master.key`, like removal, and the audit rows are marked host-local; no session is stamped. Removal (`mfa disable`) is the recovery path for a lost device with spent codes.

## Session administration

Sessions carry a public `ses_` identifier (migration 9). `local_auth::sessions` lists an account's sessions as metadata — created, deadlines, step-up time, revoked — with no digest and no cookie value anywhere in the record. `revoke_session` revokes one by name; the account itself or a platform admin may do either, and anybody else gets the same `NotFound` as a guessed identifier. `revoke_all_host_local` is the operator's logout-all.

```sh
sentinel admin key create   --data-dir <PATH>
sentinel admin mfa status   --data-dir <PATH> --user root
sentinel admin mfa enroll   --data-dir <PATH> --user root            # otpauth:// URI on stdout, once
sentinel admin mfa confirm  --data-dir <PATH> --user root --code 123456   # recovery codes on stdout, once
sentinel admin mfa codes    --data-dir <PATH> --user root            # replace the recovery codes
sentinel admin mfa disable  --data-dir <PATH> --user root
sentinel admin session list       --data-dir <PATH> --user root
sentinel admin session revoke     --data-dir <PATH> --user root --id ses_...
sentinel admin session logout-all --data-dir <PATH> --user root
```

## Verification

`sentinel-auth` unit tests: RFC 6238 reference vectors, one-step drift with the matched step reported, malformed codes refused before HMAC work, provisioning URI shape and seed redaction, recovery codes distinct and retype-tolerant, sealed values opening only under their key and context, damaged/truncated/unknown-version ciphertexts refused, key file created once at the right size.

`crates/sentinel-store/tests/mfa.rs`: a platform-admin session refused every privileged change until it steps up, the password serving as proof only before enrollment, freshness expiring on schedule and host-local needing none; enrollment confirmed by a code with the seed stored only sealed and no recovery code present in the database; a TOTP code accepted once with replay and raw rewind refused and the password no longer accepted; recovery codes one-use, retype-tolerant, reissue needing step-up and killing the old set; removal needing step-up and ending every session, with host-local removal audited; sessions listed and revoked by name with no secret in the output and outsiders refused; and the stamp neither forgeable, rewindable, placeable on a revoked session, nor fresh when in the future; wrong codes accumulating across fresh sign-ins until the account's factor locks and every session is revoked (`step_up_failures_accumulate_across_sessions`), the lock refusing a correct code and sparing recovery codes until it ends (`an_account_lockout_refuses_even_a_correct_code_until_it_expires`), and host-local recovery clearing it (`host_local_recovery_clears_the_step_up_lockout`). `crates/sentinel-store/tests/registration.rs` covers rejecting an approved account needing step-up (`rejecting_an_approved_account_needs_step_up`). `crates/sentinel-store/tests/oauth_service.rs` covers issuing needing fresh step-up and refusing a bearer authority, host-local and a non-administrator in the right order, a session's stamp being re-read in the transaction (unstamped, stale, and revoked after the authority was built), the platform reason being bounded and audited, and revoking an account's sessions revoking the grants it minted in the window and no others; `crates/sentinel-store/tests/tenant_access.rs` covers a platform administrator being refused self-grants without proof and reason, the audited `platform-override`, and sign-in names resolving only among members; `crates/sentinel-api/tests/oauth_service.rs` covers a bearer and an OAuth token holding `tenant:admin` being refused with `details.step_up`, a cold session being refused and a stepped-up one allowed, and a narrow token managing only its own grant. `mfa.rs` also covers a password change with a factor needing a fresh step-up (asked for before the password is judged), wrong current passwords counting against the session and never the factor, host-local enrollment (a wrong code confirming nothing, no session stamped, audited host-local, a confirmed factor not replaced, reissue replacing the set) and an unknown or unenrolled account refused. The HTTP and CLI coverage is `crates/sentinel-api/tests/account.rs`, `crates/sentinel-api/tests/github_sign_in.rs` and `crates/sentinel/tests/mfa_admin.rs`.
