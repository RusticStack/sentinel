# External S3 copy (R02, R03)

The default installation needs nothing but its own disk. An `[s3]` section adds an **external copy** of what the controller stores — committed objects (artifacts and uploads) and finished attempt logs — in any service that speaks the S3 API. SQLite metadata stays local, always: the bucket holds bytes under content-addressed keys, never rows. Sentinel implements no S3 server and depends on none.

## What it does

The local disk stays the write path. A committed object or a finished log is durable the moment its local write is ([storage](storage.md)); the copy follows:

1. **Replication.** The controller's `sentinel-s3-replicator` thread copies committed objects oldest first: in one request up to `part_bytes` (16 MiB by default), as a multipart upload above it. A multipart upload is recorded (`s3_uploads`) the moment it starts, so after a crash or restart it **resumes** from the parts the bucket already holds (`ListParts`) instead of starting over. Every copy is **verified** before its row records it (`objects.remote_ms`): `HEAD` must show the object's length and its BLAKE3 digest in the `x-amz-meta-blake3` metadata. Finished logs — released, stamped by retention and settled for 10 minutes, since a late end may still arrive — are copied file by file under `logs/<run>/<job>/<attempt>/`; keys a previous copy of the same log left are removed. A late end that changes a copied log resets its copy (`log_remote_ms`), and it is copied again.
2. **Tiering.** Past `local_bytes`, or whenever the disk admission gate closes for low space, replicated objects are **evicted** locally, oldest first — never one a reader or stage pins, and never one without a verified copy (the `objects` trigger refuses `evicted_ms` without `remote_ms`). A read of an evicted object fetches it back into place first, **verified**: the bytes are hashed as they arrive and a wrong length or digest is `Corrupt`, never served, never placed. The next pass marks it local again.
3. **Deletion.** A copy is deleted only after its local record is gone: reclaiming an object queues its key (`s3_deletes`, by trigger), expiring a log queues its prefix, and a copy uploaded for an object reclaimed while the upload ran is deleted as well. Nothing here ever deletes the only copy.
4. **Abort cleanup.** Every 720 passes, multipart uploads the bucket holds under the prefix that this deployment is not resuming and that are older than a day are aborted, and recorded uploads that old are aborted and forgotten, so abandoned parts do not accumulate charges.

Transport integrity does not depend on the service honouring the signature alone: every body carries **`Content-MD5`** (which every tested service verifies and refuses on mismatch) and its **signed SHA-256** payload hash (which some services skip; see the matrix). The client is about 1,300 lines, tests included, over the controller's existing rustls/ring stack (`crates/sentinel-s3`): Signature V4 in the header form, bounded response sizes and timeouts, no redirects, no SDK, no async runtime.

## Degraded durability and admission (R03)

While the bucket is unreachable or refusing, the replicator backs off (1 s doubling to 60 s), logs `s3_degraded` once, and keeps every local copy — the unreplicated bytes are the **backlog**, a bounded spool on the controller's own disk:

| Condition | Effect |
|---|---|
| Replication failing, backlog within `backlog_bytes` | `GET /admin/storage` says `s3.state: degraded` with the last error; everything else works. Local copies are kept, eviction takes only replicated objects. |
| Backlog past `backlog_bytes` | The disk admission gate closes (as below the low watermark): **new artifacts and uploads are refused** (`storage_full`, 507, retryable; an artifact the worker was streaming is recorded `failed`, and a required one fails its job with `Publication` — explicitly, never silently), and **no new work is placed**. The queue says so: `placement_paused: "external_copy_backlog"`, and a job otherwise ready waits with reason `storage`. Running jobs' **logs keep flowing** (they are refused only at the disk's log floor). |
| Backlog drains below nine tenths of `backlog_bytes` | Admission reopens, placement resumes, `s3_recovered` is logged. |

Required and optional data are distinct by construction:

- **Artifacts and uploads are required**: never evicted before their copy is verified, counted in the backlog, and refused rather than accepted beyond it.
- **Finished logs** are replicated for durability but never evicted locally; retention deletes them on both sides.
- **The remote cache store** ([cache](cache.md), Q08) is optional and is **not** replicated: a cache entry that cannot be served is a miss, so an S3 outage never touches it.

The default `backlog_bytes` is a sixteenth of the data file system, 1–64 GiB (62.9 GiB on the 1 TB reference host), beside the disk watermarks that still apply.

## Configuration

Server only ([configuration](configuration.md)):

```toml
[s3]
endpoint = "https://s3.eu-central-1.amazonaws.com"  # http(s)://host[:port], no path
region = "eu-central-1"
bucket = "sentinel-ci"
prefix = "prod/"                         # optional; ends in '/' when set
path_style = false                       # true for most self-hosted services
ca_file = "/etc/sentinel/s3-ca.pem"       # optional: trust these CAs instead of the Mozilla roots
credentials_file = "/etc/sentinel/s3.credentials"
part_bytes = 16777216                    # 5-512 MiB (default 16 MiB)
local_bytes = 0                          # keep replicated objects locally up to this; 0 (default) keeps all
backlog_bytes = 67549713920              # default a sixteenth of the data file system, 1-64 GiB
```

The credentials file is owner-only, at most 8 KiB, and holds `access_key_id = …`, `secret_access_key = …` and optionally `session_token = …`; its contents are never logged or echoed. Grant the key `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`, `s3:ListBucketMultipartUploads`, `s3:ListMultipartUploadParts` and `s3:AbortMultipartUpload` on the bucket and prefix, nothing more. At start the controller checks the bucket once (`s3_ready`, or `s3_unavailable` and it starts degraded — it never refuses to start for the bucket).

## Status

`GET /admin/storage` ([API](api.md)) carries `s3`: `state` (`healthy`, `degraded`, `unknown` before the first pass), `backlog_bytes`, `backlog_full`, `oldest_unreplicated_ms`, `unreplicated_logs`, `local_bytes`, `last_success_ms`, `last_failure_ms`, `consecutive_failures`, `last_error`, and since-start counters of replicated objects, bytes and logs, evictions, fetches, deleted copies and aborted uploads. **Platform → Storage** shows it; the queue page shows the pause.

## Compatibility matrix

`crates/sentinel-s3/tests/compat.rs` runs every case against every service `crates/sentinel-s3/tests/endpoints.sh` starts (rootful Podman on loopback, images pinned by digest), and `crates/sentinel/tests/s3_offload.rs` runs the controller's replicator end to end against each. Measured 2026-09-28 on the verification VPS:

| Service (version) | Round trip | Multipart resume | Abort cleanup | `Content-MD5` refused | Signed SHA-256 refused | Wrong secret refused | Replicator end to end |
|---|---|---|---|---|---|---|---|
| Garage v2.4.1 | pass | pass | pass | pass | checked | pass | pass |
| SeaweedFS 4.47 | pass | pass | pass | pass | **ignored** | pass | pass |
| versitygw (2026-09 image) | pass | pass | pass | pass | checked | pass | pass |
| Zenko CloudServer (2026-09 image) | pass | pass | pass | pass | **ignored** | pass | pass |
| RustFS (2026-09 image) | pass | pass | pass | pass | checked | pass | pass |

- *Round trip*: put with metadata, head, full and range read, listing, delete, not-found after. *Multipart resume*: a 5 MiB part, a fresh client (a restart) learns it from `ListParts`, a second part, complete, metadata kept, a range across the part boundary. *Abort cleanup*: an open upload is listed, aborted, gone, its parts gone, nothing stored.
- *End to end*: an object and an 11 MiB multipart object copied and verified, both evicted and fetched back byte-identical, a multipart upload interrupted after its first part resumed, an unreachable bucket filling a 3 MiB backlog budget and closing admission until the real bucket drained it, and a reclaimed object's copy deleted.
- SeaweedFS and CloudServer accept a body whose signed SHA-256 does not match — the reason every body also carries `Content-MD5`, which they do verify.
- **Not run**: MinIO withdrew its public images and downloads in 2025 (the release URL answers `410 Gone`), so it is not in the matrix; Sentinel does not depend on it. Ceph RGW needs a cluster. Hosted services — AWS S3, Cloudflare R2, Backblaze B2 — are `Blocked by: credentials for a test bucket`; the client signs exactly as AWS's published Signature V4 example (`sigv4::tests`), and the matrix command takes any endpoint list.

Reproduce: `sh crates/sentinel-s3/tests/endpoints.sh up`, then `SENTINEL_S3_ENDPOINTS=/srv/sentinel-s3/endpoints cargo nextest run -p sentinel-s3 --test compat --no-capture` and `… -p sentinel --features server --test s3_offload`; `endpoints.sh down` removes the services.

## Verification

- `crates/sentinel-s3`: Signature V4 against AWS's published "GET Object" example, timestamps and URI encoding; the XML reader's records, entities, mismatched ends and depth bound; the matrix above.
- `crates/sentinel-store/tests/replicate.rs` (an in-memory bucket with fault injection): objects copied and verified once, evicted to a budget, fetched back verified, a corrupted remote copy refused and not placed, recovery not calling an evicted object missing; a multipart upload failing at its fourth part resumed by a new replicator sending only parts 4–6; a copy deleted after reclamation and one uploaded for a row reclaimed meanwhile deleted too; a finished log copied, recopied after a late change with a stale key dropped, and deleted on expiry; an outage closing admission past the backlog budget and draining reopening it; abandoned and stale uploads aborted, a recent one kept.
- `crates/sentinel-api/tests/web.rs::a_full_external_copy_backlog_is_what_the_queue_and_the_storage_report_say`; the service's `s3_settings_are_validated_before_anything_starts`.
