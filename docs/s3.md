# External S3 copy

The default installation needs nothing but its own disk. An `[s3]` section adds an **external copy** of what the controller stores — committed objects (artifacts and uploads) and finished attempt logs — in any service that speaks the S3 API. SQLite metadata stays local, always: the bucket holds bytes under content-addressed keys, never rows. Sentinel implements no S3 server and depends on none.

## What it does

The local disk stays the write path. A committed object or a finished log is durable the moment its local write is ([storage](storage.md)); the copy follows:

1. **Replication.** The controller's `sentinel-s3-replicator` thread copies committed objects oldest first: in one request up to `part_bytes` (16 MiB by default), as a multipart upload above it. A multipart upload is recorded (`s3_uploads`) the moment it starts, so after a crash or restart it **resumes** from the parts the bucket already holds (`ListParts`) instead of starting over. Every part is read once, in order, and hashed as it is read, so the bytes sent are the bytes checked: a part the bucket already holds from an earlier try is read and hashed but not sent, and the upload completes only when the whole digest matches (a file that changed under the upload is aborted and never made visible under the digest's name, whatever its size). Every copy is **verified** before its row records it (`objects.remote_ms`): `HEAD` must show the object's length and its BLAKE3 digest in the `x-amz-meta-blake3` metadata. Finished logs — released, stamped by retention and settled for 10 minutes, since a late end may still arrive — are copied file by file under `logs/<run>/<job>/<attempt>/`; keys a previous copy of the same log left are removed. A late end that changes a copied log resets its copy (`log_remote_ms`), and it is copied again; a late end that lands while the copy is in progress is caught too, because the copy is recorded only if the log's state is the one it started from. A log that retention expires while it is being copied has its copy deleted at once (its delete is queued in the same transaction that finds it expired). A log whose local directory is gone while a copy exists keeps that copy: it is counted as a local fault and nothing is deleted.
2. **Tiering.** Past `local_bytes`, or whenever the disk admission gate closes for low space, replicated objects are **evicted** locally, oldest first — never one a reader or stage pins, and never one without a verified copy (the `objects` trigger refuses `evicted_ms` without `remote_ms`). A read of an evicted object fetches it back into place first, **verified**: the bytes are hashed as they arrive and a wrong length or digest is `Corrupt`, never served, never placed. The next pass marks it local again.
3. **Deletion.** A copy is deleted only after its local record is gone: reclaiming an object queues its key (`s3_deletes`, by trigger), expiring a log queues its prefix, and a copy uploaded for an object reclaimed while the upload ran is deleted as well. Just before an object copy is deleted, the same transaction that drops the queued delete rechecks for a live `objects` row with that key: when identical content was committed again in the meantime (more than one batch of deletes can wait while the upload stage runs), the delete is dropped and the copy stays. If the recommit lands during the remote delete itself, the following replication stage in that pass uploads the live row again. Nothing here ever deletes the only copy.
4. **Abort cleanup.** Every 720 passes, multipart uploads the bucket holds under `<prefix>objects/` (the only key family this deployment uploads in parts, so a bucket shared with another application is left alone even with no prefix) that this deployment is not resuming and that are older than a day are aborted, and recorded uploads that old are aborted and forgotten, so abandoned parts do not accumulate charges.

Transport integrity does not depend on the service honouring the signature alone: every body carries **`Content-MD5`** (which every tested service verifies and refuses on mismatch) and its **signed SHA-256** payload hash (which some services skip; see the matrix). Both digests of a body come from one walk over its bytes in 64 KiB chunks (`client::body_hashes`), so a part is not read from memory twice to be hashed, and the replicator reads an object's bytes into the buffer's spare capacity instead of zero-filling it first; the buffer is kept between objects only up to the default part size (16 MiB) and freed after a larger configured part, so resident memory stays bounded by `part_bytes` only while an object is in flight. Sending `UNSIGNED-PAYLOAD` over TLS (dropping the SHA-256 pass) is not done: it would change what the compatibility matrix below was measured with. The client (`crates/sentinel-s3`) runs over the controller's rustls/ring stack: Signature V4 in the header form, bounded response sizes and timeouts, no redirects, no SDK, no async runtime. The CPU cost of those hashes and of signing is measured by `crates/sentinel-s3/examples/s3-hash-bench.rs` ([benchmarking](benchmarking.md#s3-hashing-and-signing)); no record is committed yet.

## Degraded durability and admission

While the bucket is unreachable or refusing, the replicator backs off (1 s doubling to 60 s), logs `s3_degraded` once, and keeps every local copy — the unreplicated bytes are the **backlog**, a bounded spool on the controller's own disk:

| Condition | Effect |
|---|---|
| Replication failing, backlog within `backlog_bytes` | `GET /admin/storage` says `s3.state: degraded` with the last error; everything else works. Local copies are kept, eviction takes only replicated objects. |
| Backlog past `backlog_bytes` | The disk admission gate closes (as below the low watermark): **new artifacts and uploads are refused** (`storage_full`, 507, retryable; an artifact the worker was streaming is recorded `failed`, and a required one fails its job with `Publication` — explicitly, never silently), and **no new work is placed**. The queue says so: `placement_paused: "external_copy_backlog"`, and a job otherwise ready waits with reason `storage`. Running jobs' **logs keep flowing** (they are refused only at the disk's log floor). |
| Backlog drains below nine tenths of `backlog_bytes` | Admission reopens, placement resumes, `s3_recovered` is logged. |

Required and optional data are distinct by construction:

- **Artifacts and uploads are required**: never evicted before their copy is verified, counted in the backlog, and refused rather than accepted beyond it.
- **Finished logs** are replicated for durability but never evicted locally; retention deletes them on both sides.
- **The remote cache store** ([cache](cache.md)) is optional and is **not** replicated: a cache entry that cannot be served is a miss, so an S3 outage never touches it.

A credential that expired or was revoked is a refusal like any other. The bucket answers `403`, the copy is `degraded` with the reason in `last_error`, nothing is uploaded, and the first pass after the key is replaced in `[s3]` and the controller restarted catches up.

**One refused item does not stop the queue.** A refusal for good (not a timeout or a `5xx`) is the item's own only when the bucket accepted other requests of the same kind in the same pass: a delete it refuses beside deletes it accepted, an upload it refuses beside uploads it accepted. Then the item (an object, a log, a queued delete) is parked, `last_refusal` says why, the pass succeeds and the stages after it still run. Without such a success, a refusal is taken for the credential or the endpoint: the pass fails as a whole, nothing is parked, and the next pass tries everything again. A transient error always fails the pass. A parked item waits 15 minutes, then 30, doubling up to 6 hours, and is tried again; parked items are counted in `parked_items` and are lost on restart, so a restart tries every one once more. At most 1,024 items are parked; past that an object-level refusal fails the pass as before. A refusal that is the only work of a pass cannot be told from a bad key, so it keeps the copy `degraded` until something else succeeds beside it.

**Damaged local copies.** The replicator hashes an object's local bytes before sending any of them. A local copy that is missing or does not match its digest is never uploaded under the digest's name. That object is **parked** and counted once (`local_faults`, `last_local_fault`; `parked_objects` and `parked_bytes` are the ones waiting now), the objects after it are still replicated, and the copy stays `healthy`, because the bucket is fine. A parked object is not read or hashed again for 15 minutes, then for 30, doubling up to 6 hours, so any number of damaged objects costs one read each per delay and none of them stands in front of a healthy one. Its bytes stay in the backlog, since they are not in the bucket: enough of them still close admission, and a repaired file is copied at its next retry. Run `sentinel admin objects verify` to find out what happened to the file.

**Failure accounting.** Any failure that stops a pass counts as one failure in `consecutive_failures` and sets `last_error`, whichever stage it came from: a bucket error, or the store or the local eviction failing before the bucket is touched. Health therefore reads `degraded` whenever replication is not progressing.

**Timeouts and the slowest link.** The transport's body timeouts are totals for one request, 60 s by default. A read of an evicted object is therefore made in ranged requests of 32 MiB, each with its own 60 s, and verified as one stream, so a large object is read over any link above about 0.5 MB/s instead of failing at 60 s on every attempt. A part is sent with 60 s, or the time it needs at 4 MB/s if that is longer (a 512 MiB part gets 128 s); a link slower than 4 MB/s needs a smaller `part_bytes`.

**A `404` on a delete.** A delete counts as done when the service says the key (`NoSuchKey`) or the upload (`NoSuchUpload`) is already gone. `NoSuchBucket`, or a bare `404` with no error document (a proxy, a wrong endpoint), is a refusal: the queued delete stays queued.

**Transport errors and body limits.** A transport failure is reported with one of a few fixed strings (`timed out`, `host not found`, `TLS failure`, …) and never with the request URL or headers: a presigned URL carries a credential in its query string, so putting the URL in an error would leak it. `get_object` sets its body limit to `Content-Length` plus one, because the transport already stops at `Content-Length` but `ureq` counts reaching the limit as exceeding it, so an exactly sized body would otherwise fail.

**Bounded remote text.** A refusal keeps only the service's error code and request id, and only when each is a short identifier (ASCII letters, digits, `.`, `_`, `-`, at most 64 bytes); a longer or free-form value is dropped and the error reads `http_<status>`. Remote prose is never echoed into an error or a log. Header values are signed in their canonical form (trimmed, internal whitespace runs collapsed), so a metadata value with repeated spaces authenticates, and a range read validates its bounds before sending (an inverted range is a caller error, not an overflow).

The default `backlog_bytes` is a sixteenth of the data file system, 1–64 GiB (62.9 GiB on the 1 TB reference host), beside the disk watermarks that still apply.

## Configuration

Server only ([configuration](configuration.md)):

```toml
[s3]
endpoint = "https://s3.eu-central-1.amazonaws.com"  # http(s)://host[:port], no path
region = "eu-central-1"
bucket = "sentinel-ci"
prefix = "prod/"                         # optional; ends in '/' when set
path_style = false                       # true for most self-hosted services
ca_file = "/etc/sentinel/s3-ca.pem"       # optional: trust these CAs instead of the Mozilla roots
credentials_file = "/etc/sentinel/s3.credentials"
part_bytes = 16777216                    # 5-512 MiB (default 16 MiB)
local_bytes = 0                          # keep replicated objects locally up to this; 0 (default) keeps all
backlog_bytes = 67549713920              # default a sixteenth of the data file system, 1-64 GiB
```

The credentials file is owner-only, at most 8 KiB, and holds `access_key_id = …`, `secret_access_key = …` and optionally `session_token = …`; its contents are never logged or echoed. Grant the key `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`, `s3:ListBucketMultipartUploads`, `s3:ListMultipartUploadParts` and `s3:AbortMultipartUpload` on the bucket and prefix, nothing more. At start the controller checks the bucket once (`s3_ready`, or `s3_unavailable` and it starts degraded — it never refuses to start for the bucket).

## Status

`GET /admin/storage` ([API](api.md)) carries `s3`: `state` (`healthy`, `degraded`, `unknown` before the first pass), `backlog_bytes`, `backlog_full`, `oldest_unreplicated_ms`, `unreplicated_logs`, `local_bytes`, `last_success_ms`, `last_failure_ms`, `consecutive_failures`, `last_error`, `last_local_fault`, and since-start counters of replicated objects, bytes and logs, evictions, fetches, deleted copies, aborted uploads and local faults (`local_faults`, each object counted once), plus `parked_items`, `parked_objects`, `parked_bytes` and `last_refusal`. `/metrics` carries `sentinel_s3_local_faults_total`, `sentinel_s3_parked_items` and `sentinel_s3_parked_bytes`. **Platform → Storage** shows it; the queue page shows the pause.

## Compatibility matrix

`crates/sentinel-s3/tests/compat.rs` runs every case against every service `crates/sentinel-s3/tests/endpoints.sh` starts (rootful Podman on loopback, images pinned by digest), and `crates/sentinel/tests/s3_offload.rs` runs the controller's replicator end to end against each. Measured 2026-09-28 on the verification VPS:

| Service (version) | Round trip | Multipart resume | Abort cleanup | `Content-MD5` refused | Signed SHA-256 refused | Wrong secret refused | Replicator end to end |
|---|---|---|---|---|---|---|---|
| Garage v2.4.1 | pass | pass | pass | pass | checked | pass | pass |
| SeaweedFS 4.47 | pass | pass | pass | pass | **ignored** | pass | pass |
| versitygw (2026-09 image) | pass | pass | pass | pass | checked | pass | pass |
| Zenko CloudServer (2026-09 image) | pass | pass | pass | pass | **ignored** | pass | pass |
| RustFS (2026-09 image) | pass | pass | pass | pass | checked | pass | pass |

- *Round trip*: put with metadata, head, full and range read, listing, delete, not-found after. *Multipart resume*: a 5 MiB part, a fresh client (a restart) learns it from `ListParts`, a second part, complete, metadata kept, a range across the part boundary. *Abort cleanup*: an open upload is listed, aborted, gone, its parts gone, nothing stored.
- *End to end*: an object and an 11 MiB multipart object copied and verified, both evicted and fetched back byte-identical, a multipart upload interrupted after its first part resumed, an unreachable bucket filling a 3 MiB backlog budget and closing admission until the real bucket drained it, and a reclaimed object's copy deleted.
- SeaweedFS and CloudServer accept a body whose signed SHA-256 does not match — the reason every body also carries `Content-MD5`, which they do verify.
- **Not run**: MinIO withdrew its public images and downloads in 2025 (the release URL answers `410 Gone`), so it is not in the matrix; Sentinel does not depend on it. Ceph RGW needs a cluster. Hosted services — AWS S3, Cloudflare R2, Backblaze B2 — are `Blocked by: credentials for a test bucket`; the client signs exactly as AWS's published Signature V4 example (`sigv4::tests`), and the matrix command takes any endpoint list.

Reproduce: `sh crates/sentinel-s3/tests/endpoints.sh up`, then `SENTINEL_S3_ENDPOINTS=/srv/sentinel-s3/endpoints cargo nextest run -p sentinel-s3 --test compat --no-capture` and `… -p sentinel --features server --test s3_offload`; `endpoints.sh down` removes the services.

## Verification

- `crates/sentinel-s3` (and `tests/loopback.rs`, a scripted loopback server: a slow object read in ranges inside budgets that one request would exceed, a server that ignores `Range`, an empty object, a wrong span refused, and `404`s on deletes): Signature V4 against AWS's published "GET Object" example, timestamps and URI encoding, whitespace canonicalisation of header values, range arithmetic, and the bounded error identifiers; the XML reader's records, entities, mismatched ends and depth bound; the matrix above.
- `crates/sentinel-store/tests/replicate.rs` (an in-memory bucket with fault injection): objects copied and verified once, evicted to a budget, fetched back verified, a corrupted remote copy refused and not placed, recovery not calling an evicted object missing; a multipart upload failing at its fourth part resumed by a new replicator sending only parts 4–6; a copy deleted after reclamation and one uploaded for a row reclaimed meanwhile deleted too; a queued delete dropped, not executed, when the same content was committed again; a store failure stopping a pass and degrading health; a finished log copied, recopied after a late change with a stale key dropped, and deleted on expiry; an outage closing admission past the backlog budget and draining reopening it; abandoned and stale uploads aborted, a recent one kept. Damaged objects: twenty lost files older than a healthy object, which is still copied and the passes converge, parked objects not read again until their delay and released when repaired. One refused delete or one refused object parked while the queue goes on, and a refusal with no success beside it failing the pass with nothing parked. A multipart object that changes during its upload, or in a part the bucket already holds, is aborted and never completed; a foreign upload under another prefix survives the sweep. A log expired mid-copy, a late end mid-copy, and a missing local log directory. Disk pressure evicting only replicated objects and stopping when the disk has room, and a full backlog not evicting for pressure. A file left by an interrupted eviction collected by recovery.
- `crates/sentinel-api/tests/web.rs::a_full_external_copy_backlog_is_what_the_queue_and_the_storage_report_say`; the service's `s3_settings_are_validated_before_anything_starts`.
