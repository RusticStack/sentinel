# Metadata storage (C02)

`crates/sentinel-store` is the controller's local metadata store: SQLite in WAL mode behind one dedicated writer thread, tenant-scoped row operations, and fenced compare-and-set transitions built on [core contracts](core-contracts.md).

## Bounds and failure behavior

Closed by the Parts 01–02 audit's C02/W02 gate. Every bound is a constant on the crate and every behavior has a wall-clock-asserted test in `crates/sentinel-store/tests/bounds.rs`.

| Resource | Bound | When exceeded |
|---|---|---|
| Read connections | `READER_LIMIT` (8) opened in total, idle ones pooled and reused | A caller waits up to `READ_ADMISSION` (2 s) for a freed reader, then gets `Error::Overloaded` — back-pressure, never a new connection. |
| Writer queue | `WRITER_QUEUE` (256) accepted jobs | `Error::WriterUnavailable` immediately; nothing was attempted. |
| Writer answer | `WRITE_WAIT` (10 s) | `Error::WriteAmbiguous`. The work is still queued or running and **may yet commit**; the store never claims a timed-out write rolled back. Re-read before retrying anything non-idempotent. |
| Panicking closure | caught on the writer thread | Its transaction unwinds and rolls back; the caller gets `Error::WriterPanicked`; the writer keeps serving. |
| Shutdown | `Store::shutdown(timeout)` | `Drained`, or `Stalled` when accepted work outlives the bound. Stalled work is never discarded, and the store then **keeps database ownership** until the process exits rather than inviting a second controller in underneath unfinished writes. |

**One controller owns the database.** `Store::open` takes an advisory OS lock on `<database>.lock` for the life of the store; a second opener — another process, or a misconfigured second controller — gets `Error::AlreadyOwned` at startup instead of a conflict at its first write. The lock is released by the OS on exit, including a crash. SQLite serializing writes is not a multi-controller scheduler design, and this is what enforces that.

## Engine decision

Measured 2026-09-13 with `cargo probe sqlite` and `cargo probe redb` on the same workload (2,000 single-transaction enqueues, a 100,000-row backlog, 2,000 pick-and-lease transactions), WSL2 ext4, two repeats; record in [`bench/c02-engines.jsonl`](../bench/c02-engines.jsonl).

Provenance of that record: it was produced by an invocation that was not committed. Its SQLite lines carry `"engine":"sqlite"` and every line carries `"fs"`, fields the probes do not emit and a driver injected (as [`bench/f07-storage.sh`](../bench/f07-storage.sh) does for `fs`). The record cannot therefore be regenerated from committed code as it stands, and its source commit and compiler are not recorded. [`bench/c02-engines.sh`](../bench/c02-engines.sh) was written afterwards from the record's shape so the procedure can be repeated; it does not reproduce the 2026-09-13 numbers, which remain a single-host development reference. The values in the table match the record (for example SQLite FULL dispatch 503 µs median and 1.41 ms p99; redb immediate 600 µs and 0.93 ms). The table's "redb `Durability::None`" is the record's `"durability":"eventual"`, which the probe maps to `Durability::None`.

| Engine | Mode | Enqueue commit median / p99 | Dispatch commit median / p99 | Ready pick | Batch insert |
|---|---|---:|---:|---:|---:|
| SQLite 3.53 | `synchronous=FULL` (durable) | 0.50 ms / 1.56 ms | 0.50 ms / 1.41 ms | 2.0 µs | 1.5 M rows/s |
| redb 4.2 | `Durability::Immediate` (durable) | 0.56 ms / 1.13 ms | 0.60 ms / 0.93 ms | 0.8 µs | 1.3 M rows/s |
| SQLite 3.53 | `synchronous=NORMAL` | 5 µs / 17 µs | 6 µs / 21 µs | 0.3 µs | 1.5 M rows/s |
| redb 4.2 | `Durability::None` | 10 µs / 19 µs | 13 µs / 27 µs | 0.2 µs | 1.4 M rows/s |

Both durable paths are bound by the same fsync and land within 20% of each other; redb has a tighter p99, SQLite a lower median and 2x the non-durable throughput. Neither is the bottleneck for a CI controller whose intake is webhooks. The decision therefore rests on what the engine gives for free: SQLite provides declarative constraints (foreign keys, uniqueness, `CHECK`), partial indexes, ad-hoc queries for diagnostics and the web UI, the online backup API, and a file format every operator tool reads. redb would require hand-built secondary indexes and constraint checks in Rust, code that has to be as correct as SQLite's and would not be faster. sled is still alpha and jammdb has had no commits since 2023; neither was benchmarked. **Decision: SQLite via `rusqlite` (bundled), reconsidered only if profiling of a real controller shows the writer thread saturated.**

## Layout and ownership

Migrations are an append-only list of `(version, sql)` in `schema.rs`; each runs in its own `BEGIN IMMEDIATE` transaction and is recorded in `schema_migrations`. Version 1 creates `tenants`, `repos`, `runs`, `jobs` and `attempts` as `WITHOUT ROWID` tables keyed by 16-byte IDs. Version 2 adds `run_specs` (the immutable compiled specification per run: pipeline digest, format byte, postcard blob) and `jobs.spec_index`. Version 3 adds `idempotency_keys`, scoped to (tenant, principal, route): `idempotency::begin` decides execute/replay/mismatch inside the mutation's own transaction and `complete` records the created run, so a duplicate can never execute twice. A record older than the 24-hour TTL is dead to `begin` (it executes afresh and overwrites it); `idempotency::purge_expired` removes expired records oldest first off `idempotency_by_age`, at most a batch per call, and the controller's maintenance tick calls it with the credential purges (1,000 rows per kind every ten minutes, and every second while a kind still fills its batch), so distinct keys do not accumulate forever.

The list is contiguous from 1 by construction: a compile-time assertion in `schema.rs` (and a unit test) refuses a build whose versions are not exactly `1..=N` in order, and `migrate` refuses to apply an entry that is not the database's version plus one (`Corrupt("migration order")`). An out-of-order, renumbered or duplicated entry would otherwise be skipped silently by databases already past it and applied by fresh ones.

Migration 31 (`031_foundation_hardening.sql`) makes `run_specs` rows immutable: a `BEFORE UPDATE` trigger aborts any update, raw SQL included, as the attempt summary and image-digest triggers already do for their write-once facts. `tests/runs.rs` proves it against raw `UPDATE`s of `spec`, `digest` and `format`. Decoding is strict as well: `RunSpec::decode` rejects a blob with bytes left over after its format's layout.

Tenant-owned tables carry `tenant_id`; global human users/external identities are linked through memberships. Inserts of runs and jobs are `INSERT … SELECT` from the parent row filtered by tenant; both fail as `NotFound` for a missing or foreign parent. Controller read/transition predicates include `tenant_id`, but these trusted helpers alone do not authorize a user.

Version 4 adds [identity and authorization](authorization.md): namespaces/users/external identities, memberships and explicit repo grants. New grants use composite ownership FKs; triggers enforce equal tenant ownership across the existing parent/child graph even through raw SQL. Migration refuses inconsistent existing rows and unknown newer versions. Client-facing repository and spec queries join current membership/grants and credential scope; authorized dispatch derives the owning tenant inside its writer transaction.

Encodings: IDs are raw UUID bytes; `state_code` is one integer with terminal states at 16 plus the outcome, so the ready-queue partial index is `WHERE state_code = 1` and `>= 16` means finished; `failure_class` uses the core discriminant; timestamps are UTC milliseconds, first entry wins via `COALESCE`.

Version 14 ([worker link](worker-link.md#dispatch-w02)) copies each job's `cpu_millis`/`memory_bytes` from its spec, records a worker's reported capacity, and makes the attempt row the reservation: `cpu_millis`, `memory_bytes`, `offered_ms`, `acked_ms` and `released_ms`, with `attempts_held_by_worker` (partial, `released_ms IS NULL`) for the capacity sum and `attempts_pending_ack` (partial, unacknowledged and held) for the ack-timeout sweep. A trigger fixes an attempt's identity, worker and reservation at the lease and refuses to undo an acknowledgement or a release.

Version 15 ([executor](executor.md#steps-w04)) adds `attempts.summary` (at most 32 KiB, the worker's encoded `AttemptSummary`), written once with the terminal report; the recreated `attempt_update` trigger refuses to replace it.

Version 16 ([cancellation](cancellation.md)) copies each job's execution timeout to `jobs.timeout_ms` for the controller's backstop and adds `attempts_held_by_lease` and `jobs_queued_since`, the partial indexes the expiry and queue-timeout sweeps walk.

## Writer and acknowledgement policy

One thread owns the only write connection. `Writer::write` sends a closure over a bounded channel (256 slots), runs it inside `BEGIN IMMEDIATE`, commits, and only then replies. With `synchronous=FULL` the WAL is fsynced before `COMMIT` returns, so **a write is acknowledged to the caller only when it is on disk**. This is the contract worker acknowledgements, lease grants and cancel requests rely on. `Durability::Normal` exists for replayable data and tests; it is never used for transitions.

A full queue returns `WriterUnavailable` immediately instead of blocking or growing; callers shed load or retry with back-off. Readers use separate read-only WAL connections and observe a committed snapshot; the pool, the writer's answer and shutdown are bounded as the table under [Bounds and failure behavior](#bounds-and-failure-behavior) lists. Long read snapshots can still constrain checkpoint progress.

At the API a `WriteAmbiguous` answer is `503 outcome_unknown`, not retryable as is ([protocol](protocol.md#structured-errors)); `WriterUnavailable` and `Overloaded`, where nothing was attempted, stay `429 rate_limited`.

**Commit notifier.** The store carries a commit generation (`Store::changes()`, the `Changes` type) that long polls park on (O05, [API](api.md)). The writer bumps it after every `write` or `raw` closure whose work succeeded — for `write`, only once `COMMIT` has returned — and before the caller's reply, so a caller that got its acknowledgement never observes the previous generation. A write that fails, rolls back or panics bumps nothing. Waiters register, then re-check the generation (`SeqCst`), and the writer notifies under the lock, so no wakeup is lost; the writer's cost per commit is one atomic add and one load. A generation says only "something committed": a waiter re-reads what it cares about (for a run wait, the run's version, at most every 10 ms). `tests/changes.rs` covers ordering, rollback, 1,000 racing commit/wait cycles and eight concurrent waiters.

## Transitions

`jobs::transition` reads the row, lets `JobControl::apply` decide (actor permission, fence, edge), then executes one static `UPDATE … WHERE id=? AND tenant_id=? AND state_code=? AND fence=?`. Zero rows changed means the row moved between read and write: `Conflict`, and the transaction rolls back. `jobs::lease` bumps the fence, transitions to `Leased` and inserts the attempt row in the same transaction. `jobs::pick_ready` is a single indexed `ORDER BY priority, created_seq LIMIT 1`; the test asserts the query plan uses `jobs_ready`. `jobs::run_state` recomputes the run outcome from job rows through the core aggregation. `runs::create_run` writes the run, its spec and its job rows in one transaction (dependency-free jobs start `Queued`); `runs::rerun_job` applies the core `Rerun` edge with a compare-and-set that clears attempt history and keeps the fence.

## Fleet placement (Q01–Q04)

Migration 28 adds what a job needs beyond CPU and memory (`disk_bytes`, `arch`, `labels`, `concurrency_group`) and what a worker reports beyond its capacity (`disk_bytes`, `labels`, `host_id`, `drain_ms`, `avail_images`, `cache_bytes`, `load_ns`). `runs::create_run` copies the compiled job's disk, architecture, labels and rendered concurrency group onto the job row in the same transaction, and `jobs::lease` copies the disk reservation onto the attempt beside CPU and memory. Migration 35 adds `jobs.repo_id` (copied from the run at insert), `jobs.pull_request` (set by a trigger when the run's `pull_request` provenance is recorded) and `attempts.repo_id`, and replaces the placement indexes (below). Migration 28's own comments overstate two things that were never built: `wait_code`/`wait_detail` were never written and `jobs_fair` never read — migration 35 drops all three, and `load_ns`/`cache_bytes` are now read by the dispatcher's ranking. Migration 36 adds `jobs.image_name`, the repository part of the job's image reference, which `runs::create_run` writes beside the digest (only names in the OCI reference charset, 1–255 bytes) so the prefetch pass (K05) can hint `name@digest` without decoding a spec. `dispatch::prefetch_hints` reads the longest-waiting ready jobs through `jobs_queued_since` — a scan of that partial index bounded by `PREFETCH_SCAN` (256), sorted in memory by priority and age, pinned by both plan tests below — plus one grouped held-CPU read, one point read per worker and one pool-access probe per (tenant, pool) it meets; see [executor](executor.md#the-image-pull-k05) for what it hints to whom.

**Hard admission.** `dispatch::place` considers only jobs whose CPU, memory and disk fit the worker's free capacity, whose architecture is the worker's (`jobs.arch` is stored in the same spelling as `workers.arch`), whose labels are a subset of the worker's, whose image is durably resolved, whose pool admits the tenant, whose worker is not draining, and whose concurrency group is free for it (below). Every one of these is in the candidate statement itself, labels included: `sentinel_labels_subset(job, worker)` is a deterministic SQL function registered on every store connection (`sentinel_store::register_functions`) that compares the two sorted, newline-separated label blobs with one merge walk and no allocation, and the unlabeled case (`labels = X''`) never calls it. Labels used to be filtered in Rust after a per-tenant `LIMIT 32`, so a page of `gpu` jobs hid a fitting plain job from an idle worker (P08-4). Disk is a hard gate only for a worker that reported it: `disk_bytes = 0` means a protocol-6 worker never reported disk (migration 28's default), and such a worker is not disk-admitted — unreported is absence, not a zero-sized scratch area. Labels and architecture are always hard; a worker that reported no labels carries none. `dispatch::report_capacity` owns CPU/memory/disk; `dispatch::report_profile` owns the rest so either call order leaves both halves current, and a fact a worker does not report keeps its last recorded value rather than being written as zero. A job no worker can ever run is not rejected at enqueue — a worker able to run it may enroll later — but explained (`NoMatchingWorker`, `ArchMismatch`, `LabelMissing`, `DiskShort`) and bounded by `QUEUE_TIMEOUT_MS`; it no longer reserves anything while it waits (below).

**Host reservation.** `dispatch::free_capacity` subtracts the attempts of every worker sharing the same `host_id`, not just the worker's own: several identities on one machine each measure that machine, so the aggregate of their reservations may never exceed one host's report. A worker with no host on record accounts for its own attempts alone. Values may go negative when a report shrinks under live reservations. Two consequences operators must know (P08-12): a `cpu_millis`/`memory_bytes` override on identities that share a host must state the **whole host's** capacity, not a split — two identities overridden to 8,000 each on one 16-core host share 8,000, not 16,000 — and identities that report no host id (in a container without `/etc/machine-id`, say) are each accounted alone, so several of them on one machine can oversubscribe it. `host_id` is worker-asserted: a worker credential can claim another host and shrink that host's free capacity, never grow its own. [Configuration](configuration.md) states both.

**Fair queue.** Ready work is read as (tenant, repository) *streams* from the `jobs_ready_repo` partial index (`tenant_id, repo_id, priority, queued_ms, created_seq WHERE state_code = 1`). The streams are ordered by the tenant's held millicpu (least first, from the covering `attempts_held_by_repo`), then the repository's held millicpu within its tenant, then the repository's head job — priority, then arrival — so the head that has waited longest goes first among equals (aging). A repository with a thousand-job backlog therefore takes turns with its siblings instead of draining first (P08-5; a repository used to have no term at all). Tenants the pool admits are found with one `EXISTS` descent per tenant; a tenant's ready repositories with a loose index scan (one `MIN` seek per repository); held sums are skipped where there is nothing to rank (one ready tenant; one ready repository in a tenant). Candidates are read a page (16) at a time per stream in the fair order with a keyset, and only the bounded locality hold (below) can skip a row after SQL has admitted it, so a stream is paged past held rows for at most eight pages (128 rows) per placement before the next stream is tried — never an unbounded walk, and never a hidden job behind a cut.

**Reservations.** A waiting job at or above `LARGE_JOB_CPU` (8 cores) reserves a path: a younger, smaller job is not placed if that would leave the worker unable to run it — small jobs are still backfilled while the large job's remainder stays free. While a pull-request job waits, `PR_RESERVE_DIVISOR` (a quarter) of the worker's reported millicpu — its host's, since an identity reports the whole host — stays free for it. Both count only a job **this worker could run**: a tenant its pool admits, and an architecture, labels, resources and concurrency group that allow it on this worker (the same predicates as the candidate scan). A large job in another tenant's dedicated pool, or one no worker here can ever run, reserves nothing, and nor does a pull-request job this worker cannot run (P08-2); the pull-request reserve no longer sums every identity on the host (P08-3). Both reservations are terms of the candidate statement, so a held job is never read only to be rejected; a worker whose free room is already inside the pull-request reserve reads only pull-request candidates, from their own `jobs_ready_pr` index.

**Work only this worker can run goes first (Q10).** `dispatch::place_in_fleet` is `place` told, per resource, the most any *other* connected worker of the pool holds (`elsewhere`; the controller computes it per sweep from the sessions' reported sizes, a worker with no reported disk counting as unbounded). When this worker's free room exceeds `elsewhere` in some resource, a first pass over the streams reads only candidates exceeding `elsewhere` — jobs no other connected worker can run — and offers the first; otherwise (or when that pass finds nothing) the normal pass runs. Every hold above still applies. Without it the fair order could spend the only large worker's room on quarter-core jobs a smaller worker was about to take, leaving a job that fits nowhere else queued until that work finished. The exclusive pass never runs on a worker that is not the largest in some resource. It is an ordering, not a reservation: a job that does not fit the worker's free capacity now is not waited for (that is the `LARGE_JOB_CPU` path).

**Bounded locality.** A worker without the job's image passes while another worker that could run it holds the image and is expected to free within `LOCALITY_WAIT_MS` (30 s). "Expected to free" is the earliest held attempt's offer plus its job's timeout — an upper bound on completion — or now when it holds nothing; it used to be the lease deadline, which renewal keeps inside the window forever, so any busy warm worker looked about to free (P08-6). Past the bound any eligible worker takes the job, so cache affinity never strands work. Worker cache images are matched by the first eight bytes of the image digest (`dispatch::image_key`), the same key the protocol-7 profile reports. The locality view is read per tenant, once per placement, and only when some worker has reported an image.

**Concurrency groups.** A group is a (tenant, repository, key) lock (`jobs_conc` is `tenant_id, repo_id, concurrency_group`). A job's group is free for it when no other run of the same group has a job a worker owns (`Leased` through `Finalizing`) and no **older** run — by `(runs.created_ms, runs.id)`, a total order — has any live job. A queued run therefore waits only for runs ahead of it: two queued runs of a serializing group used to exclude each other and neither ever placed (P08-1). When `cancel_in_progress` is set, creating the run cancels every live run of the same repository holding the same rendered group that is not newer than it (`created_ms <=`, so two runs created in the same millisecond still supersede — the one applied later wins). A group template that needs `event.*` is applied by `runs::apply_concurrency` once the run's provenance is recorded (the intake path calls it in the same transaction), because guessing the event would key the group wrong; a template that cannot be evaluated for a run leaves the group unset and supersedes nothing. Lease ownership stays per attempt: the group orders runs, and the fence still decides which worker may report.

**Queue explanations.** `dispatch::wait_reason` names the blocking fact by asking placement's own questions of every connected worker that could run the job: `Dependency` (blocked), `Policy` (cancel pending, image unresolved), `ConcurrencyLimit` (the group predicate above, negated), `ArchMismatch`, `LabelMissing`, `NoMatchingWorker` (CPU/memory shortfall), `DiskShort`, `FairnessHold`, `LocalityWait`, `Capacity` (connected workers could run it once their work releases), `Drain`, `WorkerOffline`, and `Ready` — nothing holds it and a connected worker has the room now, so the next dispatch pass places it unless older work in the fair order takes that room first. `Capacity` used to be the fall-through for a job a label cut had hidden from an idle worker (P08-4). `dispatch::list_queue(conn, tenant, connected, limit)` returns at most `limit` waiting jobs — queued oldest first, then blocked — each with its reason and its age against the controller clock, and `total`, the count of the tenant's waiting jobs. The limit is applied in the query (`jobs_waiting`, `tenant_id, queued_ms, created_seq WHERE state_code IN (0, 1)`: a range read that stops at the limit, no sort), and what a reason reads that is not the job's own row — the admissible workers, each connected worker's free capacity and reservations, the tenant's locality view — is read once per call. Explaining every waiting job before the route cut the page took 5.9 s for 5,000 queued jobs and 20 workers; it now takes 3.7 ms (WSL2 release, `fleet_load.rs::listing…`, P08-8).

**Drain.** `workers::drain` records a durable moment after which the worker takes no offers but keeps running what it holds; `workers::undrain` returns it to service. Both are platform-administration operations and refuse a revoked worker; re-draining keeps the first timestamp.

**Revocation.** A revoked worker holds nothing: `acknowledge`, `renew` (`Forbidden`), `report`, `is_held`, `attempt_scope` and `attempt_log_scope` all require `workers.revoked_ms IS NULL`, and `dispatch::reconcile_revoked` (driven from the `workers_revoked` index, one sweep batch per call) ends its acknowledged attempts `Reconciled` and lapses its unacknowledged offers. The controller runs it at start and whenever `dispatch::revocations` — the latest `revoked_ms` and the revoked count — changes ([worker link](worker-link.md)).

**Leases.** `renew` refuses a lease that has already passed (`lease_until_ms >= now`), so a late beat cannot resurrect an expired attempt, and `expire` re-checks the deadline (or the execution backstop) in its own transaction, so an attempt renewed between the sweep's read and its write is not expired (P08-13).

**Placement cost.** The placement loop is per-offer work, so every statement in it reads by index, and every partial-index predicate is written as a *literal* (`state_code = 1`, `cpu_millis >= 8000`, `pull_request = 1`, `state_code IN (0, 1)`, `released_ms IS NULL`). The reason is not the one this section used to give. With the bundled SQLite (3.53.2) a bound parameter does **not** silently disable a partial index: SQLite re-prepares a statement when a bound value can change whether a partial index applies, and the re-prepared plan uses it (the audit measured `fullscan_steps = 0, reprepares = 1` for a bound state code). A literal is still right because it fixes the plan at prepare time with no re-prepare per execution. The Q09 "258 s → 52 s" improvement is better attributed to replacing grouped scans with per-tenant probes than to literals. What did scan was the pull-request probe: it walked the whole ready queue on every placement (3.1 ms of a 7.2 ms `place` at 10 k ready jobs), and migration 29's `jobs_ready_run` and `provenance_pr`, added for it, appeared in no plan; migration 35 drops both. The probe now reads `jobs_ready_pr` (ready pull-request jobs only), so none waiting is one empty index probe. The candidate page, the pull-request page and both reservation probes name their index with `INDEXED BY` (a statement whose index became unusable fails to prepare instead of silently scanning). Free capacity, tenant and repository deficits and the dispatcher's per-worker load are index-only sums over the covering `attempts_held_by_worker` (`worker_id, cpu_millis, memory_bytes, disk_bytes`) and `attempts_held_by_repo` (`tenant_id, repo_id, cpu_millis`). `jobs::lease_reserved` takes the resources the candidate row already carries instead of re-reading the job. Two tests pin all of this: `dispatch::tests::placement_statements_plan_their_indexes` asserts each statement's `EXPLAIN QUERY PLAN` names its index, never sorts and never scans `jobs` or `attempts` (a scan only of the statement's own partial index is allowed), and `placement_statements_never_scan_the_queue_at_runtime` executes each against a 2,000-job queue and asserts SQLite's own counters — zero full-scan steps and zero sorts — which is what a changed runtime plan would show and a compile-time plan cannot.

**Load evidence (Q09).** `tests/fleet_load.rs` is store-level: 100 worker identities (50 hosts, two identities each, reporting whole-host capacity), 10,000 queued quarter-core jobs from four tenants (one with 70 % of the runs) over twelve repositories, a tenth of the runs pull requests and an eighth needing a label half the fleet has. It places in the controller's round structure (one placement per hungry worker per writer transaction) and **holds** what it places — capacity fills as a real fleet's does — until no worker can take more; then the wave completes and the next places. It asserts every job is placed exactly once, no host goes negative, and each quiet tenant gets at least its share of the first wave, and records per-placement latency, queue wait, throughput and (Linux) CPU, peak RSS and I/O in `bench/q09-fleet-load.jsonl`. It runs no TLS session and no executor: the 100 concurrent real TLS sessions are `sentinel-link/tests/fleet_sessions.rs` (100 sessions × 200 jobs), a separate test, and the three-worker link fleet (`sentinel-link/tests/fleet.rs`) covers partitions, stale fences, drain, spreading a burst over identical workers, revocation of a live session and a counted placement failure. Controller restart is covered by `sentinel-link/tests/link.rs` for a single worker, not in the fleet suites.

## Objects and manifests (D01)

`sentinel-store::objects` is the controller's content-addressed body store, under the same data directory as the database:

```text
<data>/objects/<tenant>/<hex[0..2]>/<hex-digest>        committed objects
<data>/manifests/<tenant>/<kind>/<name-hash>/<version>  manifest files
<data>/tmp/<unique>                                     staging, never committed
```

Objects are addressed by their BLAKE3-256 digest and deduplicated **within one tenant only** — identical bytes stored by two tenants are two objects, so object existence never leaks across tenant boundaries. A reference commit is the `objects` row (migration 23): `stage` streams the body to `tmp/` hashing in one pass, verifies any declared length/digest and the caller's byte cap, `fdatasync`s the file, atomically renames it into the tenant's namespace and `fsync`s the directory chain; `commit` then inserts the row inside the caller's transaction. A crash between rename and commit leaves an **orphan** — wasted space, never a published incomplete object. A second stage of bytes the tenant already holds (a dedup hit) skips the `fdatasync`, drops its temporary copy and adopts the existing file. The triggers on both tables refuse `UPDATE`; rows leave only through reclamation (D06).

**Who may delete an object's file.** A deduplicated file has no single owner, so the decision is never taken from the filesystem alone. A stage *pins* `(tenant, digest)` in the same locked step as its "does the file exist" decision and holds the pin until the `Staged` is dropped — after its commit, which runs on the writer. A live `Reader` pins the same way. Every deletion — `Objects::discard` of an abandoned stage, `Objects::unlink` of a reclaimed object, a retired manifest version or an orphan-sweep find — runs **on the writer** and removes a file only when no pin holds it and no committed row names it (and, for a sweep find, when it is still older than the one-hour grace). So a failed publication cannot delete bytes a concurrent identical publication committed, the orphan sweep cannot take an aged orphan a new stage just adopted, and a reclaim's unlink cannot remove a file the same content was committed to again after the row delete. `tests/faults.rs` and `tests/artifacts.rs` drive each interleaving.

Manifests are named, monotonically versioned lists of object references (`kind`, `name`, `version` → immutable file + row). `commit_manifest` chooses `MAX(version)+1` inside the transaction, **refuses references to objects the tenant has not committed**, writes the manifest through the same stage discipline and inserts the row — a manifest can never dangle. Entry paths are `/`-separated relative archive names; `.`/`..`, absolute, drive-prefixed and separator-bearing components are refused at commit. The row records the manifest file's own digest and the summed payload length for quota and retention accounting without reopening the file.

Reads are verified: `read` streams the object while rehashing and compares digest *and* length to the committed row; `manifest` parses the file and checks it against its committed digest and identity. A committed row whose file is absent or short is `Corrupt`, not `NotFound`.

**Recovery.** The server opens the store and runs `recover` at startup (logged as `objects_recovered`); `sentinel admin objects recover` runs the same reconciliation host-locally while the controller is stopped. It removes anything in `tmp/` (incomplete staged writes), then walks both trees against the committed rows: files with no row are **orphans** (reported, never deleted — a staged-but-uncommitted file and a leaked file are indistinguishable), files whose row disagrees on length are **corrupt**, and rows with no file are **missing**. `verify` — `sentinel admin objects verify` — rehashes every committed object for the deeper integrity check that catches content rot a length check cannot see; it is a drill, not a per-request cost.

## Resumable uploads, reads and materialization (D02)

`<data>/incoming/<upl_…>` is durable staging for resumable upload sessions, backed by the `uploads` table (migration 24): each row records the owning tenant, declared length, an optional declared digest, a compact blob of received byte ranges, an expiry and a state (`open` → `committed`/`aborted`).

- `begin_upload` creates the row and a file pre-sized to the declared length in one transaction. `put_chunk` writes a chunk at a client-chosen offset — bytes are `fdatasync`ed **before** the range is recorded, so a crash can never claim bytes it does not hold — and overlapping or identical re-sends merge into the range set, making retries idempotent without corrupting the count. `upload` reports the sorted disjoint ranges so a resuming client sends exactly what is missing. Chunks outside the declared length, sessions past their TTL (≤ 24 h), and any write to a sealed or aborted session are refused. Touching an expired session retires it in **its own** writer transaction (`retire_expired`, then `drop_upload` removes the staging file and charge once that committed) and only then refuses the request — retiring inside the refused request's transaction would roll back with it. A declared length past `MAX_UPLOAD_BYTES` (4 GiB, the single-artifact-entry ceiling) is refused at `begin_upload` whatever the quota: with the default quota of 0 (unlimited) it is the bound on one session.
- **File work stays off the writer.** A chunk is two phases: `write_chunk` checks the session on a read connection, admits the newly covered bytes, writes and `fdatasync`s them under the upload's I/O lock (64 stripes by upload id); `record_chunk` is the writer's short transaction that re-checks the session and merges the range. A seal is two phases too: `prepare_seal` hashes the staged file under the same I/O lock (so a re-sent chunk cannot change bytes after they were hashed), checks the declared digest, pins the object path and renames it into place; `finish_seal` is the writer's bookkeeping — re-check the session, close it, insert the object row. A multi-GiB seal therefore never holds the writer: `tests/storage.rs` keeps writer round trips completing while a 64 MiB seal hashes. `put_chunk`/`seal_upload` remain as one-connection conveniences for host-local tools and tests.
- Sealing requires the ranges to tile `[0, len)`, rehashes the staged bytes and checks them against the declared digest, then renames the file into `objects/<tenant>/…` and commits the reference — the D01 publish order is preserved, so a crash can orphan but never publish a partial object. Sealing twice answers the same digest; a digest mismatch keeps the session open so the client can rewrite whichever ranges were wrong.
- `sweep_uploads` retires expired sessions and drops their files; it runs at server startup and as `sentinel admin objects sweep`. `recover` keeps files that still have an open row and sweeps the rest.

Downloads go through `open_read`, which pins `(tenant, digest)` with a live `Reader` and hands out a seekable handle; the pin drops with the guard, and reclamation never unlinks a pinned file. `materialize` writes a manifest's entries into a directory: entry paths are re-validated, every existing ancestor component under the destination is checked for symlinks, existing targets are refused, and object bytes are verified while streaming — so a destination prepared *in advance* cannot redirect the extract. The checks are path-based (check, then `create_dir_all`), so they do not hold against a directory an adversary changes while the extract runs; no controller path calls `materialize` today, and a caller extracting into space others can write needs a descriptor-relative (`openat`) walk first.

The API exposes this as `POST /tenants/{slug}/uploads`, `GET|PUT|DELETE /uploads/{upl}` (`PUT` takes `?offset=` and a raw body of at most 8 MiB), `POST /uploads/{upl}/commit` and `GET /tenants/{slug}/objects/{digest}` with `Range: bytes=…` support. Upload sessions require operator-level tenant membership. Downloads authorize through repository evidence (`auth::require_object_read`): the caller must be able to `READ` a repository with an artifact whose manifest references the digest, or be an operator-or-above member holding `RUN` in a tenant where the digest was committed through an upload; platform scope confers nothing, and a refusal is the same `not_found` as an unknown digest. An upload id resolves its owner before authorization so a foreign id is indistinguishable from a missing one. At most three transfer bodies are in flight at once (`TRANSFERS`), counted until a download's body has been written, and seals hold a slot while they hash; the next request is `rate_limited` rather than queued work. A whole-object download is rehashed while it streams and ends short of its declared length if the bytes no longer match their digest; range reads are not verified.

## Artifact records (D03)

The `artifacts` table (migration 25) is the durable outcome of each declared artifact on an attempt: one row per `(attempt_id, name)` with the job and run for scoping, a terminal `state_code` (`captured`, `absent`, `failed`), entry and byte counts, the `manifests` version when captured, the retention deadline and the creation timestamp. `UNIQUE(attempt_id, name)` makes a redelivery a conflict rather than a duplicate; the state/identity columns sit behind the usual immutability triggers.

A captured row and its manifest commit in **one writer transaction**: the controller stages each file body through `stage_begin`/`stage_write`/`stage_seal` (the streaming counterpart of `stage` — a `Staged` keeps the same rename-then-commit discipline and pin, and `Objects::discard` on the writer never removes a file another stage or committed row owns), commits the object references, commits the `{job_id}/{name}` manifest under `Kind::Artifact`, then inserts the artifact row. Absent and failed outcomes write only the row. A partial publication that never reaches `ArtifactEnd` leaves staged files that `recover` or the orphan sweep collects and in-flight byte accounting that the session drop releases; no artifact row exists for it, so nothing claims it. Each attempt's publication has its own lock: file writes, `fdatasync`s and renames happen under it, and the controller-wide artifact map is held only to find the publication and to charge the run budget.

The API lists a run's artifacts (`GET /runs/{run}/artifacts`) and shows one row's detail (`GET /runs/{run}/artifacts/{arf}`), the latter inlining the manifest's entry paths, digests, lengths and modes; entry bytes download through the existing `GET /tenants/{slug}/objects/{digest}` route.

## Segmented logs (D04)

Attempt logs no longer live in one flat `logs/<attempt>.log` file. Each attempt owns `logs/<run>/<job>/<attempt>/`: `seg-NNNNNN` record segments sealed at 4 MiB and compressed to `seg-NNNNNN.z` (zlib, `SNLZ` format 1) by a background thread, a sparse `index` (`SNLI` format 1; 41-byte checkpoints on segment starts, step changes, every 64 frames, and a seal record per closed segment), and the atomic `end` marker (`SNLE` format 1) that is the single completeness boundary. Sequence jumps record holes instead of refusing; fills narrow them; the marker's gap list merges observed holes, worker-declared gaps and the never-stored tail (≤ 1,024 ranges, coalesced). Reopen truncates torn segment and index tails, rebuilds a missing index, repairs an end record that reached a segment without its marker, and re-queues un-compressed sealed segments. Reads seek by sequence through the index and can filter to one step; pre-D04 flat files still read through `read_tail`. The full contract is in [logs](logs.md#on-the-controller-segments-index-and-the-end-marker-d04).

## Terminal publication (D05)

A job's terminal transition now carries its data status in the same transaction — `finish` is also the finalization boundary:

- **`attempts.log_state`** (migration 26) records the log's durable status: `pending` while live, `complete` once the `end` marker is on disk, `incomplete` when the job went terminal first. The `LogEnd` handler writes the marker, then the row, and only then answers `Acked`/`LogEndAck`; the writer-transaction commit means an acknowledgement is never sent for a status that is not durable. The recreated `attempt_update` trigger adds `NEW.log_state < OLD.log_state` to the forbidden moves — the column may heal `incomplete → complete` on a late retransmitted end, never regress.
- **Artifact coverage is checked against the stored run spec**, not the worker's claim: for every declaration due under the outcome (`when`), a row must exist, and a *required* one must be `captured`. Due-but-missing declarations get `failed` rows so the loss is on record; a reported `Passed` standing over an uncaptured required artifact is applied as `Failed(Publication)` instead. Optional misses and not-due declarations change nothing but the row set.
- The same stamping runs on every terminal path — `report`, `expire`, `abandon`, `reconcile_startup` — all take the `LogStore` so the answer to "was the end marker durable at publication" is the marker itself, not a worker's claim. A caller without a log store (`None`) answers `incomplete`, never `complete`.

Because log frames and `LogEnd` are accepted for an attempt the worker owns even after release (`attempt_log_scope`), a post-terminal retransmission can still land its marker and upgrade `incomplete → complete`; artifact publication stays held-only, since it is part of the verdict.

## Disk admission, quotas and reclamation (D06)

One `Admission` gate (`sentinel_store::space`) watches the filesystem holding the data directory — `statvfs` on Unix, `GetDiskFreeSpaceExW` on Windows — with the probe result cached for one second. The model is a single axis of free bytes: `reserve` is held back for the metadata database and log evidence, `low`/`high` are the close/reopen hysteresis for discretionary admission, and `floor` (inside the reserve) is where even log frames refuse. Between probes the in-flight charge is what keeps concurrent writers honest: `admit` charges promised-but-uncommitted bytes per tenant and per filesystem, released when the bytes land (the next probe sees them) or the write is abandoned. A refused frame is reported `StorageFull`, never silently dropped and never recorded as a log hole.

Object staging and streaming artifact writes charge per write; resumable uploads charge only the byte ranges each chunk actually adds (re-sent ranges are free), with the charge released on seal, abort, expiry or a failed write. `begin_upload` also checks the tenant's quota against `tenant_usage` — committed object bytes plus open uploads' declared lengths, kept by triggers — before promising the reservation, and `commit` re-checks it for staged objects. Both surface as `QuotaExceeded` (`quota_exceeded`, 403) or `StorageFull` (`storage_full`, 507, retryable) through the API. A tenant's own quota (since R01 a `storage_policies` row, which also holds its retention; [retention](retention.md)) overrides the configured default; `admin tenant quota --tenant SLUG [--bytes N | --clear]` and `admin tenant storage` manage it host-locally. Usage now counts stamped log bytes too, and a deployment-wide cap and repository quotas sit beside the tenant's ([retention](retention.md)).

Reclamation is now real but stays reader/lease-safe (migration 27): `manifest_refs` records the object→manifest edge at commit and is backfilled for pre-D06 manifests by `index_refs` (`manifests.refs_indexed` marks the flag's one-way flip, the only manifest update the recreated trigger admits). A tenant with any unindexed manifest is exempt from reclaim — an unseen reference must never be collected under it. `reclaim` deletes an object row only when no edge remains, no unexpired `object_leases` row pins it (`lease`/`release_lease`/`sweep_leases`), no live `Reader` or stage pins it, and it is older than a 24-hour unreferenced grace; the caller hands the returned files to `Objects::unlink`, on the writer, after commit. Migration 34 keeps the candidates in `object_unreferenced` (maintained by triggers: a new object enters, its first reference removes it, its last reference leaving puts it back) with an age index, so a reclaim pass reads candidates oldest first and never walks the objects table; `manifests_unindexed` indexes the per-tenant unindexed-manifest probe. The orphan sweep (`Objects::orphans`) finds files no row owns once their mtime passes a one-hour grace: it walks shard by shard (a tenant's manifests, one object prefix directory, `tmp/`) in name order, stops after a bounded number of directory entries and resumes after that shard next pass, holding one shard's names or one tenant's manifest paths in memory; its finds unlink through `Objects::unlink`. `artifacts.retain_until_ms` (D03) is the artifact retention deadline `sweep_expired` acts on: the row and its manifest version retire in one transaction, cascading the edges that then let `reclaim` collect the objects.

The controller runs the whole pass — expired uploads and leases, artifact retirement, the reference backfill, object reclaim, orphan files, idle log writers, and log retention (stamp, expire, sweep; [retention](retention.md)) — on its own maintenance thread (`sentinel-storage`), at most every `sweep_interval` ([configuration](configuration.md)); placement never waits on it. The row stages take at most 256 rows through indexes; the orphan and log sweeps each examine at most 4,096 directory entries and resume where they stopped. Below the low watermark the dispatcher also stops placing new work and artifact grants answer `TooLarge` — a job that cannot store its output does not consume capacity finding out. `admin objects reclaim` runs the same pass by hand against a stopped server and `admin objects status` reports free space and per-tenant usage.

## Fault boundaries (D07)

Every write path settles one of two ways: bytes durable *and* row committed, or the residue found and swept. `tests/faults.rs` drives the boundaries — a `commit` or `commit_manifest` rolled back after the rename leaves an orphan that `recover` reports and `sweep_orphans` collects past the grace; an upload chunk whose transaction rolled back leaves bytes the resend converges into a verifiable seal; closed admission refuses object bytes while log frames still flow above `floor`; binary frames round-trip byte-identical, oversized frames refuse and the refused sequence becomes a declared gap; the per-attempt log cap refuses with `log size` and the refusal is declared, not silent; a torn segment tail never reaches a tail reader and is cut on reopen; and a lost `end` marker is rebuilt from the sealed segment's end record instead of silently reopening the log. `read_tail` now streams flat logs in bounded chunks instead of loading the whole file.

## Verification

Thirteen integration tests. Runs: spec persisted and read back byte-for-byte, job states seeded from dependencies, cross-tenant read denied, duplicate run creation rejected with the original intact, rerun keeps the fence and stales the old attempt, rerun refused for running and cancelled jobs. Core: migrations idempotent with WAL and foreign keys on; full lifecycle with fence, timestamps and run aggregation; stale fence and wrong tenant rejected; compare-and-set conflict rolls back the whole transaction; dangling and cross-tenant inserts fail; ready-queue ordering and index use; durable cancel flag; acknowledged writes survive drop-without-checkpoint and reopen; writer back-pressure rejects only overflow. Plus two codec round-trip tests. Fleet placement (Q01–Q04) adds `tests/fleet.rs`: unsatisfiable jobs name their arch/label/CPU/memory/disk constraint, the queue listing agrees with `wait_reason`, the fair queue serves the tenant executing least, a waiting large job keeps its reserved path, a waiting pull request keeps a quarter of the host, two identities on one host cannot oversubscribe it, drain stops offers until undrained and is refused for a revoked worker, a warm worker is waited for only inside the bound, and a new run supersedes the live run its concurrency group replaces (a group without `cancel_in_progress` only serializes). The Part 08 audit fixes add regression tests that each failed on the code before them: two queued runs of a serial group both run, in order; a group is held per repository; same-millisecond superseding runs leave exactly one; a large job in another pool, an unrunnable large job and an unrunnable pull-request job reserve nothing; the pull-request reserve counts the host once; neither forty label-mismatched jobs nor forty locality-held jobs hide a placeable one; a repository backlog does not starve its siblings; a busy warm worker with long work does not hold a cold job; a revoked worker holds nothing and its attempts are settled; a passed lease stays expired and a renewed one is not expired. A noisy tenant with demand above capacity still leaves the quiet tenant its share. All pass on Windows and Linux.

Not yet covered: crash injection mid-fsync (requires a fault-injecting VFS), multi-process access (unsupported by design), and checkpoint scheduling under sustained load.
