# Scoped secret records and bindings (S02)

Migration 38 stores tenant-owned secret identities, immutable encrypted versions, repository allowlists, explicit bindings, and an audit trail. Each secret name belongs either to one tenant or one repository. Names use `[A-Z_][A-Z0-9_]*` and at most 64 bytes. A value is 1–65,536 bytes. The current version increases on rotation; a stale expected version fails with a conflict. Deleted names stay reserved and all their versions are revoked. A single historical version can also be revoked permanently. Ciphertext uses [sealed storage](sealed-storage.md), with tenant, optional repository, name, and version in its authenticated context. No plaintext read-back function is exposed to callers.

The existing `WRITE_SECRETS` repository permission is independent of `RUN` and repository operator status. A tenant admin can give a reader or service account that bit for one repository through the normal repository grant. The secret writer can create and rotate repository secrets and bind eligible secrets for that repository. Creating a tenant secret or changing its repository allowlist requires live tenant administration. Every mutation checks that authority in the same writer transaction, including before replaying an idempotent response. Metadata listing and description accept either read or secret-write authority for the relevant scope, so a delegated writer can learn the version needed for a compare-and-set update. HTTP routes also require the `secrets:metadata` or `secrets:write` OAuth scope. No repository grant or super-admin identity gives ambient cross-tenant secret access.

Allowlists, bindings and single-version revocation are reachable through the API and CLI (`sentinel secret allow|deny|allowed|bind|unbind|bindings|revoke-version`, [CLI](cli.md), [API](api.md)); they are idempotent state changes, so a retry needs no idempotency key and a repeated change is not audited twice. A tenant secret must be allowlisted for a repository before it can be bound there. Removing the allowlist removes its bindings in the same transaction, so reallowing needs an explicit new binding. A binding identifies a repository, secret name, source secret ID, and optional job and step IDs. Empty job selects all jobs; empty step selects all steps of the named job. A compiled job still has to declare the name before a value can be delivered. The resolver prefers an exact job and step binding, then a job binding, then the repository-wide binding. A repository secret whose name collides with an allowlisted tenant secret requires an explicit `override_tenant` binding. A tenant binding with an active repository secret of the same name fails as ambiguous. A later secret change can make an old binding ambiguous; resolution checks again rather than silently changing source.

The metadata resolver returns secret ID, source scope, name, and current version, never the sealed value. It refuses missing or revoked versions and inactive tenants or secrets. During preparation, one writer transaction checks the acknowledged attempt's worker, fence and live lease, resolves only declared target names, opens the current active values and writes use audit rows. The transaction serializes delivery against rotation, revocation, binding changes and lease changes. A target the preparation refuses by policy fails the attempt's delivery; the preparation's own writes are rolled back to a savepoint and one `use` audit row with result `missing` (no binding, a revoked current version, an inactive secret) or `denied` (an ambiguous name, a removed allowlist entry) is committed with the attempt, step, name and whatever secret and version were resolved. Audit rows record action, result, actor when applicable, tenant, repository, secret/version IDs (the name only for a refusal with no secret), attempt and step when applicable, and time. They contain no value or value-derived digest, and the table is append-only (update and delete triggers refuse; retention is R01's).

The `secrets`, `secret_versions`, `secret_repo_allow`, `secret_bindings`, `secret_audit`, and bounded `secret_idempotency` tables live in SQLite. Backup the database and master key as a matching pair. Sealed historical versions remain available for audit until explicitly revoked or deleted. Every new attempt, including a rerun, receives the current active version at its preparation transaction; an old version is never selected just because an earlier attempt used it. A secret's repository allowlist is an authorization boundary, not an injection instruction.

## CLI and HTTP writes (S03–S04)

`sentinel secret set`, `rotate`, `list`, `describe`, `delete` and `import` use the API. Set values come from hidden terminal input, redirected stdin, or a protected regular file, never an argument; a stray argument is refused without being repeated. The API accepts raw value bytes up to 65,536 and seals them inside the same SQLite writer transaction as the version and audit row. Compare-and-set uses `If-Match`; the required idempotency key saves only a metadata response and a request fingerprint in a bounded table. The fingerprint is a keyed BLAKE3 MAC under a subkey derived from the master key, so a database copy cannot confirm a guessed value; after a key rotation, a retry record from before it no longer matches. Reusing a key for a different request is `idempotency_mismatch`. Authorization is checked again before a retry may replay a response. When a write's outcome is unknown, the CLI names the idempotency key and version that replay it. Source files must be regular nonsymlinks with owner-only access: Unix mode and ownership is checked; on Windows the owner must be the current user or SYSTEM and the DACL may grant only them.

`secret import --env-file` parses UTF-8 `NAME=value` records literally. It skips a leading UTF-8 byte-order mark and accepts LF or CRLF line ends, blank lines and `#` comment lines; a carriage return anywhere else is refused, and quotes, escapes and variable expansion are not interpreted (`A="x"` stores the quotes). The 1 MiB file limit, 100-entry limit, name/value bounds, duplicate checks and complete expected-version map are validated before writes; errors name the line. All entries seal and audit in one writer transaction, so any conflict rolls back the import. Preview lists names, expected versions, deleted names and quote/whitespace warnings, and prints an `--if-versions` pin that makes the real import refuse if anything moved. The CLI and API never echo imported values; secret values are not included in argv, diagnostics or response output.

## Execution binding and cleanup (S05–S06)

Jobs declare names in `secrets`. A step can consume a name as an environment variable with `steps[].secrets` or as a file with `steps[].secret_files`; a job can select one declared name for host-only registry authentication with `registry_auth`. Example:

```yaml
jobs:
  test:
    image: ghcr.io/acme/ci@sha256:...
    secrets: [TOKEN, CLIENT_CERT, OCI_AUTH]
    registry_auth: OCI_AUTH
    steps:
      - id: unit
        run: ./test.sh
        secrets: [TOKEN]
        secret_files:
          CLIENT_CERT: tls/client.pem
```

The worker runs only jobs requiring this contract when it negotiates protocol 10 and advertises `SECRET_DELIVERY`. The controller sends the bounded bundle after the durable offer acknowledgement, bound to that attempt and fence. The store records selected version IDs and the job/step use in the same transaction that opens the sealed values. Each value is at most 64 KiB and the whole bundle is at most 1 MiB. The worker checks that the received target set exactly matches the stored run spec, rejects invalid env values and unsafe file paths, and registers every value with the attempt redactor before opening the log pipe. A declared name that cannot be delivered — revoked, deleted, unbound or ambiguous — fails the attempt as `Preparation` with the detail `secret NAME: reason` (never the value), and the refused use is audited exactly once, by the delivery that refused it: one `use` row with the attempt, step, name and whatever secret and version were resolved, result `denied` when a binding exists but policy refuses it (ambiguity, a removed allowlist entry) and `missing` when there is no binding or its secret or current version is gone (P10S-6, P10D-7). A re-asked spec after a lost session still receives its bundle (P10D-3).

Secrets are **step-scoped**, and that holds because of process clearing, not just file timing (P10D-1). All steps of a job run in one container, as one user, in one PID namespace, so a process an earlier step left running (a daemonized post-install hook, a `setsid` watcher) could otherwise read a later step's environment through `/proc/<pid>/environ` or its files. Before the worker materializes a step's secrets it freezes the container's cgroup, kills every process in it except the keepalive and waits until none is left; it does the same when that step ends, before its files are removed. A container whose cgroup is not visible, or that cannot be emptied within 5 s, gets no secret: the step fails as `Runtime`. Measured with rootless Podman 4.9.3 on WSL2 (debug build): clearing a container holding three strays and the keepalive's `sleep` took 2.3 ms (4 of 5 runs; one 15 ms). Consequences: a background service an earlier step started does not survive into a secret-bearing step, and one a secret-bearing step starts does not survive it; steps without secrets are untouched. What a step writes to the workspace, `/tmp` or a cache view is not cleared — a secret-bearing step runs workspace content earlier steps produced, which is within the secret's trust policy.

Secrets are staged under the worker's runtime directory, `$XDG_RUNTIME_DIR/sentinel-<key>/secret-delivery/<attempt>`, a tmpfs on systemd hosts, when `XDG_RUNTIME_DIR` is an owner-only directory of the worker account; otherwise under `<data_dir>/run/`, which is persistent disk where the overwrite before removal is not an erasure. The attempt directory is owner-only on the host. File targets appear read-only at `/run/sentinel-secrets/<relative-path>`; directories below the attempt directory are 0755 and files 0644, so an image that runs as a non-root user (node, distroless `nonroot`) can read them (P10D-4) — the mount is private to that attempt's container and read-only. Environment targets are written as `export NAME='value'` lines to a file mounted read-only at `/run/sentinel-env`, and the step's argv is wrapped as `/bin/sh -c '. /run/sentinel-env/step-N.sh && exec "$@"'` (P10D-8). The values never pass through Podman — its `--env-file` reader refused lines over 64 KiB, and Podman 4.9.3 writes an exec session's environment in plaintext into `overlay-containers/<id>/userdata/` under its graph root for the step's duration — and never appear in any argv. Any value up to the 64 KiB bound works. The worker materializes only a step's targets immediately before that step, then zeroes and removes them. Secret target paths may not overlap or conflict with step environment names. Default artifact and cache collection only sees the workspace and declared cache views; the secret mounts are outside both. The worker removes the attempt directory on every terminal path, and startup recovery reaps secret directories left by a process crash in both the runtime directory and the data directory. Job containers run with a hard core-dump limit of 0, and the controller and worker processes with `RLIMIT_CORE` 0 and not dumpable (P10D-9); wiping of secret memory is best effort beyond the buffers Sentinel owns ([protocol](protocol.md#protocol-10-secret-delivery)).

Private registry auth is an OCI auth JSON object containing only an `auths` map. It is written to an owner-only host file for the image pull, removed immediately afterward and never passed into the job container. Every attempt explicitly runs `podman pull` with that attempt's auth file, even if the digest is present locally, so a resident manifest cannot authorize a revoked credential. The runtime checks authorization **per manifest, not per layer**: a layer already in the store it pulls into is reused without being fetched, so a tenant replaying another tenant's manifest and config from a registry of its own would receive that tenant's private layers from a shared store (P10D-5, reproduced with Podman 4.9.3). An image pulled with `registry_auth` therefore goes to that tenant's **private store** (`<data_dir>/image-stores/<tenant>/graph`, run root a short owner-only directory in the runtime directory or `/tmp`), and its container runs there too; the shared store only ever receives anonymously pulled — public — layers. Repositories of one tenant share its private store. The cost is paid only by private images: the first pull of one per tenant per worker downloads every layer, including public base layers the shared store already holds, and those layers take disk once per tenant; later attempts of the tenant reuse its store as before. Sentinel garbage-collects neither store; operators prune them (`podman --root … image prune`). An image a tenant pulls without `registry_auth` — including from a registry that authorizes by network location — is treated as public. Pulls suppress ambient auth-file overrides and external credential-helper executables; use `registry_auth` rather than a worker-wide Podman login for private images. Prefetch is anonymous and does not grant access: the attempt performs its own authorized pull before using the image.

Redaction runs before spool persistence and controller delivery. It handles a secret split across log frames by holding a bounded stream tail. Because the controller's failure parser decodes structured output ([diagnostics](diagnostics.md)), registration also covers every standard JSON escaping of a value (with and without the `\b`/`\f` short forms and Go's HTML-safe `\u003c`, `\u003e`, `\u0026`, `\u2028`, `\u2029`), and every line of a multi-line value that holds anything but ASCII punctuation and whitespace, whatever its length, raw and escaped, since line-oriented producers such as `go test -json` write one record per line. The Go parser never joins an output event that ended mid-line to the next one. Together these keep a parsed diagnostic from containing a value the stored log did not hold contiguously. Only a line made entirely of punctuation and whitespace (`{`, `}`, `-----`, a blank line) stays visible when printed on its own: it is format structure, and registering it would erase that character from every later line of the attempt's output. A short line such as a password or a PEM's last base64 line is redacted (and, like any short value, can make redaction noisy). It cannot hide transformations of a secret (for example, a program that prints a hash or a substring), so jobs should still avoid deriving and printing secret material.

## Verification (S07)

`sentinel-store/tests/secret_delivery.rs` checks acknowledgement/fence gating, declared target resolution, selected-version audit, current-version selection after rerun, and refusal of a revoked version. The Linux rootless `sentinel-worker/tests/end_to_end.rs` runs a real protocol-10 secret job: its bound `TOKEN` reaches the declared step environment, and the controller receives its output redacted. The separate `inspect`-job redaction fixture registers a synthetic value before each attempt. `sentinel/tests/oauth_e2e.rs::a_delegated_cli_writer_can_provision_a_secret_for_a_job_without_disclosure` extends the delivery path from the authorized CLI writer: the CLI-created value is bound to a job step with `sentinel secret bind` (no store call in the provisioning flow), consumed through both environment and file targets, redacted from controller logs, absent from sealed ciphertext and audit metadata as plaintext, and removed from worker scratch after completion. An artifact declaration using the same relative path as the secret file resolves absent, and a scan of worker cache/scratch files finds no plaintext.

Import idempotency and competing version writes are covered by API tests, including synchronized concurrent retries with one idempotent result and two different imports racing on the same expected versions. Image tests verify that tenant or credential changes do not share an in-flight authorized pull. `sentinel-worker/tests/secret_isolation.rs` (rootless Podman, a local `registry:2` with htpasswd authentication, and a manifest-replaying server) checks that a private image pulled with credentials lands only in the tenant's store, that once resident there an anonymous pull is still refused, and that another tenant replaying its manifest and config gets no layer; through the executor, that a `setsid` watcher started by an earlier step records nothing of a later step's environment or files (it records the token when clearing is disabled), that a 65,000-byte environment value and a hard core limit of 0 reach the step, that a non-root image reads its file target, and that an unbound secret fails with `secret NAME: unbound`. The older `tests/podman.rs` resident-image check pulls a public image and cannot fail on an authorization bypass; the registry test is the evidence. A session unit test covers a secret transfer answered on a new session after the acknowledging one was lost, and store tests cover placement below protocol 10 and the refusal detail and audit. Sealed-key tests rotate, restore the matching key backup and reject values sealed after that backup. These checks run on the full Windows CLI/API suite and the Linux server/worker suite; rootless execution uses `SENTINEL_PODMAN_TESTS=1` as the worker account.
