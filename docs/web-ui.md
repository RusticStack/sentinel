# Web interface

The human web interface is its own process, `sentinel-web`: a TanStack Start server (React 19, TypeScript, Tailwind CSS v4) in [`web/`](../web), run by Node with server-side rendering, never a static build. It renders every page on the server as the signed-in person, streams live run and log updates to the browser, and proxies the controller's own routes so the browser sees one origin. The controller remains the only authority: `sentinel-web` holds no credential, stores nothing and forwards each browser's own session cookie; every read and every action is authorized by the controller's API exactly as for the CLI and MCP ([API](api.md)).

The web interface is optional: the controller, CLI and MCP work without it.

It replaced the Nuxt 4 interface in Part 20 ([plan 16.4](../plan.md#164-web-interface-on-tanstack-start)) view by view, each move checked by the browser test below; [how it is built](#how-it-is-built) says what changed underneath, and [`bench/u14-web-start.jsonl`](../bench/u14-web-start.jsonl) measures it against the Nuxt baseline [`bench/u08-web-baseline.jsonl`](../bench/u08-web-baseline.jsonl).

## Architecture

```
browser ──https──▶ reverse proxy ──▶ sentinel-web (Node, :3000) ──▶ sentinel server api_listen (:7080)
                                     ├─ pages: server-rendered React, then hydrated
                                     ├─ /_stream/run/<id>, /_stream/log/<attempt>: server-sent events
                                     └─ /api/v1/**, /oauth/**, /auth/github/**, /.well-known/**, /device, /mcp: proxied unchanged
```

- **One origin.** The server entry (`src/server.ts`, with `src/server/proxy.ts`) passes the controller's routes through with their cookies, redirects and bodies. Request bodies are streamed, never buffered, under a hard ceiling that matches the controller's own (1 MiB for the API, 8 MiB for an upload chunk, 4 MiB for the GitHub webhook, 2 MiB for MCP): a larger declared length is refused with 413 before anything is relayed, and a body that grows past it, or an upload the browser aborts, fails the request (413 or 502) instead of reaching the controller as a shorter body. A path is allowlisted exactly as it will be sent: backslashes, encoded dots, slashes or percent signs, control characters and `.`/`..`/empty segments that could reach a controller route are refused with 400 rather than normalized. The proxy replaces `X-Forwarded-For` with one address (below); a client's own header is dropped. See [client addresses](#client-addresses). The controller's `public_url` is the origin browsers use — the web interface's — because sign-in checks `Origin` against it, and GitHub check links (`{public_url}/runs/<id>`) point at it.
- **Server rendering.** The first request for a page runs on the server with the browser's cookie (the API helper `src/lib/api.ts` reads the controller directly from a server-only module during the render): a signed-out visitor is sent to `/login?next=…` before anything is drawn, and a signed-in one receives the page with its data. The browser then hydrates and navigates client-side. The server and the first browser render are identical (the browser test asserts no hydration mismatch): times render as UTC clock time until mounted, and a page's render clock travels in its payload.
- **Live updates.** A page that shows something still changing opens one `EventSource` to `sentinel-web`, which holds the controller's long poll on the browser's behalf and pushes each change:
  - `/_stream/run/<run>`: `run` (the whole run document, on every version change), `status` (`live`, `busy`, `reconnecting`), `refused` (the controller's error — the session ended or access was removed; the page says so and the tenant list is re-read), `finished`.
  - `/_stream/log/<attempt>?step&after`: `frames` (a page of frames, with `id: step:seq`), `step_done`, `complete` (with the log's gaps), `status`, `refused`. The browser reconnects by itself with `Last-Event-ID`, and the server resumes after exactly that frame: a dropped connection never repeats or loses a line.
  - A controller that is unreachable or answers 5xx is retried with capped exponential back-off and jitter. A busy one (`rate_limited`, its subscriber share full) is retried at the `retry_after_ms` it states (jittered, never grown), and the notice ends as soon as a retry is parked, one second after the request went out unrefused, not when the park (up to 25 s) returns. The page shows "Updates paused" or "Reconnecting", never an error.
- **Controller side.** A parked long poll gives its handler permit back while it waits (waiting is not work), re-authorizes whenever the tenant's authorization epoch moves (a removed member's open page is refused within a quarter second), and ends as soon as its client hangs up, returning its slot. So live views are bounded by the subscriber budget (`sentinel_api::SUBSCRIBERS`, 32 parked at once, 8 per user), not by the 8 handler permits, and clicking between live pages never exhausts a person's share ([API](api.md#live-updates-and-long-polls)).

Actions go through one helper (`act` in `src/lib/act.tsx`): a toast for the outcome; on `not_found`/`forbidden` a re-read of the caller's tenants, so the navigation follows a role or membership change made while the page was open. Confirmations guard removals, suspensions, revocations and deletions.

**Step-up.** Any request refused with `forbidden` and `details.step_up` — issuing service credentials and creating or widening service accounts (for everyone), a platform administrator's change in a tenant they do not administer (members, repository access), suspension, recovery-code reissue, GitHub linking, a password change with a factor — opens the "Confirm it's you" dialog (`StepUpDialog`, which `act` and the account page share), then retries the action once; closing the dialog drops it silently. The dialog offers the authenticator code (`autocomplete="one-time-code"`, numeric keypad) or a recovery code for an account with TOTP, the password (`current-password`) for one without; a GitHub-only account with neither is told to set up an authenticator, with a link to `/account`. It focuses the field, announces refusals (`role="alert"`), says that five wrong proofs end the session and ten wrong codes lock the authenticator for 15 minutes, counts down a `rate_limited` answer's `retry_after_ms` with Confirm disabled, and, when a refusal ended the session (`401`), closes and leaves the page to the sign-in redirect below. The proof is cleared from the field after every try. A platform administrator acting in a tenant they do not administer also gets a "Reason" field above the members, repositories and service-accounts sections (`src/lib/override.ts`); it is sent as `reason` with those changes, as the controller requires (audited `platform-override`), and a change is not sent while it is empty.

**Session ended.** In the browser, a `401` on any request while someone is signed in — a page refresh, a poll, an action, the step-up itself — means the session ended under the open page (deadline, revocation, five wrong proofs, a password change elsewhere). The API helper then forgets the person once, however many requests were refused together, and goes to `/login?reason=expired&next=<page>`, which says so and continues to the page after sign-in (`next` is checked by `sameOriginPath`). A refused live stream does the same.

**Shown once.** Recovery codes and a service credential's refresh token appear in a dialog (`ShowOnceDialog`) that cannot be dismissed by Escape or a click outside; it offers Copy and Download (a `.txt` built in the page) and closes only after "I have saved this somewhere safe" is ticked, then drops the values. The authenticator's `otpauth://` URI lives in the account page's memory until the code is confirmed or the setup is cancelled; its QR code is drawn in the page (`src/lib/qr.ts`, byte mode, level M, as one SVG path — no library, no service sees the seed). None of these, nor any password, is put in storage, a URL, a toast or the log, and each is cleared when it has served or the page is left. The same holds for the setup token, the wizard's passwords, and the verification and invitation secrets (the one exception is the invitation's ten-minute `sessionStorage` hand-over across a sign-in round trip, above). An invitation link made when the deployment sends no mail is shown in the same shown-once dialog.

**Namespace switcher.** The sidebar's switcher ("Active namespace") groups the person's namespaces from `GET /tenants` (`kind`, `membership`): **Personal**, **Organizations** (managed in Sentinel) and **GitHub organizations** (a GitHub icon and "GitHub-managed" beside the role), so nobody looks for an invite button on an organization whose members GitHub decides. Only namespaces the person belongs to are listed; a guessed slug is the controller's uniform `not_found`. Every namespace has a **Settings** entry, and "Organizations" (`/organizations`) is in the navigation for everyone.

### First-run setup

`/setup` is the browser alternative to `sentinel admin bootstrap` ([admission](admission.md#first-run-setup)). The route middleware reads `GET /setup` on `/login` and `/setup`: while open, a signed-out `/login` goes to the wizard; once closed (remembered for the page's life, since it never reopens) `/setup` redirects away. Steps, each with its heading focused as it opens and a step list (`aria-current="step"`):

1. **Setup token** — where to read it (the `setup-token` file in the data directory, or the `setup_required` log line), its one-hour life and the five-minute lock after wrong tries; a password-type field.
2. **Administrator** — email, optional name, password and repetition (`autocomplete` `email`, a hidden `username`, `new-password`) with guidance: a four-step meter and one hint, judged in the page against the controller's bounds (12–256 bytes, not only spacing) and penalising common words, repetition and the address or instance name (`src/lib/onboarding.ts`, `passwordAdvice`).
3. **Who can join** — the registration policy (`invite-only`, recommended; `approval-required`; `closed`) and who can create organizations (`super-admin-only`, `approved-users`), each explained in a sentence.
4. **Instance** — name (up to 64 characters) and the address people use (pre-filled with the page's origin; an absolute http(s) URL, no credentials, query or fragment).
5. **Email** (optional) — whether the controller delivers mail through Resend, read from `GET /setup` (`mail_configured`) each time the step opens. When it does (or the answer is unknown), a "Send test to" address (the administrator's by default) and "Send test message", which sends `POST /setup/mail-test {token, to}` and nothing else. The answer is "sent", or the failure kind in words (`not_configured`: no key and sender yet; `invalid_settings`: the address cannot receive it; `transient`: Resend unreachable or asking to wait; `permanent`: Resend refused, check the key and the sender's verified domain) followed by the short reason ("Resend said:" for the last two, "The controller said:" for the first two, which never reach Resend). If `GET /setup` says setup closed meanwhile, the wizard says so as on finishing. A busy test (`429`) counts down on the button, a refused setup token returns to step 1, an origin refusal says how to fix the address; none of these, nor a failed test, blocks finishing. When mail is not configured (or the test answers `not_configured`) the page says so and shows the two lines for the controller's environment, `SENTINEL_RESEND_API_KEY_FILE=/etc/sentinel/resend-key` and `SENTINEL_EMAIL_FROM=Sentinel <sentinel@example.com>`, each with its own copy button (labelled with the variable name; no trailing comment), and explains that the key goes in that owner-only file, never in a variable or in the page, and that until then verification and invitation links are printed by `sentinel admin`. Nothing typed here is stored, and the step asks for no key or password. The review shows whether email is configured and whether a test was sent.
6. **Namespaces** (optional) — a personal namespace and a first organization, checked against the organization name rules.
7. **Review** — every answer with a "Change" link back to its step; "Finish setup" sends one `POST /setup`. A refused token returns to step 1 with the reasons it can be refused; `404` (completed elsewhere meanwhile) says so and leads to sign-in; `409` (address or name taken) and `400` say which answers to look at; `429` counts down.

After the one commit the administrator is signed in (the CSRF secret stored as at sign-in) and the wizard offers an authenticator (the same enrollment component as the account page, with the password just typed sent once) or "Skip for now", then a next-steps screen (invite people to the first organization, workers and pools, the policy, an authenticator). **Resuming:** the non-secret answers and the step are kept in this tab's `sessionStorage` (`serializeDraft` writes an allowlist of fields, `parseDraft` checks each one back); the setup token, the passwords never are. A refresh opens on the token step with "picking up where you left off", then asks for the password, then returns to the step the person was on. The draft is deleted when setup completes or is found completed.

### Sign-up and email links

The emailed links are `/verify-email#token=…` and `/invitations/accept#token=sntl_…`, the secret in the fragment so it reaches no server. Both pages render a neutral "Reading the link…" on the server, then in the browser take exactly one well-formed token from the fragment (`fragmentToken`), replace the history entry without it, and keep it in memory. Verification spends it only when "Confirm my address" is pressed, so a mail scanner that opens links does not use it up. Every reply that could tell whether an address has an account reads the same: sign-up, the resend form and an address change all say "if the address can be used here, a link is on its way", and a deployment without mail says to ask the administrator for the link (`verification: "operator"`). A pending account (approval-required) is told an administrator approves it first. The account page adds or changes the address (a claim until its link is opened; replacing a confirmed one may ask for step-up) and resends a pending link.

### Invitations

`/invitations/accept` shows nothing about an invitation before the controller accepts it — there is no route that reveals one without spending it — so the organization is named only on `joined`. Signed out, the page offers "I have an account" (the sign-in form, then Accept) and "I'm new here" (sign-up carrying the invitation; the join happens when the address is confirmed); the secret stays in the page's memory. Only a round trip that leaves the page (GitHub sign-in, "Not me — sign out") parks it in this tab's `sessionStorage` for at most ten minutes: the accept page removes it on every visit, whether it uses it or the link's own fragment wins, and any full page load in the tab drops it once past its ten minutes. The controller ends GitHub sign-in (and GitHub linking from the account page) on `/` with a full page load, so where the person was going is kept in a `sentinel-return` cookie (`SameSite=Lax`, ten minutes, a same-origin path only, never a secret) rather than in browser storage: the server-side render of `/` reads it and continues there before it would open the first tenant, and it is cleared once it has served. The refusals the API folds into one `not_found` (expired, used, revoked, addressed to another mailbox, GitHub-managed organization) are one message listing those possibilities.

## The log viewer

`src/lib/logviewer.ts` is plain DOM, deliberately outside React's state: up to a quarter-million held lines, their typed per-line columns (sequence, stream, line number — no object per line), the memory bound and the stream state are ordinary data, never proxied.

- **Steps fold.** Each step is a section loaded on demand through `?step=` pages; passed, skipped and not-run steps start folded, failed and unfinished ones open. The step list and each section header toggle with `aria-expanded`.
- **Windowed rendering.** A fixed-height viewport over a spacer as tall as every row; only the rows in view plus 12 above and below exist, pooled and reused — a row that scrolls in only changes its text, link and class. Arrow keys, Page Up/Down, Home and End scroll; `End` follows.
- **Bounded memory.** At most 250,000 lines and 48 M characters are held; past that the oldest lines of the largest step are released in blocks of 25,000, the view stays on the lines being read, and the step's first row says how many were released, with "load earlier" to fetch them again. A line longer than 4,096 characters is shown cut, with the rest counted.
- **Nothing hidden.** A gap the store declared is a marker line where it falls ("frame N was never stored"); a completed log with gaps says so; ANSI colour codes are dropped.
- **Search** is the controller's indexed literal search (`/logs/search`, 4 MiB of log a request), continued until something is found; each hit jumps to its exact line, highlighted, with the term marked.
- **Deep links.** Every line number links to `…/logs/<attempt>?step=S&seq=N` (and `&q=` from a search); opening one loads a window around the frame and highlights the line.
- **Live.** A running attempt is followed through the log stream, step by step, and resumes exactly after a lost connection. The stream (`/_stream/log/<attempt>`) emits `frames` (frames and gaps), `step_done` (step), `complete` (gaps), `status` (`busy`, `reconnecting` or `live`) and `refused`, and each event's id is `step:seq` so `Last-Event-ID` resumes exactly. The run stream (`/_stream/run/<id>`) emits `run`, `status`, `refused` and `finished`, and sends a bare `:` keepalive while the run's version is unchanged. The browser code depends on these names and payload shapes, so renaming one breaks it.

## Security

- The browser holds only the controller's `__Host-sentinel_session` cookie (`Secure`, `HttpOnly`, `SameSite=Strict`) and the session's CSRF secret, kept in `localStorage` (handed over by the login response or the GitHub finish page) and sent as `x-sentinel-csrf` on mutations; server-side rendering only reads.
- `sentinel-web` validates identifiers before they go into an upstream URL, forwards the caller's credentials unchanged and never logs them; it has no credential of its own, so it can do nothing the browser's session cannot. The proxy allowlist (`classifyProxyPath`) judges the path exactly as it will be sent upstream and never inspects the query string, where percent-encoding is normal; a target that could mean one thing here and another at the controller (encoded dots, slashes or backslashes, NUL, control characters) is refused rather than forwarded, so it cannot open path-confusion access to controller routes. Fields an older controller may omit (`Me.email`, `Me.email_verified`, `TenantChoice.kind` and `membership`, `Member.source` and `synced_ms`) are typed optional in `web/src/lib/types.ts`; making one required would break the interface against that controller. This controller always emits every one of them: `GET /me` writes `email` (null without an address) and a boolean `email_verified`, `GET /tenants` (and the namespace settings) write `kind` and `membership` on every entry, and `GET /tenants/{slug}/members` writes `source` (`app` or `github`) and `synced_ms` (a number exactly when the source is `github`, otherwise null) on every row; `the_serializers_always_emit_the_fields_the_web_types_mark_optional` in `crates/sentinel-api/tests/api.rs` fails if one goes missing.

**Supported skew.** `sentinel-web` is released with the controller and supports a controller of its own release and the release before it; it is not promised against anything older or newer. Within that window the web interface treats a missing optional field as absent (an address not shown, a namespace shown as app-managed and an organization, a member as app-sourced) and never as an error. A field leaves the optional list only when every controller in the supported window emits it, and the types change in the same release that drops the older controller from the window. An additive controller field never needs a web release; a removed or renamed one is a contract change and needs an entry in [compatibility](compatibility.md).
- Pages carry `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` that turns off the sensors, camera, microphone, payment and USB, and a `Content-Security-Policy` (`src/server/csp.ts`): same-origin for everything, no objects, `base-uri 'none'`, `frame-ancestors 'none'`, and scripts and style elements only from the origin or by the SHA-256 of each inline block rendered into that response (no `unsafe-inline`, no nonce); only style attributes, such as bar widths and the log viewer's row offsets, may be inline. Pages are rendered whole rather than streamed so that every inline script, including the router's dehydrated state, is known before the header is written. Nothing creates a style element at run time: icons are inline `<svg>` (`src/components/icons.ts`), the colour theme is a `sentinel-theme` cookie the server renders as a class on `<html>` (no inline script reads storage first), and the dialogs, select and menu are native elements and small in-house widgets with no runtime styles. The browser test's "no script errors" checks fail on any violation, so a dependency update that adds a runtime style element or an `eval` shows up there. The account, step-up, setup, sign-up, email-link, invitation, organization and settings views add no inline script or style (the QR code is an SVG path with presentation attributes; the password meter is classes, not style attributes; a download is a `blob:` link made and revoked in the page). The policy is not set by `vite dev`, whose hot reload needs inline code; the controller's own pages keep their policy. The post-sign-in `next` destination must be a path on this origin (`src/lib/redirect.ts`); `//host`, backslash and absolute URLs fall back to `/`. The request target is judged as the client sent it (Node's raw target, not a URL the parser has already resolved).
- Build assets are content-named and served `immutable`, gzip or brotli precompressed.
- The OAuth consent and device pages and GitHub sign-in stay the controller's own server-rendered pages, under their strict policy, reached through the proxy.

## Running it

Build once per release (Node 22+ and pnpm, at build time and run time):

```sh
pnpm -C web install --frozen-lockfile
pnpm -C web build            # writes web/.output (server + public assets)
```

Run it next to `sentinel server`, on loopback behind the reverse proxy:

```sh
SENTINEL_API=http://127.0.0.1:7080 HOST=127.0.0.1 PORT=3000 node web/.output/server/index.mjs
```

| Setting | Meaning |
|---|---|
| `SENTINEL_API` | the controller's `api_listen`, reached from this process (default `http://127.0.0.1:7080`); the Nuxt release's `NUXT_SENTINEL_API` is still read when it is unset, for one release |
| `SENTINEL_CLIENT_IP_HEADER` | (or, for one release, `NUXT_CLIENT_IP_HEADER`) the header the reverse proxy sets to the real client address (`x-forwarded-for`, `x-real-ip`); empty by default, which trusts no header and, behind a proxy on a private or loopback address, names no client (see below) |
| `SENTINEL_GITHUB_WEB_URL` | GitHub Enterprise Server only: its web address, which the GitHub App setup page may post the manifest to (default `https://github.com`) |
| `HOST`, `PORT` | where `sentinel-web` listens (default `0.0.0.0:3000`; bind loopback behind a proxy) |

### Client addresses

Three hops each see a different peer: the browser reaches the reverse proxy, the reverse proxy reaches `sentinel-web`, and `sentinel-web` reaches the controller from loopback. The controller rate-limits unauthenticated requests per client and, for a peer in its `trusted_proxies` (loopback by default, which `sentinel-web` is), keys on the last address of `X-Forwarded-For` ([configuration](configuration.md)). So `sentinel-web` must send the real client there, as the only entry:

- **Default (`SENTINEL_CLIENT_IP_HEADER` empty):** no header is read, so no client can choose its bucket. A socket peer that is a remote address is the client itself and is named to the controller. A peer that is loopback, private, link-local or unique-local is a reverse proxy's hop: `sentinel-web` names nobody, and the controller keys on the upstream connection ([API](api.md#client-keys-behind-a-reverse-proxy)), which is finer than one allowance for everybody but weaker than a real client address, so set the header for real per-client limits.
- **Behind a proxy you control:** set `SENTINEL_CLIENT_IP_HEADER` to the header that proxy sets, with the proxy overwriting or appending to it so its own entry is last (`x-forwarded-for`, or a single-valued `x-real-ip`). Only the last entry is used, and only when it is a valid address; otherwise a remote peer is used, and an internal one names nobody. Bind `sentinel-web` to loopback or a private interface that only the proxy reaches, because a client that reached it directly could set the header itself.
- A client's own `X-Forwarded-For`, `X-Real-IP`, `Forwarded` and `X-Forwarded-Host/Proto` never reach the controller.

The reverse proxy terminates TLS and sends everything for the public origin to `sentinel-web`; the controller's `public_url` is that origin ([configuration](configuration.md)). [`examples/sentinel-web.service`](../examples/sentinel-web.service) is a systemd unit, ordered after the controller's [`sentinel-server.service`](../examples/sentinel-server.service) ([deployment](deployment.md#the-controller-as-a-systemd-service)). Verified nginx and Caddy configurations for this layout, with `trusted_proxies`, are in [deployment](deployment.md#tls-and-a-reverse-proxy).

## Stack choice

`web/bench/log-view.mjs` renders the same 200,000-line log (127-character lines in 32 KiB frames) four ways in a real browser, three fresh pages each, and records medians in [`bench/u01-log-view.jsonl`](../bench/u01-log-view.jsonl) (Edge 154, i7-13700KF):

| Candidate | Shipped JS (gzip) | Ingest + first paint | Elements | Work per scroll jump |
|---|---|---|---|---|
| One element per line | — | 2,118 ms | 200,012 | frames dropped (39.5 ms/jump wall) |
| Preact 10 + htm, windowed | 7.1 KB | 52 ms | 157 | 1.17 ms |
| Vue 3, windowed | 61.4 KB (whole runtime) | 43 ms | 155 | 0.98 ms |
| Shipped viewer (`logviewer.ts`), windowed | 6.7 KB | 56 ms | 181 | 1.11 ms |

Windowing is what matters: one element per line costs 200,000 elements and seconds per load. The windowed renderings are far under a frame's 16.7 ms, so the stack was chosen on what else it gives (at first Nuxt UI's accessible components, server rendering and typed code; since Part 20 TanStack Start and React, chosen for weight and measured in U14), and the viewer stays plain DOM to keep its state outside the framework's, not for speed. The record keeps no spread, so small differences between the windowed candidates cannot be called signal or noise.

The file's second record is the verification VPS (headless Chrome 154, AMD EPYC 9645, 12 vCPU): one element per line 3,012 ms to load; Preact 1.96, Vue 1.92 and the shipped viewer 2.43 ms of work per jump, every windowed candidate at the same 33.3 ms wall per jump.


`measure_the_web_interface` in the same file runs `web/bench/web-bench.mjs` against the same seed: shipped JavaScript per first view (gzip), server render time per view, resident memory idle and after the views, CPU for ten live log streams over 30 s and log-view work per scroll jump; `SENTINEL_BENCH_RECORD=<file>` appends the record and `SENTINEL_BENCH_HOST_LABEL` names the host. `SENTINEL_WEB_SERVER` points the harness at another build of the interface.

The assertions are in `web/test/ui.mjs`:

- **Structure and keyboard:** every control has an accessible name, one main landmark and navigation, one level-one heading per view; the first tab stop is "Skip to content" and it moves focus to the content; client-side navigation moves focus to the new heading; every tab stop on the run page shows a focus ring; cancel, rerun and log controls are reachable; the log viewer scrolls by line, page and end with the keyboard and steps fold from it.
- **Contrast:** every visible text element meets WCAG AA (4.5:1, 3:1 for large text) in both colour schemes on every view.
- **Layouts:** no horizontal page scroll at 360, 768 and 1280 px on every view.
- **Behaviour:** sign-in (refusal announced, continuing to the page asked for), run filters through the form and by deep link, the failed job's summary and evidence link, cache outcomes, the gap marker, folds, search jump and deep link, server rendering identical to the browser's.
- **Large log:** the 64 MiB, 524,289-line log is read to its end with a bounded number of row elements, the oldest lines released and said, and bounded heap; search finds the one line at the end.
- **Live and failures:** the running job's lines stream in; the relay cut is said ("Connection lost"), and after it the lines resume consecutive, nothing lost or repeated; with the user's subscriber share held, the run page says "Updates paused", then turns live again and shows a change; hopping between live pages never exhausts the share.
- **Role changes during open sessions:** an operator lowered to reader has an action refused and said, and the navigation follows; removed from the tenant, their open run page says "You no longer have access" within 5 s and the tenant leaves the navigation.
- **Administration:** suspending a tenant asks for a second factor, then suspends; reactivating inside the window does not ask again; a member's role changes from the members table.
- **Account security:** `/account` and the service-accounts section join the structure, contrast and layout checks; at phone width (390 px) a member enrolls an authenticator (QR code and key shown, the confirm field asks for one-time-code autofill, a wrong code refused and said with the setup still open, then the code computed from the key), sees ten recovery codes in a dialog whose Done stays disabled until "saved" is ticked and whose codes are gone from the page afterwards, sees "10 of 10 left", has a wrong current password refused and said without losing the session, and changes the password, landing on sign-in with "Password changed". `web/test/qr.test.mjs` checks the QR encoder against the standard's Reed-Solomon and format-information values and the symbol's fixed patterns, and the key extraction.
- **Onboarding:** the public pages (sign-up, verification, forgot-password, invitation) join the structure checks signed out, with contrast in both schemes and no horizontal scroll at 360 px; `/organizations`, `/t/acme/settings` and `/t/acme/admin/invitations` join the signed-in structure, contrast and layout checks. With setup closed `/setup` lands on sign-in; sign-up under the seed's invitation-only policy is refused with the reason and empties the password fields; a forged verification link leaves the address bar before anything is sent, is refused, and the resend form answers alike for an unknown address; the tenant list carries kind and membership; an organization name of the wrong shape is refused in the page, a good one is created and opens on its settings (managed in Sentinel, the domain rule read-only), and the switcher groups it; an email invitation without mail delivery shows its one-time accept link once, is listed pending without a secret and is revoked; a forged invitation link leaves the address bar and is refused without naming an organization. `web/test/onboarding.test.mjs` checks the fragment-token reader, password guidance at the byte bounds, organization names, base URLs, that the stored wizard draft never holds the token or a password whatever the object carries and that a malformed stored draft falls back field by field, and the GitHub standing.

Several choices in `web/test/ui.mjs` exist to keep it deterministic on a loaded host, and a change to them tends to show up as flakiness rather than a failure:

- The contrast probe reads every colour through a 2D canvas, because computed colours may come back as `oklch()` strings the luminance arithmetic cannot parse.
- The log's `End` key must settle over three consecutive at-bottom samples (0.3 s) for up to 4 s: a re-measure of the list can move the scroll end just after the first sample, and a niced host renders rows late.
- The number field in the storage policy dialog commits only on blur, so the test presses `Tab` before saving; without it the retention assertion reads the old value.
- The held-subscriber spell lasts 20 s (9 s sometimes ended before the run page opened) and must stay inside the controller's 25 s wait bound. The spell opens only once a further park by the same user is refused (the share is full), refused holders pause 25 ms instead of spinning, and "live again" gets 12 s: the relay turns the page live about `retry_after_ms` plus one second after the share frees (`busy_recovery_ms` in the metrics). The scenario used to fail about half the runs because the relay doubled its pause on every refusal (1, 2, 4, 8, 15 s) although the controller states one second, and called the page live only when a 25 s park returned, so recovery could take longer than the old 40 s wait.
- Row counts on the run page come from the first table only (`main table`): later tables, such as cache entries, load after hydration and add rows.
- The account-security scenario submits one wrong authenticator code on purpose. A session is revoked after five wrong proofs ([step-up](step-up.md)), so any added wrong-code step has to stay inside that limit.

The setup wizard has its own seed, a controller with no administrator and a setup token issued: `the_setup_wizard_in_a_real_browser` runs `web/test/setup.mjs` through every step, a refresh that resumes (token, then password, then the step the person was on), the mail step without delivery, finishing, and skipping the authenticator, checking that the stored draft never holds the token or a password. Sending a test message through a configured Resend sender is not exercised (tests never reach Resend). `pnpm -C web test:unit` runs the guard, onboarding, QR, relay-pacing (`streams.test.mjs`: a fake controller that refuses parks) and environment-name unit tests on any Node 22 (`test/ts-register.mjs` compiles the TypeScript sources with esbuild where Node has no type stripping).

## How it is built

TanStack Start with React 19 and Tailwind CSS v4 (CSS-first configuration in `src/styles.css`, colours as variables so a theme is one class), built by the Vite plugin with the Nitro Node preset into `.output/server/index.mjs`. Versions are pinned exactly in `web/pnpm-lock.yaml`; the repository's supply-chain rule (`minimumReleaseAge`, seven days) decides the newest version that may be installed, which is why `@tanstack/react-start` is 1.169.3 while 1.169.4 (published 2026-10-22) was younger than the rule allowed when it was chosen.

- **Server entry.** `src/server.ts` relays the controller's routes under the allowlist (`src/server/guard.ts`), the body ceilings and the client-address rule, serves `/_stream/run/<id>` and `/_stream/log/<attempt>` (`src/server/streams.ts`, whose long polls share one keep-alive `node:http` agent), and hands every other request to Start, hashing the rendered page's inline scripts into its policy. The controller address and the header rules live in server-only modules and never reach the browser bundle.
- **Reading data.** Route loaders call one isomorphic helper (`src/lib/api.ts`): during the server render it reads the controller with the browser's own cookie (`src/lib/api.server.ts`); in the browser it calls the same-origin proxied API. The server render only reads; mutations are made in the browser with the session's CSRF secret. No server function is used, so the interface adds no endpoint of its own.
- **Routes.** File routes under `src/routes/` mirror the paths in the Views table; `_auth` is the centred signed-out layout and `_app` the signed-in shell with the namespace switcher. Search parameters are validated by hand-written Standard Schema validators (`src/lib/search.ts`; a malformed field is dropped) and kept as plain `key=value` pairs, so deep links such as `?pr=42` or `?step=1&seq=40` read as before. The log viewer route is `ssr: 'data-only'`.
- **Widgets.** Native elements styled with Tailwind, plus three small ARIA widgets in `src/components/ui.tsx`: a listbox select, a menu button and a modal on the native `<dialog>`. React Aria Components was measured first and not taken: about 71 KB of gzipped JavaScript for those three patterns ([`bench/u09-web-spikes.jsonl`](../bench/u09-web-spikes.jsonl)).
- **Public landing page.** `/` shows a signed-out visitor what Sentinel is, with Sign in and Sign up; a signed-in person goes on, as before, to a pending return, the last tenant used or the first one. The runs view opens with the tenant's waiting jobs, connected workers and held attempts as the controller reports them.
- **GitHub App setup.** `/setup/github` (platform administrators) creates the deployment's GitHub App from the controller's manifest and lets tenant administrators install it; `/setup/github/created` and `/setup/github/installed` are where GitHub sends the browser back. They only relay the code and state to the controller ([GitHub App](github-app.md)). The page policy of `/setup/github` alone adds GitHub's origin to `form-action` for the manifest form: `https://github.com`, or the origin of `SENTINEL_GITHUB_WEB_URL` for GitHub Enterprise Server.

For a live-editing session, `SENTINEL_API=http://127.0.0.1:7080 pnpm -C web dev` serves the interface with hot reload (no page policy); sign in on the origin the controller names as `public_url`.

## Known limits

- Live views are bounded by the controller's subscriber budget (32 parked at once, 8 per user); past it pages say "Updates paused" and retry. A deployment with many simultaneous viewers of live pages should expect that; raising the budget is a controller constant.
- Secret values, source credentials and hook secrets are managed from the CLI and host-local commands; the interface shows metadata only. Email invitations are created, listed and revoked in tenant administration and accepted at `/invitations/accept`; deployment-wide and identity-bound invitations stay host-local (`sentinel admin invite`).
- Password reset is host-local only (`sentinel admin recover`); `/forgot-password` says so.
- The auto-join domains are shown, never edited: they are the operator's `SENTINEL_AUTO_JOIN_DOMAINS`.
- "Re-check access" asks for a GitHub check through the repositories read, which queues one only when the last confirmation is older than five minutes and at most once a minute per person; the answer arrives in the background.
- Removing or replacing an enrolled authenticator has no API route: it is host-local (`sentinel admin mfa disable`, [step-up](step-up.md)), and the account page says so. Unlinking an identity has no interface either (`sentinel admin identity unlink`, [GitHub sign-in](github-sign-in.md)).
- Service accounts are listed from the tenant's first 100 members.
- Keyboard and screen-reader behaviour is verified through the accessibility tree and keyboard events in a real browser, not with a screen reader in person.
