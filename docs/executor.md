# Worker execution: workspaces, checkout, rootless containers and steps

Implemented in `crates/sentinel-worker` (Linux only; empty elsewhere); the report and spec messages are in the [worker link](worker-link.md), the controller side is `dispatch::report`/`spec_bytes`. `sentinel worker` uses it whenever rootless Podman answers; otherwise it declines every offer and says why.

## Nothing is reused

Every attempt gets `<data_dir>/workspaces/<attempt>` (`workspaces/` is `0700`; the attempt directory keeps the umask's mode so a non-root image user can enter its bind-mounted `/workspace`), created empty exactly once (`Workspace::create` refuses an existing directory — a leftover belongs to [reconciliation](reconciliation.md), not to a new attempt) and destroyed after finalization. A rerun is a new attempt with a new directory. `Workspace::leftovers` lists what an earlier process left behind.

## The commit, not the branch

`checkout::checkout` asks Git for the pinned SHA itself: `git init`, `git fetch --no-tags --depth 1 -- <repo> <sha>`, `git checkout --detach FETCH_HEAD`, then `git rev-parse HEAD` must equal the SHA or the checkout is a `Preparation` failure. The branch name on the run is provenance only. Every Git invocation runs with a cleared environment, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and a `HOME`/`XDG_CONFIG_HOME` that name no directory (never the workspace, so a committed `.gitconfig` cannot configure a later Git command, and Git before 2.32, which ignores `GIT_CONFIG_GLOBAL`, finds no global config either), in its own process group under one shared deadline (`CHECKOUT_TIMEOUT`, 10 min); past it the whole group is killed. A repository argument that looks like an option is refused before Git sees it.

By default a **bound** repository's checkout runs through the worker's per-repository [object mirrors](mirrors.md) (a manual run, which names its own remote, always checks out direct): a serialized incremental fetch into `<data_dir>/mirrors/<rep_id>/`, the pinned SHA verified as a commit, then a private object store materialized into the workspace — reflink-copied where the filesystem allows, byte-copied when the store is small, and otherwise fetched at depth 1 out of the mirror so only the pinned tree is written — while a reader lease keeps GC from pruning mid-read. A mirror that cannot serve (lock wait, IO, a damaged store) falls back to the direct fetch above with the reason recorded; the remote's own answer never retries, and `git_mirrors = false` disables mirrors entirely.

Credentials reach Git through `GIT_ASKPASS` — an owner-only helper script that answers from its own environment — or, for SSH deploy keys, through a `GIT_SSH` wrapper that pins `ssh -F /dev/null` with `BatchMode`, `IdentitiesOnly`, `StrictHostKeyChecking` and the bound `known_hosts`. Bound source access arrives with the spec ([sources](sources.md)) and is verified before Git starts: exact remote, allowed ref, unexpired. Everything the checkout installs lives in a sibling `*-askpass` directory created `0700` and deleted on every path, including failure. The credential is never in a URL, never in `.git/config`, never in the job's environment, never in a log line; a failure excerpt is one bounded line with the credential replaced. HTTP redirects are off, the credential helper list is empty, and exactly one Git protocol is allowed. Unbound repositories keep the explicit manual mode: a remote named by the run, no credential.

Submodules and LFS are not fetched, and only the one repository is checked out.

## The container

`podman::probe` refuses to start without **rootless** Podman on **cgroup v2**: an executor that cannot isolate is not one. Every container is created with the baseline the probes proved enforceable ([feasibility probes](feasibility-probes.md#2-rootless-podman-resource-enforcement)):

| Flag | Why |
|---|---|
| `--cpus <job>` | CPU quota from the compiled resources (`cpu_millis`) |
| `--memory <job> --memory-swap <job>` | memory limit with no swap escape; the kernel OOM-kills inside the cgroup |
| `--pids-limit 4096` | a fork bomb ends inside its cgroup |
| `--network none` | loopback only; no egress from job steps (the default; see [job network](#job-network)) |
| `--read-only --tmpfs /tmp` | the image is immutable; `/tmp` (1 GiB tmpfs) and the workspace are the writable places |
| `--cap-drop ALL --security-opt no-new-privileges` | `CapEff` all zero, and nothing can regain it |
| `--ulimit core=0:0` | no core dump of a step, whatever it held |
| `--ulimit fsize=<disk>:<disk>` | no single file a step writes may exceed the job's declared `resources.disk` (a step that tries gets `SIGXFSZ`); a cap on one file, not on the total — see [Disk](#disk) |
| `--entrypoint /bin/sh` | the keepalive is the container's main process whatever the image's `ENTRYPOINT` says; left alone, an entrypoint would take the keepalive for its arguments |
| rootless user namespace | uid 0 inside is the worker account outside; files the job creates in the workspace are the worker's |
| `--volume <workspace>:/workspace --workdir /workspace` | the workspace; the only other writable binds are the attempt's private cache views for absolute cache paths |
| `--pull never`, image `name@sha256:…` | the bytes the run pinned; the pull is a separate, bounded preparation step (`IMAGE_PULL_TIMEOUT`, 15 min), refused for an unpinned reference |
| `--name sentinel-<attempt>`, labels `io.sentinel.worker`/`io.sentinel.attempt` | ownership recorded in the runtime itself: `podman::owned(worker)` lists what this worker created, whatever its state, for [reconciliation](reconciliation.md) |

The container's main process is a keepalive: a `/bin/sh` countdown that exits on `TERM` and, in any case, after the job's timeout plus a fixed 5 minutes (`podman::KEEPALIVE_SLACK_SECS`: the secret-clearing passes, artifact capture and the graceful stop that precede teardown) — 24 h plus that when the caller names no bound. When the keepalive ends, the container's PID namespace goes with it, so a container that a dead worker never tore down ends by itself instead of running on while the controller reallocates its capacity; startup reconciliation ([reconciliation](reconciliation.md)) removes what is left. The bound is a shell countdown rather than `podman create --timeout`, which not every Podman supports; steps run in it with `podman exec` — the image must provide `/bin/sh`, which the run spec's shells already require. There is no Docker socket, no privileged flag, and no pipeline key that loosens any of this.

`Container::exec` runs one `StepCommand`: its argv, its environment with the worker's context appended **after** the pipeline's (`SENTINEL_RUN`, `SENTINEL_JOB`, `SENTINEL_ATTEMPT`, `SENTINEL_SHA`, `SENTINEL_WORKSPACE`, `CI`), so a pipeline cannot spoof them; its working directory under `/workspace`; its timeout. Exit status and signal (Podman's `128 + n`) are reported as such; a step past its timeout stops the whole container — steps are sequential and the attempt is over. Output tails of 64 KiB per stream are kept for diagnostics; the same bytes stream through the [log pipeline](logs.md) as they are produced.

**Shutdown.** On `SIGTERM`/`SIGINT` the worker calls `Executor::shutdown` before it stops the link: no further offer is taken, offers still waiting for their spec are handed back (`Decline`, so the controller requeues them), every running attempt's container is removed in parallel (`podman rm -f`), the attempts' own threads tear down their workspaces and secret directories, and nothing is reported for them — the controller settles them by expiry exactly as for a lost lease, instead of recording a cancel nobody asked for. The wait for the teardowns is bounded (20 s); `attempts_shut_down` logs how many ended and how many were still going. A crash (no shutdown) leaves the containers to their keepalive bound and to startup reconciliation.

`Container::destroy` is `podman stop -t 2` then `podman rm -f` — the removal runs even when the stop failed or timed out (a container whose graceful stop hung must still go before its capacity is released), and the first failure is returned. Finalization runs both teardowns (container and workspace) even when one fails.

Every helper (`git`, `podman`) is also asked of the kernel to die with the process that spawned it (`PR_SET_PDEATHSIG` with `SIGKILL`, checked against a parent that died before the call; `sentinel_git::die_with_parent`), so a fetch holding a credential in its environment cannot outlive a crashed worker or controller until its deadline. The signal follows the thread that forked the helper — every call starts and waits for its helper on one thread — and reaches the helper itself, not what the helper starts; a container's own processes are the keepalive bound's business above. A helper wait that fails with an I/O error kills the helper's process group and settles its readers instead of returning with the child still running. Spawning with a `pre_exec` hook means `fork` instead of `posix_spawn`. Every helper runs in its own process group under a deadline; the wait for it is a pidfd poll, so its exit is noticed at once rather than on a 20 ms sleep tick, and the preparation helpers are also killed, group and all, when the attempt is cancelled. Diagnostic output tails are kept in a fixed ring (no per-chunk memmove).


## Job network

A job container has no network by default: `--network none` leaves it loopback only, so a step cannot fetch anything and dependencies come from caches or the source. An operator can grant outbound network on one worker with `job_network = "egress"` in its configuration. Its job containers then run with `--network pasta:--no-map-gw`: rootless pasta forwards outbound connections through the worker account's network stack, and with the gateway mapping off the container's gateway address is not the host, so a listener on the host's loopback (the worker's metrics port, a local database) is unreachable from a step. Every other address the worker account can reach is reachable, including other hosts on its networks and host services bound to a non-loopback address; firewall the worker account where that matters. The setting is per worker, never per job: a tenant cannot ask for it, the worker advertises the scheduling label `egress`, and a pipeline that needs the network selects such a worker with `runs_on: {labels: [egress]}`. The worker logs `job_egress_enabled` at start. Grant it to pools that run trusted code only: like every rootless container, a job shares the kernel ([plan](../plan.md)). `crates/sentinel-worker/tests/podman.rs` (`a_granted_egress_container_has_a_route_out_but_cannot_reach_the_hosts_loopback`) checks that an egress container has an interface and a default route but reaches neither a host loopback listener directly nor through its gateway. A microVM job has the same policy, enforced differently and a little stricter ([network](#network-m05)).
## Disk

A job's scratch disk is accounted by placement: the controller fits `resources.disk` against the disk the worker advertises (its free space less an eighth, 512 MiB to 2 GiB). A worker that could not measure its disk advertises zero, which is no disk at all: no job declaring scratch disk (every compiled job does) is placed on a protocol-7 or later worker that advertises it. The offer itself carries no disk figure, so the worker's own check is a **watermark on the data directory's file system**: while its free space is below `executor::admission_floor` — one eighth of the file system, kept between 512 MiB and 2 GiB, the same reserve the advertised disk leaves; `Executor::set_admission_floor` overrides it — every offer is refused and the controller places it elsewhere or waits, with `offer_refused_low_disk` logged at most every 30 s. A file system that cannot be measured is admitted: an unmeasured disk is not a full one. The check is one `statvfs` per offer, outside the state lock. Per job, Podman can bound only what it can meter: `--ulimit fsize` caps any single file at the declared disk, and `/tmp` is a 1 GiB tmpfs. Rootless Podman has no storage quota on a bind mount (no `io` delegation, see [feasibility probes](feasibility-probes.md#2-rootless-podman-resource-enforcement)), so the total a job writes into its workspace is bounded by admission and by the declared figure the controller placed it with, not enforced per byte; the spool and the cache keep their own quotas.

## The image pull

`podman::pull` is the only way an image arrives — the worker checks `podman image exists`, then runs an explicit `podman pull --authfile …` for a pinned `name@sha256:…` reference under `IMAGE_PULL_TIMEOUT`. The result of the first check is the `image_present` signal. A credentialed pull, or any pull into a tenant's private store, contacts the registry even for a resident digest, so a warm digest never skips that tenant's authorization. An anonymous pull into the shared store uses a resident digest without asking the registry (`podman::registry_check_needed`): it carries no authority to check, the shared store only holds what was anonymously pullable, and a digest names immutable content. Asking anyway would cost a registry round trip per job (about 1 s) and exhaust Docker Hub's anonymous limit of 100 manifest requests an hour. `images::Images` keeps one in-flight pull per exact reference, tenant and credential fingerprint. Matching attempts in the same tenant share a pull; another tenant or rotated credential must authorize its own pull. Followers wait on their leader's result, bounded by their own deadline and stopped early by their cancel flag. A stale slot whose leader vanished is dropped by the first follower whose deadline passes, so nothing accumulates and a failure retries fresh on the next attempt. A tag never reaches this path.

Preparation **overlaps the pull with the checkout** — they touch different state (the content store versus the fresh workspace): the checkout runs on its own thread while the attempt thread pulls, joined before `Container::start`. A checkout that has already failed still skips the pull, a cancel still aborts preparation (the checkout is joined first — it owns the workspace until it ends), and when both fail the checkout's error is reported, exactly as when the two ran in sequence. `checkout_ns` and `image_pull_ns` each measure their own phase's wall time, so their sum can exceed the wall-clock time preparation took.

Pulls run as the worker's rootless user with an explicit auth file from the acknowledged attempt's secret bundle. The controller resolves the job's declared `registry_auth` secret inside the same writer transaction that checks the live worker, attempt and fence; its version and attempt are audited. The secret is host-only and is never added to a step environment. Pulls remove `REGISTRY_AUTH_FILE` and `DOCKER_CONFIG`, pass the scoped `--authfile`, clear `PATH` after resolving the Podman executable, and accept only an OCI auth JSON object containing `auths`. This prevents ambient auth files and named external credential helpers from authorizing one tenant with another tenant's worker credentials. A credentialed pull always contacts the registry for the manifest and config, including when the digest is already in the local store; resident layers are reused without a fetch, so authorization is per manifest, not per layer. A credentialed pull therefore goes to the tenant's private store (`podman::Store::Private`, `--root`/`--runroot` on every command for that image and its container) and never to the shared one, which only anonymous pulls fill ([secrets](secrets.md#execution-binding-and-cleanup)). A public prefetch uses an empty scoped auth file and lands in the shared store; only shared-store pulls join the held set placement reads. An unavailable external helper fails closed, so workers should move private-registry access to the per-tenant `registry_auth` binding.

Secret environment values are exported by a `/bin/sh` wrapper from a file mounted read-only at `/run/sentinel-env`, never passed to `podman exec` (which would write them into its on-disk exec spec); file secrets appear read-only at `/run/sentinel-secrets/<path>`, readable by a non-root image user. Both are staged under the worker's runtime directory (tmpfs when `XDG_RUNTIME_DIR` is usable), outside the workspace, cache mounts and artifact roots. Only values needed by the current step are materialized, and the container is cleared of every process but its keepalive before such a step and after it (`Container::clear_strays`: freeze the cgroup, `SIGKILL`, thaw; about 2.3 ms), so no other step's process sees them. Containers are created with `--ulimit core=0:0`. The log redactor registers every delivered value before a log pipe opens and retains enough bytes to redact matches split across read frames. Files are zeroed and removed after their step; the attempt's private secret directory and registry auth file are removed on success, error, cancellation and panic. Startup recovery reaps leftovers from a worker crash before another attempt can use them. The current active secret version is selected for every new attempt, including a rerun; historical versions remain auditable but are not implicitly replayed.

**Bounded prefetch.** An offer names only the image digest, so a pull cannot start from an offer; the controller instead hints references ahead of placement. After every dispatch pass (at most every 500 ms), `dispatch::prefetch_hints` reads the longest-waiting ready jobs (at most 256, off the `jobs_queued_since` index) whose image name and digest are on the job row (`jobs.image_name`, migration 36) and picks, per idle or underused protocol-9 worker, up to 4 `name@sha256:…` references of jobs it could be placed — its tenant may use the worker's pool, architecture, labels, CPU, memory and disk fit, the worker is not draining and does not already report the image warm — hinting each image to at most 2 of the most idle such workers. The session sends `Prefetch { images }` (the whole wanted set) only when that set changed, empty included. On the worker, `prefetch::Prefetcher` rebuilds each reference from its parts (digest-pinned, reference charset, no tag), replaces its wanted set, and pulls in the background through the same `Images` single-flight lane. Prefetch uses no tenant secret; each actual attempt performs its own authorized pull before using a resident digest. The pull lands in the held set, the next profile refresh reports it warm, and a profile refresh wakes placement. Bounds: one prefetch pull at a time and none while an attempt leads a pull of its own; a byte budget of 4 GiB per 10 minutes charged with each pulled image's real size (`podman image inspect`), since `podman pull` has no rate limit; a pull starts only while podman's graph root keeps a tenth of its filesystem (at least 2 GiB) free, and never when that cannot be measured; `IMAGE_PULL_TIMEOUT` per pull. A reference that leaves the wanted set is stale: not started, it is dropped; under way, its `podman pull` is killed — unless an attempt already joined it. A failed or skipped reference is retried only when a later hint names it again. Measured: with a fake 300 ms pull over the real link, a job a locality hold kept from an idle cold worker was offered to it after 5.0–5.2 s instead of 30.0 s (the hold's bound; the refresh waits for the next heartbeat); with rootless Podman on WSL2, an attempt's pull of the 123 MB `python:3.12-slim` took 2.25–2.39 s cold and 29–52 ms after a prefetch (`tests/prefetch.rs` in `sentinel-link` and `sentinel-worker`; [`bench/b04-transfer-copies.jsonl`](../bench/b04-transfer-copies.jsonl)).

Every confirmed pull records the digest in a bounded held set (`images::MAX_HELD`, oldest-first eviction) exposed by `Executor::images().held()` — the locality record every session's profile advertises for placement (the newest 64 as 8-byte keys, refreshed from protocol 8 when it changes; [worker link](worker-link.md)). It is learned from pull outcomes alone, never scanned at startup: a restarted worker's set is empty and relearns on the next pull, whose `image exists` check is the same authority either way.

## The attempt

`attempt::run` is the lifecycle the controller's state machine expects, reported under the attempt's fence: `PreparationStarted` → workspace, checkout, image pull, container start → `StepsStarted` → each step in order → `FinalizationStarted` → **artifact capture while the workspace still exists** → teardown → durable log completion (the spool is kept until the controller's `LogEndAck` on protocol 5, or the `LogEnd` send on older links — [logs](logs.md)) → `Passed` or `Failed(class)`:

| What happened | Class |
|---|---|
| fetch, pull or container start failed | `Preparation` |
| a step exited non-zero | `CommandFailed` |
| a step died from a signal | `CommandSignaled` |
| a step passed its timeout | `ExecutionTimeout` |
| cancel seen between steps | `Canceled` |
| a `required` artifact absent or unpublished | `Publication` (`infra_failed`) |

`executor::Executor` is the link's `Executor`: it takes an offer when the runtime is usable and fewer than `MAX_LIST_ITEMS` attempts are held — a repeated offer of an attempt it already holds or awaits is re-acknowledged, never started twice — asks for the run spec over the link (`NeedSpec` → `Spec` chunks of 48 KiB, at most 1 MiB), decodes it and starts the attempt on its own thread. A spec request that goes unanswered is asked again every `SPEC_RETRY` (10 s); an attempt still without a spec after `SPEC_DEADLINE` (60 s) is handed back with `Decline` — it never started, so the controller requeues it (`Notice::HandedBack`); a `NoSpec` is definitive and the attempt is reported `Failed(Preparation)` at once. Reports go out on the live session in order; without a session they queue in memory and are replayed at the next attach (a durable spool is not part of the executor). A `stop` from the controller flips the attempt's cancel flag and removes its container off the heartbeat thread; it is not reported, because the controller already counts the attempt as gone. A panic in an attempt's thread is contained: its container and workspace are removed, what it printed is delivered and its log closed (the spool goes with it), and it is reported `Failed(Runtime)` instead of staying held until the controller's backstop. Every attempt's spool draws on one `SpoolSpace`: a quota on the bytes all spools hold together and a free-space reserve on the data directory (`set_spool_limits`, from the worker's `spool_quota_bytes` and `spool_reserve_bytes`; defaults 4 GiB and 1 GiB). Output past either is declared as gaps in the attempt's log, never lost in silence, and `Notice::SpoolRefused` reports the refused frames by cause when the attempt finishes ([logs](logs.md)).

Secret values are redacted **per attempt**: `Executor::register_secret(attempt, value)` registers into that attempt's log pipe — immediately, also while it runs, or before it starts when it is still waiting for its spec — and returns whether the value was accepted (at least `MIN_SECRET_BYTES`). Nothing registered for one attempt touches another's output, and it goes with the attempt. The verdict detail and the stored summary pass through the same redactor, and a failed step's stderr excerpt is redacted from the raw tail before it is decoded, reduced to its last line and cut to 200 characters — multi-line values line by line, a wrapped ring without its first line — so neither a whole value nor a line of a multi-line one, a value with a control character, a binary value, or one straddling the cut reaches `attempts.summary` or the worker's own log. A value shorter than `MIN_SECRET_BYTES` (4) is refused by the redactor, and a bound secret that short fails its attempt as `Preparation` instead of being delivered unredacted; a value of up to 16 KiB is also redacted as base64 and percent-encoded ([logs](logs.md)); a value the step itself printed only in part, or transformed in any other way, cannot be recognized by any exact-match redactor.

On the controller, `dispatch::report` checks that the attempt is held by that worker under that fence and then applies the event through the state machine; a stale or foreign report changes nothing and is counted. A terminal report is also the finalization boundary: the same transaction stamps `log_state` from the `end` marker's durability, checks every due artifact declaration against its row — a missing one is recorded `failed`, and a due *required* one that never reached `captured` turns a reported `Passed` into `Failed(Publication)` — releases the reservation, decides dependents and wakes the dispatcher. `expire`, `abandon` and startup reconciliation stamp the same way, so a lost worker's attempt reports its real data status rather than a defaulted one.

**Artifact capture.** Once the steps settle, `artifacts::capture` walks each declared artifact whose `when` matches the step verdict — the same descriptor-rooted resolver as `hash_files` (`openat2` `BENEATH | NO_SYMLINKS | NO_XDEV` under the pinned workspace root, shared traversal budgets), so a pattern can never escape into the host or follow a link planted by the job. Each file streams to the controller in `ArtifactData` chunks — nothing buffers a whole artifact — and the controller stages, digests and commits it into the object store, ending in the `{job}/{name}` manifest and the durable `artifacts` row ([storage](storage.md#artifact-records-d03)). Capture runs before workspace teardown and before the terminal report, so a controller-side verdict is always known before the attempt goes terminal; a required artifact that ends `absent`/`failed`/unpublished converts to `Publication`, an optional one is recorded and the job keeps its verdict. On a protocol-3 link the sink reports itself incapable and every declaration resolves `absent` without touching the filesystem.

## Steps

Steps run in order in the attempt's container, each as the run spec compiled it: `/bin/sh -e -c` (fail at the first failing command, with its status) or `bash -eo pipefail -c` (the image must provide Bash); the job's environment, then the step's overriding by name, then the worker's context (`SENTINEL_RUN|JOB|ATTEMPT|SHA|WORKSPACE`, `CI`) last so a pipeline cannot spoof it; the working directory joined under `/workspace`; the step's timeout, or the job's, **bounded by what is left of the job's budget** so a job cannot outlive its timeout through many steps each within theirs. A step after a failed one never starts and is recorded as `NotRun`.

A step's `if:` is evaluated on the worker (`Phase::Worker`, the expression evaluator of the [pipeline schema](pipeline-schema.md#expressions-c06)) against the job context the controller sends with the spec — `job.id|name`, `repo.id|name`, `run.id`, `event.sha` (the pinned commit), `event.ref` (the run's ref name), `needs.<job>.result` and `success()`/`failure()`/`always()`/`cancelled()` from the dependency outcomes and cancel state — and `hash_files` over the private checkout. `false` skips the step (`Skipped`); a non-boolean, a type error or a value the run does not hold is a `Preparation` failure naming the step and the reason, never a default. Event fields intake does not record (`event.name|key|base_ref|pr_number`) are exactly that case.

The verdict keeps these distinctions, and the summary records them per step:

| What happened | Failure class | Step outcome |
|---|---|---|
| exit 0 | — | `Passed` |
| `if` false | — | `Skipped` |
| non-zero exit | `CommandFailed` | `Failed { code }` |
| killed by a signal, OOM counter unchanged | `CommandSignaled` | `Signaled { signal }` |
| killed and the cgroup's `oom_kill` counter moved | `OutOfMemory` | `OutOfMemory` |
| past its (bounded) timeout; the container is stopped | `ExecutionTimeout` | `TimedOut` |
| Podman could not run it (exit 125–127 with its `Error:` line; a shell's own 126/127 stays a command failure) | `Runtime` (`infra_failed`) | `Runtime` |
| fetch, pull, container start, `if` unresolved | `Preparation` | — |
| cancel seen between steps | `Canceled` | — |

OOM is read from the host's view of the container's cgroup (`/sys/fs/cgroup<CgroupPath>/memory.events`, path from `podman inspect`), before and after a failed step: after an OOM the pages that caused it stay charged, so a process exec'd inside to read the counter could be the next victim and the OOM would be misreported as a signal.

**Timings.** Every phase is measured with a monotonic clock in nanoseconds: checkout, image pull, container start, all steps, finalization, and each step. Absent means not measured. They travel in the `AttemptSummary` (`sentinel-protocol::summary`, format byte 4, at most 32 KiB) with the terminal `Report` and are stored once on the attempt row (migration 15; the trigger refuses a replacement). A summary over the cap is not an error: the controller drops it, keeps the verdict, and the session stays open. `checkout_ns` stays the whole checkout; `checkout_fetch_ns` and `checkout_materialize_ns` split the mirror update from the worktree materialization, and `checkout_route` says which path produced it ([mirrors](mirrors.md)). `image_present` records whether the pinned image was already held locally before the required scoped registry authorization pull, and `caches` carries one bounded record per declared `cache:` entry: restore outcome and phase timings (`lookup`/`lock_wait`/`clone`/`first_touch`), file/byte/copied counts, the commit's `commit_ns` and staged/reused/dirty split with its publish answer, and the `costly_hit` flag ([cache](cache.md)). `dispatch::attempt_summary` reads it back.

**Worker availability.** The same bounded sweep that reclaims the cache root — at worker start and after every attempt's finalization, never on a timer — ends by emitting `Notice::Availability`, a compact snapshot of what this worker could serve: the sorted digests its image store is known to hold (`images::held`, bounded by `MAX_HELD`), pulls in flight, and cache-root occupancy (entries, generations, payload bytes held, `truncated` when the pass hit its work bound). The pass computed those counts already, so the snapshot costs no second walk; the digest list never reaches a log line — only counts do. A nominal hit whose restore paid rebuild-scale cost is flagged separately as `Notice::CostlyCacheHit` under the documented rule in [cache](cache.md) — a warning, never a verdict.

## MicroVMs

A worker with a `[microvm]` setup runs an attempt in a Firecracker VM instead of a rootless container where the job or the worker's `isolation` default says so ([configuration](configuration.md), [plan 16.8](../plan.md#168-microvm-execution-on-kvm-hosts)). The attempt flow, the log, spool and redaction path and the artifact and cache handling are the container path's; `sandbox::Sandbox` is the only fork. A VM's network and its warm start from a snapshot are below ([network](#network-m05), [snapshot warm start](#snapshot-warm-start-m06)).

**Guest images (M03).** The job's pinned `name@sha256:...` reference is pulled exactly as for a container, then `microvm::guest_image` converts it once into a read-only ext4 root file system under `<data_dir>/microvm/images/<key>.ext4`, `<key>` naming the (store, reference) pair so a tenant's private store never shares a file with the shared one. A tag is refused (`image is not pinned by digest`). The build asks `podman image inspect` for the image's manifest digest and repo digests and refuses an image that does not carry the pinned digest, so the root file system a job boots is always the one the controller pinned. `<key>.json` is written after the ext4 file and is the marker that the image is complete: it records the digest, the image ID, the file's size, the image's environment and its configured `USER`, and its modification time is the image's last use (a hit refreshes it when it is older than a minute). A hit costs one open of the marker and one stat. Concurrent attempts on a new image build it once; a cancel stops a waiting or running build. The kernel is the operator's pinned guest kernel booted directly, the agent is the `/init` of an initramfs written once per agent binary, and each attempt gets a fresh scratch disk sized to its disk reservation (the per-attempt writable layer); the image disk itself is never written. A step runs as the image's `USER` (`name`, `uid`, `name:group` or `uid:gid`, resolved by the agent against the image's own `/etc/passwd` and `/etc/group`, with the user's supplementary groups; an unknown name fails the step) the way `podman run` does, and the workspace the step starts in is given to that user first (the copy the guest unpacked belongs to root). Steps get no core dumps and `no_new_privs`, as a container does. A VM has `GUEST_OVERHEAD_MIB` (64 MiB) of memory beyond the job's reservation for its kernel and agent; the agent puts every step into a memory cgroup of its own and `Request::MemoryLimit` caps it at the reservation, so a step that outgrows it (a `dd` into the memory-backed `/tmp`, say) is OOM-killed inside the guest, counted by `oom_kills`, and the agent stays able to report it, as for a container's cgroup; a guest kernel without memory cgroups fails the start.

**The digest a job ran.** The VM records the guest image it booted (`GuestImageRecord`: the pinned digest, the root file system's size, whether this attempt built it and for how long) in the attempt's `AttemptSummary` (format 4, [compatibility](compatibility.md)), which `GET /attempts/{id}/steps` returns as `guest_image` ([API](api.md)). It is absent for container attempts. Together with the job's own `image_digest` row it makes the digest a job ran part of its provenance.

**Image GC under the image budget.** The sweep that reclaims Podman's images (`Executor::sweep_images`, at most once a minute, after attempts and at start) counts cached guest images against the same `image_bytes` budget: Podman's unused images go first against what the guest images leave of the budget, then `images::Images::reclaimable_guests` gives back whatever still does not fit, least recently used first, at most `MAX_IMAGE_REMOVALS` per pass. Nothing used within `IMAGE_KEEP` (10 minutes), no image whose digest is being pulled and no image a live attempt holds is removed. An attempt holds an image through an `ImageLease` taken before the cache is consulted and kept by the VM until it is destroyed (a lease also covers the build of a new image), so a day-old attempt's root file system stays however stale its marker is; `remove_guest_image` refuses a leased image under the same lock a lease is taken under, which makes a removal either finish first (the next lookup misses and rebuilds) or see the claim, and `GuestEntry::in_use` keeps the LRU plan off it. Several attempts on one image share the claim. An image is a hit only while its marker parses, names the pinned digest and the root file system has the recorded size; a truncated or missing root file system, an unreadable marker or a marker without its file is dropped (the marker first, so GC does not count it) and rebuilt by the next attempt, once however many attempts ask at the same time. A same-size root file system with changed content is not detected: the file is written once by a build the worker made and is never opened for writing afterwards. Files in the image directory that no complete image owns (temporaries of failed builds, an ext4 file whose marker never landed, leftovers of an earlier layout) are removed once an hour old. The figure counted is the root file system's apparent size, which is conservative for sparse files.

**The workspace copy.** A VM works on its own copy of the workspace, which the host does not see change. What the host reads afterwards comes back through the agent: `sync_out` at the end for the declared artifacts and the writable mounts, and, before a step `if:` evaluates `hash_files` after an earlier step ran, `Sandbox::pull_workspace` for the patterns it names (`WorkerContext::with_refresh`; a container shares the directory and does nothing). The agent returns literal paths, so a glob (`out/**`, `target/*.so`) is fetched as the directory its literal prefix names (`.` when it starts with a glob) and the host applies the glob to what arrived; a symlink the guest made arrives as a symlink and is refused by the same checks as in a container.

**Isolation.** The VM configuration (`microvm::vm_config`) has exactly five sections: boot source, the read-only image drive plus the scratch drive, machine config without a named CPU template, a custom CPU template (`cpu-config`, `microvm::CPU_CONFIG`) that clears CPUID.1:ECX bit 5 (VMX) and CPUID.80000001:ECX bit 2 (SVM), and vsock; a guest the worker granted egress has a fifth, its one network interface ([network](#network-m05)). The guest is therefore given no hardware virtualization: no `/dev/kvm`, no nested KVM and no `vmx`/`svm` flag (Firecracker passes the host's flags through unless the template masks them; the template is part of every snapshot's name) (a pool that wants it decides so explicitly in M09). The VMM runs in a user namespace from `podman unshare` (whose mount namespace every `podman unshare` of the account shares, so the VMM takes a mount namespace and a network namespace of its own with `unshare --mount --net`), a user systemd scope that caps CPU and memory, and Firecracker's seccomp filters.

**Network (M05).** A VM has no network interface at all unless the worker sets `job_network = "egress"`: the same setting, the same `egress` scheduling label and the same trust rules as for containers ([job network](#job-network)). Granted, the VM's own network namespace (created rootless with the VMM by `podman unshare` and `unshare --net`; no interface, bridge or rule of the host is touched) holds a tap device `vmtap` (10.211.0.1/30) that Firecracker attaches as the guest's one virtio-net interface (`eth0`, 10.211.0.2, the same in every VM because each has a namespace of its own). The guest agent configures it from the kernel command line (`sentinel.ip`, `sentinel.gw`, `sentinel.dns`). Before the VMM starts, the namespace loads the nftables rules `net::Policy::rules` generates (`egress.nft` in the VM directory): forwarding is closed (`policy drop`), the guest may answer connections it opened (`ct state established,related`), may ask the resolver address 192.0.2.53 on port 53 (`pasta --dns-forward` answers it with the host's resolver), and may open connections outward from its own address except to the refused destinations; everything else is dropped, including anything addressed to the namespace itself (the tap) and all IPv6, and outbound packets are masqueraded behind the namespace's address. The refused destinations are 0.0.0.0/8, loopback, link-local (169.254.0.0/16, which holds the cloud metadata endpoints 169.254.169.254 and 169.254.170.2), 100.100.100.200 (Alibaba Cloud metadata), 192.0.0.0/24, multicast and reserved ranges, the VM's own link, every IPv4 address of the host's interfaces (read at each start, so a service bound to any host address is out of reach) and the controller's link endpoint, address and port (`[microvm]` `Setup::guard`: the configured `controller` and the local Tailcat forward when the link goes through the helper). `pasta` is attached to the namespace by the launch script (`launch.sh` in the VM directory) with the container policy's `--no-map-gw`, every port forward off and IPv4 only, and carries the namespace's outbound connections through the worker account's sockets. As for containers, every other address the worker account can reach stays reachable (other hosts on its networks): firewall the account where that matters. The tap, the namespace, `pasta` and the rules belong to the VM's systemd scope and go with it, so cancel, lease loss, shutdown and startup reconciliation need nothing of their own for the network. Egress needs `ip` (iproute2), `nft`, `pasta` and `/dev/net/tun` for the worker account; the worker logs `microvm_egress_unavailable` at start naming what is missing, and a VM whose network cannot be set up fails its start (`Preparation`) with the console output. Guests get no IPv6.

**Snapshot warm start (M06).** With `snapshots = true` in `[microvm]` (the default), a VM is restored from a snapshot of a booted guest of its shape instead of being booted. The shape is the image, the vCPU count, the memory, the scratch disk size and whether the guest has a network; a snapshot is named by the image's key and a digest of that shape, of the root file system file's identity (size, inode and modification time, so a rebuilt image is a different file), of the initramfs (named by the agent's digest), the kernel and Firecracker files, the boot line, and of the host's CPU model, flags and kernel release, so any changed input is a miss and never a stale hit. `microvm/snapshots/<name>/` holds Firecracker's `state` and `mem` files, the pristine `scratch.ext4` and `meta.json`, written last as the completeness marker (its modification time is the last use, as for guest images). Every restore maps `mem` privately, so the page cache backs all restored VMs and each pays only for the pages it touches; each restore gets its own clone of `scratch.ext4` (a reflink where the file system has them, else a copy of only the data extents), so no attempt's writes reach the snapshot or another attempt.

The first VM of a shape builds its snapshot: a template VM of that shape (a VM directory and scope of its own, which startup reconciliation finds like any VM; with the tap and rules but no uplink) boots, its agent answers, the host closes its connection, the VM is paused (`PATCH /vm`) and saved (`PUT /snapshot/create`, full), the files move to a staging directory and are published by renaming it. The attempt then restores like every later one. An attempt that finds the same snapshot being built boots cold at once instead of waiting, and a shape whose build failed boots cold for ten minutes before another try. Guests with more than 8 GiB of memory boot cold, because the memory file is written whole.

Firecracker cannot rebind a drive when it loads a snapshot, so the paths saved in a snapshot must stay valid: every VMM that builds or restores one sees its VM directory at the fixed path `microvm/run` (an empty directory on the host), where the launch script binds it inside the VMM's own mount namespace. A restore clones the scratch disk and links the image into the attempt's directory, starts a VMM with no configuration, loads the snapshot with `resume_vm`, connects to the agent and sends `Resume`: 64 fresh bytes credited to the guest kernel's random pool (two restores never share a random stream) and the host's wall clock. The workspace and mounts then go in as for a cold boot. The snapshot is taken before any job data exists.

A restore that fails at any step (the snapshot unreadable, Firecracker refusing the load, the agent not answering) stops the VMM, clears the attempt's directory, removes the snapshot (the next attempt builds a new one) and boots the same attempt cold; a cancel during a build or a restore stops what it started like any start. `Vm::start_report()` says which path ran (`Start::Cold` or `Restored`), how long the guest took to be ready (monotonic, from the start of the VMM to the agent's answer to `Resume`; a build is inside it for the attempt that made the snapshot, which `snapshot_built` marks), and the reason for any fallback; the attempt summary does not carry it. Snapshots count against the image budget with their root file system (`GuestEntry::bytes` includes them, and removing an image removes them), a rebuilt root file system removes the snapshots taken from the old one, and the hourly orphan sweep removes snapshots of images that are gone and staging directories older than an hour. The agent protocol moves to version 2 (`Request::Resume`; version 3 below); the agent binary and the worker ship together, and the initramfs name changes with the agent, which invalidates older snapshots (the initramfs is written to a temporary of its own per call, so attempts starting together share one file). The warm-start budget (ready to first user process p95 under 2 s) and the cold-boot figure published beside it are measured by M06's benchmark, not by the tests below.

**Per-step secrets.** A step's secret files and environment file are delivered the way a container is given them, once per step and not before it: `Sandbox::deliver_secrets` puts them into the guest under `/run/sentinel-secrets` and `/run/sentinel-env` (`agent::SECRET_MOUNTS`), which the agent mounts as tmpfs at boot so the bytes never reach the guest's disk, and `Sandbox::retract_secrets` sends `Request::Wipe` after the step so a later step of the job does not see an earlier step's secrets. The guest root file system is otherwise the job's, so a step that is not given a secret cannot read one.

**Cancel, lease loss and shutdown.** All three set the attempt's cancel flag and then act on the VM by name (`sandbox::terminate` / `sandbox::remove`). The VM's directory exists from the start of `Vm::start_canceled`, so a cancel or lease loss that arrives during the image build or the boot finds the VM, and the start itself observes the flag (before the image build, in the build's process wait, in the boot's connect loop and after the workspace is copied in) and removes what it made (`microVM start canceled`). A polite cancel signals every guest process with `SIGTERM` through a connection of its own to the agent, asks it to report when no guest process is left (`Request::WaitIdle`, bounded by the grace period) and, when something is still running at the end of it, signals `SIGKILL`; the outcome is `Graceful` when the processes left on their own and `Forced` when the kill was needed, as for a container. Each confirmation must arrive within 5 s; a guest that cannot be reached or does not confirm loses its VM instead (scope killed and stopped, directory removed), which closes the connection the running step waits on, so that step ends with a runtime error at once. Lease loss and shutdown remove the VM the same way without the polite phase. Removal is strict: it kills the scope, stops it, checks `is-active`, and keeps the directory and reports an error when the scope is still up, so the VM is still found by startup reconciliation ([reconciliation](reconciliation.md)).

## Verification

Tests of this area live in `crates/sentinel-worker`:

- `tests/checkout.rs` (any Linux, needs `git`): the pinned commit is checked out even when it is not the branch head and only it is fetched; a workspace is never reused; an unknown revision is a `Preparation` failure; a transport Git refuses and an option-shaped repository are refused in bounded time; a credential delivered through askpass leaves neither the helper nor the secret behind.
- `tests/images.rs` (any Linux, needs `git`, no registry): the pull begins before the checkout finishes; a tag-only reference is refused on the shared path. The unit tests of `src/images.rs` cover single-flight pulls, followers' errors and retries, early cancel and the bounded held record.
- `tests/runtime_failures.rs` (any Linux, `podman` shimmed on `PATH`): a container whose stop fails is still removed; recovery refuses to proceed when the runtime cannot list or remove what the worker owns.
- `tests/executor_faults.rs` and the executor's own unit tests run the real executor against a live controller (`tests/support/live.rs`): a worker clock a minute ahead never ends live work; a cancel that finds the step still starting is tried again; a stop order never holds the heartbeat thread; a panicking attempt is torn down and reported `infra_failed`/`runtime`; a shutdown ends the running attempt without reporting it.
- `tests/podman.rs` and `tests/end_to_end.rs` run only with `SENTINEL_PODMAN_TESTS=1` as an account with rootless Podman (otherwise they report "skipped"). They check the enforced limits inside a real container, a resident image still going through `podman pull` with its auth file, exit codes and signals, OOM, timeouts, graceful and forced cancel, `if:` gating, secret redaction and that no container, workspace or spool is left behind.
- `src/redact.rs`, `src/logpipe.rs`, `src/process.rs` and `src/workspace.rs` unit tests cover redaction (floor, base64, percent-encoding, size cap, per-attempt registration), helper cancellation and output tails, and workspace removal of read-only trees and planted symlinks.

- `src/microvm.rs` unit tests (any Linux, no KVM, `systemctl` and the guest agent faked): the guest image's cache key, marker, stamp and digest check, damaged and partial images rebuilt, a stampede on a new image building it once, leases keeping GC off an image in use and the budget's LRU eviction, glob artifact paths fetched as literal directories; the inspect answer parser; orphan sweeping; the VM configuration giving the guest no nested virtualization; startup reconciliation of directories and scopes (including a scope with no directory, another worker's scope, a scope that will not stop and a failing listing); polite (graceful) and stubborn (forced) cancel through the agent, a guest that does not answer, an unreachable agent; a canceled start making no VM. `src/microvm/net.rs` unit tests cover the generated rules (the built-in refusals, the host's addresses, the controller's endpoint, the order of the accept after the refusals, IPv6 and the namespace closed, determinism) and the installed scripts; `src/microvm/snapshot.rs` the snapshot naming (every input changes it), completeness, publication, budget accounting, removal with the image, orphan sweeping, the scratch clone and the build lock; `src/microvm/fcapi.rs` the Firecracker API client. `src/images.rs` unit tests cover the guest-image budget and its LRU reclamation. The agent's tests cover the kernel command line's network, the framing of `Resume`, `Wipe` and `WaitIdle`, and the resolution of an image user against the image's account files.
- The worker suites that run real jobs run under either executor (TODO M04): `end_to_end`, `slice`, `k09` and `secret_isolation` read `SENTINEL_MICROVM_TESTS` through `tests/support/isolation.rs` and put their executors under microVMs, with the setup in `SENTINEL_FIRECRACKER`, `SENTINEL_GUEST_KERNEL` and `SENTINEL_GUEST_AGENT`, or under rootless containers when only `SENTINEL_PODMAN_TESTS` is set; run each binary once per executor. The same assertions hold for both: polite and forced cancel, timeouts, OOM, `if:` gating, artifacts and caches, secret isolation, stray clearing, no sandbox, workspace or spool left behind, the recovery of an attempt a crashed worker left, and a `sealed` job that asserts `/dev/kvm` is absent (under microVMs also that the CPU's `vmx`/`svm` flags are). Under microVMs the attempt summary must also carry the pinned digest as `guest_image`. `runtime_failures` and `recovery` shim the `podman` binary and therefore test the container runtime's error handling; the microVM counterparts (a scope that will not stop, a failing listing, reconciliation of leftovers) are the `src/microvm.rs` unit tests above. `artifacts` tests capture from a directory and is independent of the executor.
