# API and CLI

Implemented in `crates/sentinel-api` (HTTP/1.1 on the crate's own bounded acceptor — 64 connections (at most 16 from one peer address, an IPv6 /64 counted as one; a configured reverse proxy is exempt), 8 handler permits of which at most 3 go to transfer bodies, and a separate budget of 32 parked long polls (at most 8 of one user, whatever credential it presents) that hold a connection but give their handler permit back while they wait, so 5 permits always serve everything else; deadline-bounded heads/bodies/writes) and `sentinel api …` (the CLI client in `crates/sentinel`). `sentinel server` opens the API on `api_listen` (default `127.0.0.1:7080`) beside the worker link. The human web interface is a separate process in front of it ([web interface](web-ui.md)).

## One surface

Everything a person, the CLI, the web interface or an agent does goes through the same routes, authenticated the same way and authorized by the same store predicates. The web interface is not a second path into the controller: it renders pages and relays updates by calling `/api/v1/…` with the browser's own session cookie ([web interface](web-ui.md)).

Plain HTTP on loopback by default; TLS and exposure are a reverse proxy's job. The session cookie is `__Host-sentinel_session` (Secure, HttpOnly, SameSite=Strict), which a browser accepts from `localhost` or over HTTPS only — deliberately.

A response body that fails mid-stream, or ends shorter than its declared length, closes the connection (`Request::respond` sets `close` and, on a failed write, shuts the socket) instead of reusing it for another request head. Otherwise the client would read the next response out of the middle of the unfinished body, a framing desync; keep that branch when changing `respond`.

## Authentication and authorization

| Credential | How | Mutations |
|---|---|---|
| `Authorization: Bearer sntl_…` ([API credentials](api-credentials.md)) | `tokens::authenticate`: one digest lookup; scope is a ceiling on the account's live membership | allowed; no CSRF (nothing sends a bearer ambiently) |
| session cookie ([local authentication](local-authentication.md)) | `local_auth::authenticate` | require the `x-sentinel-csrf` header with the session's CSRF secret, else `forbidden` |
| `Authorization: Bearer sntl_at_…` ([OAuth](oauth.md)) | `oauth::authenticate_access`: one statement (token, grant and account by key); the grant's scopes are the ceiling | allowed; no CSRF |

The credential yields a `Principal`; every route then asks the store — `auth::require_repo` for anything under a run, `auth::list_repos`, `tenancy::pools_for_tenant` and `workers::in_pool` under an `Authority` — so a resource the caller may not see is `not_found`, never revealed. A bearer credential can never step up. Every route also requires the **scope** in its row below: an OAuth access token carries exactly its grant's scopes, while a session or `sntl_` credential carries the scopes its permissions imply (`read` → every `:read` scope and `secrets:metadata`, `run` → `runs:write`, `cache:write` and `artifacts:write`, the administrative bits one to one), so their authority is unchanged. A missing scope is `403 forbidden` with `details.scope` and `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`; every `401` from `/api/v1` carries `WWW-Authenticate: Bearer realm="sentinel", resource_metadata="…"` naming the RFC 9728 location of `{issuer}/api/v1` ([OAuth](oauth.md#access-tokens-on-the-api)), plus `error="invalid_token"` when a token was presented (the login and hook routes excepted). A credential the store is too busy to check is `rate_limited` (`429`, `details.retry_after_ms`), never `401`, so a client does not take overload for a dead credential. A session's idle deadline slides (one write per session per five minutes) as it is used.

With no cursor, Go test/rustc/cargo JSON parsing starts at sequence 0 and reads at most 4 MiB or 1,024 frames; when that page is cut, the failed step's newest window (at most 4 MiB/1,024 frames, sought through the sparse index so a later `always()` step cannot displace it) is parsed too and is the excerpt's source. Failures and errors are budgeted before warnings and informational records. Text defaults to 8 KiB, `budget` accepts 1–65,536, and `limit` defaults to 20 diagnostics (max 20). With no `budget` the whole compact JSON body is at most 8 KiB: tail frames go first, oldest first, and a frame larger than the remaining excess keeps its newest bytes and carries `cut:true`; then diagnostic messages longer than 256 bytes are shortened from the end, last diagnostic first, keeping at least their first 256 bytes and carrying `message_cut:true`; whole diagnostics are dropped (and counted in `omitted_diagnostics`) only after that. Every secret route checks the path, query, headers and body shape first, then resolves the tenant slug through the caller's membership and the repository name inside the same transaction that authorizes the operation, so a foreign tenant or repository answers exactly like a missing one. `repo` is percent-decoded (`repo=Acme%2Fapp`). A reused `Idempotency-Key` with a different request is `idempotency_mismatch` (422), distinct from a stale `If-Match` (`conflict`, 409). The retry record stores a keyed MAC of the request under a subkey of the master key, never a digest that could be recomputed from the database.

Audited as `worker-uninstall-requested` (and `worker-uninstalled` when it settles) |

## Short-lived download links

`POST /runs/{id}/artifacts/{arf}/link` mints a URL that anyone holding it can redeem — `GET /dl/{token}`, deliberately
outside `/api/v1` and needing no credential — for at most an hour. It exists so an interface or a chat message can hand
a browser a working download without a session or a credential file: the token is the authority.

The token is self-contained, so redemption costs one keyed BLAKE3 MAC and one artifact lookup, with no server-side
record created or consumed. Its payload is the version, the target kind, the owning tenant, the artifact id, the expiry
in wall-clock milliseconds and the key epoch; an entry link adds the entry's path before the tag. A **5-minute** life is
the default, `expires_secs` sets 1–3600, and a token is valid while the clock reads *before* `expires_ms`, so the expiry
millisecond itself is refused. Minting requires `artifacts:read` and the same repository `read` the archive route
requires, and it checks what redemption will check again — a captured artifact inside its retention and, for an entry
link, the path being in the manifest — so a link that could never work is never handed out. The MAC uses a subkey
derived from the sealed master key's **active** key, and the epoch names that key, so `sentinel admin key rotate` retires
every link minted before it: an old-epoch token is dead the moment the controller reloads the key ([secrets](secrets.md)).
Redemption re-checks the artifact's retention deadline and the owning tenant's active state at request time, because
the minting session's authority is not re-checked — the short life is what bounds that gap.

Every refusal is the same `not_found`, byte for byte: a forged or truncated tag, a token past its expiry, one from
another epoch or another key, an artifact of another tenant (a token's tenant is inside the tag, so a token cannot be
edited into one), an artifact whose retention passed, and one of a suspended tenant. So the route cannot be used to
probe for artifacts, tenants or epochs. A token is a bearer capability for its short life and **may be redeemed more
than once** inside it; nothing consumes it, and nothing can, without server-side state that would cost a write per
download. Treat minting like sharing the bytes: the life is the exposure.

`sentinel artifact link` and the MCP `get_artifact_link` tool mint through this same route, so a URL handed to a chat
message, a terminal or a model carries exactly the authority a reader has at minting time and nothing afterwards.

Redemption is logged once per attempt, accepted or refused, as the access-log event `download_link` with a 16-hex
**digest** of the token (`token_digest`), the target kind and the outcome. The token text never enters a log line, an
error body or the database. Because a link is a bearer capability, anything that records full request URLs (a reverse
proxy's access log, browser history) records the token itself; that is the operator's log, not Sentinel's, and
`public_url` is the only host a minted URL names.

## The CLI

```sh
export SENTINEL_SERVER=http://127.0.0.1:7080
sentinel api --token-file ~/.sentinel/token me
sentinel api --token-file ~/.sentinel/token run --tenant acme --repo app \
    --pipeline .sentinel.yml --source https://github.com/acme/app.git --sha <full sha> --ref main --idempotency-key push-1
sentinel api --token-file ~/.sentinel/token status run_…
sentinel api --token-file ~/.sentinel/token logs att_… --follow
sentinel api --token-file ~/.sentinel/token cancel --run run_…
sentinel api --token-file ~/.sentinel/token rerun job_…
sentinel api --token-file ~/.sentinel/token workers --tenant acme --json
sentinel api --token-file ~/.sentinel/token queue --tenant acme --limit 50
sentinel api --token-file ~/.sentinel/token drain wrk_…
sentinel api --token-file ~/.sentinel/token undrain wrk_…
```

`--json` prints the server's document, and a failure as one `sentinel.error/1` line on stderr; text output is for people. `--token-file`/`--token`/`SENTINEL_TOKEN` accept an `sntl_` credential or an `sntl_at_` access token. Exit codes are the shared table in [CLI](cli.md#exit-codes): 0 success, 1 remote fault or malformed answer, 2 usage, 3 `unauthenticated`/`forbidden`, 4 `not_found`, 5 `conflict`/`idempotency_mismatch`, 6 busy or unreachable after retries. `--token-file` keeps the secret out of the process list; `--token` and `SENTINEL_TOKEN` exist for tooling that already protects its environment.

Draining needs a platform-admin credential on the API; on the controller's own host the same change is `sentinel admin worker drain --id wrk_… --data-dir …` (and `undrain`), which acts on the store directly like the rest of `sentinel admin`.

## The web interface

The controller serves no page of its own besides the OAuth consent and device pages: `GET /` is `not_found`. The web interface is `sentinel-web` ([web interface](web-ui.md)), a client of these routes.

## Client keys behind a reverse proxy

The per-client rate limits on the unauthenticated routes, the sign-in lockout pair `(client, account)` and the public-body slot all use one **client key**:

| Peer | Key |
|---|---|
| Not in `trusted_proxies` | its own address (an IPv6 /64 counts as one); every header is ignored |
| In `trusted_proxies` (loopback when the key is absent), `X-Forwarded-For` ends in a valid address | that last address; a proxy appends the real peer, so the entry before it is whatever the client wrote and is never read |
| In `trusted_proxies`, no `X-Forwarded-For` or a last entry that is not an address | the proxy's **connection**: its address and source port |

The last row is the dependency on the proxy. A proxy that does not send `X-Forwarded-For` used to give every client behind it one key: one guesser exhausted the allowance of all, and five wrong passwords for an account from the shared key locked that account out for the owner. Now each upstream connection is a client of its own, so a guesser throttles and locks out the connections it uses, not the people behind other ones. That is the finest identity the controller has without the header, and it is weaker than a real client address: a client that reaches the controller through a new upstream connection for every request (a proxy without keep-alive) gets a fresh key each time. The following still bound it, and none depends on the header: the global ceiling of every budget, the 8 handler and 4 public-body slots, the 10 s body deadline, and the account-wide lock, which locks the account for everybody after four times the per-client failures (`ACCOUNT_LOCK_FACTOR`) whatever address they come from. Unauthenticated per-client limits, the lockout and the per-client body slot are therefore only fully effective when the proxy overwrites or appends `X-Forwarded-For` with the address it saw, as the web interface does with `SENTINEL_CLIENT_IP_HEADER` ([web interface](web-ui.md#client-addresses)). A proxy must be listed in `trusted_proxies` for its header to be read, and nothing else may reach the API port: a client that reaches it from a trusted address could name any client.

Quotas that reconnecting must not mint are still keyed on the proxy's address alone, so everything behind a proxy that names no client shares them: the dynamic client registrations per registrant ([OAuth](oauth.md)). A trusted-proxy peer is exempt from the per-peer connection cap, which is why a proxy that names no client is not capped per connection.

## Mail limits

Every message the controller queues (an address verification, an email invitation, or a storage threshold notice) is bounded per **recipient address**, whoever asked for it, on top of the per-account and per-client limits: at most **5 messages to one address per hour** and **at least 60 seconds between two messages of the same kind** to it. A request refused by this allowance sends nothing and leaves the link already mailed valid (the link is minted only when the message can be queued). The bounds are shared by every requester, so they cap the mail a stranger can make the deployment send to a victim, but they also mean a stranger can spend a victim's allowance: while it is spent, the holder's own resend waits (at most until the oldest message leaves the hour; `POST /me/email/resend` answers `429`, every unauthenticated or address-taking route still answers `202`), and an operator can still mint a link on the host with `sentinel admin account email-link` ([admission](admission.md#email-identity-and-email-invitations)). An invitation is not delayed by a verification message, or the reverse, and a storage threshold notice is a third kind of its own; all three count toward the hourly 5. Delivered messages keep counting for seven days of outbox retention, so delivery does not reset the allowance. Email-registered accounts that never verify their address are retired after seven days ([admission](admission.md#email-identity-and-email-invitations)).

## Body limits

A body longer than its limit is `413 payload_too_large` (`details.limit_bytes`; the OAuth endpoints answer `413 invalid_request` in their own error shape). A declared `Content-Length` over the limit is refused from the request head alone; a body without a length is cut off while it is read, one byte past the limit.

| Route class | Limit | Source |
|---|---|---|
| authenticated JSON (`/api/v1`, the default) | 1 MiB | `MAX_API_BODY_BYTES` in `sentinel-protocol` (a pipeline file inside it is at most 256 KiB, `MAX_PIPELINE_FILE_BYTES`) |
| `PUT /uploads/{upl}` chunk | 8 MiB | `MAX_UPLOAD_CHUNK` |
| secrets: value / import | 64 KiB / 1 MiB | [secrets](secrets.md) |
| `POST /login` | 16 KiB | `MAX_LOGIN_BODY_BYTES` |
| `POST /setup` and the email routes, public and signed-in (`/me/email`, `/invitations/accept`, a tenant's invitations) | 8 KiB | `MAX_BODY_BYTES` in `routes/setup.rs` and `routes/email.rs` |
| account security routes | 4 KiB | `MAX_BODY_BYTES` in `routes/account.rs` |
| GitHub App routes | 4 KiB | `MAX_BODY_BYTES` in `github_app.rs` |
| `POST /worker-enrollments/redeem` | 2 KiB | `MAX_REDEEM_BODY_BYTES` ([worker enrollment](worker-enrollment.md)) |
| `POST /hooks/github` | 4 MiB | `MAX_WEBHOOK_BODY_BYTES` |
| `POST /intake/{repo}` | 64 KiB | `MAX_HOOK_BODY_BYTES` |
| `POST /mcp` message | 2 MiB | `mcp::MAX_MESSAGE_BYTES` (larger than the API limit; MCP responses are capped separately at 8 MiB, [MCP](mcp.md)) |
| `/oauth/*` forms and the device page | 8 KiB | `MAX_OAUTH_FORM_BYTES` (the consent form answers `413 invalid_request` in the OAuth error shape, or `503 temporarily_unavailable` when no body slot frees up; the signed-in device page answers `413` as an HTML page; any other unreadable form is `400`) |
| `POST /oauth/register` | 16 KiB | [OAuth](oauth.md) |

The unauthenticated classes read their body through the public body slots below. `every_route_class_enforces_its_own_body_limit` (`crates/sentinel-api/tests/api.rs`) sends one byte over and exactly the limit to the API, upload, login, setup, GitHub webhook, intake, MCP, OAuth token and consent routes, the signed-in device page, the account security, signed-in email and invitation routes and the GitHub App routes, and a chunked login body and a chunked device-page form over the limit (the enrollment redeem route has its own test in `worker_enrollment.rs`; `oauth_code.rs` `an_open_registration_cuts_an_oversized_body_off_at_16_kib` covers `POST /oauth/register`).

## Unauthenticated bodies

A handler permit is never held while a client with no credential yet sends its body. The login, the sign-up, setup and public email routes, both webhooks (`/hooks/github`, the generic hook) and the OAuth forms and registration read their whole body first: if it is not already in the connection's buffer, the handler permit is given back, the read waits for one of 4 body slots (`sentinel_api::PUBLIC_BODIES`) and must finish within 10 seconds, slot wait included (`rate_limited`, or `503 temporarily_unavailable` on the OAuth routes, when no slot frees up in time), and only then is a handler permit taken again. Each client (the admission key: peer address, or the `X-Forwarded-For` address behind a trusted proxy, or the proxy's connection when it names none; [client keys](#client-keys-behind-a-reverse-proxy)) may hold only one of those slots at a time, and a second body from the same client is turned away at once, so one host cannot fill the pool and block other people's sign-in or webhook delivery. A client that trickles a body therefore delays only its own other unauthenticated bodies, and never a run read, a token refresh, a health check or another client's sign-in. A trusted-proxy peer is exempt from the per-peer connection cap, so the clients it forwards are bounded in the slots instead: together they may hold at most 3 of the 4 (`sentinel_api::PROXY_BODIES`), each for at most 5 seconds, slot wait included (`sentinel_api::PROXY_BODY_TIME`), and one slot is left to direct clients however many addresses the proxy names; a forwarded reader that finds its share spent waits for it within those 5 seconds and is then turned away (`rate_limited`, or `503` on the OAuth routes). Many distinct forwarded addresses can still take the 3 for five seconds each; that is bounded by the admission budgets, not by this pool. Authenticated routes keep the 120 s body deadline: their sender has already presented a credential. Bodies are also bounded in size (login 16 KiB, OAuth forms and registration by their own limits, webhooks by the intake limits), and `Content-Length` and chunk sizes are plain digits (decimal or hexadecimal); a sign or any other character is `400`.

## Live updates and long polls

`GET /runs/{id}/wait` and `GET /attempts/{id}/logs?wait=1` are the live paths every client uses — the CLI's `wait` and `--follow`, MCP, and the web interface's event streams. A parked poll:

- takes one of 32 subscriber slots (8 per user), holds its connection, and gives its handler permit back while it waits, so parked polls never starve requests doing work (`sentinel_api::SUBSCRIBERS`, `SUBSCRIBERS_PER_USER`, `RESERVED_HANDLERS`);
- re-authorizes whenever the tenant's authorization epoch moves (a membership, role or grant change, a suspension) and then answers what a fresh request would (`not_found`), rather than keep serving a reader who lost access until its deadline;
- ends as soon as its client hangs up (a non-blocking `peek` every 250 ms), giving the slot back, so a closed tab or an aborted upstream request never holds a slot to the 25 s deadline.
