# Failure drills

Each failure Sentinel is meant to survive, what Sentinel does about it, and the test that shows it. All of them run with the regular suites on the verification VPS ([development](development.md#where-tests-run)).

| Failure | What happens | Shown by |
|---|---|---|
| **Sustained disk pressure** | Admission closes below the low watermark and reopens only above the high one. A write is admitted or refused `StorageFull`, nothing else. Charges of refused, abandoned and committed writes all come back, and no staging file is left behind | `sentinel-store/tests/storage.rs` `admission_flapping_under_sustained_writes_leaks_nothing`: eight writers for about ten seconds while free space swings across the marks eight times. Also the hysteresis, reserve and log-floor tests in the same file, and `faults.rs` for logs under closed admission |
| **Interrupted backup** | A backup is staged in `.<id>.partial` and renamed only after `backup.json` is durable, so a kill never leaves something listed as a backup. The next backup removes every staging directory left behind (`partials_removed`), and pruning removes half-copied `.part` objects no kept backup names | `sentinel-store/tests/backup.rs` `an_interrupted_backup_leaves_nothing_the_next_one_does_not_clean` (the leftovers, planted) and `backups_killed_at_staggered_points_leave_only_complete_ones` (a child process taking backups in a loop is SIGKILLed six times at 120 ms to 1.6 s; every listed backup verifies after each kill, then the next backup, a prune and a restore succeed) |
| **Interrupted or failed restore** | The database lands last, so a restore that stops (a rotten or missing object in the backup, a bad config file, a bad key file) leaves a directory without one, never something a controller would open. Run it again once the cause is fixed, or give `--id` of an earlier backup | `backup.rs` `a_failed_restore_leaves_no_database_and_a_retry_succeeds`, `a_restore_refuses_a_bad_key_file_and_a_leftover_journal_before_writing_anything`, `rot_in_a_backed_up_controller_identity_is_caught_and_refused` |
| **Interrupted garbage collection** | Reclamation deletes only after its commit and spares bytes re-staged meanwhile. A commit rolled back after the file moved leaves an orphan that the sweep collects after its grace period | `sentinel-store/tests/faults.rs` (rolled-back commits, reclaim unlink races), `storage.rs` `orphan_sweep_removes_only_unowned_files_past_the_grace`, `a_seal_recovers_the_renamed_but_uncommitted_upload`; a file left by an eviction that stopped between its mark and its unlink is removed by startup recovery (`replicate.rs` `a_file_left_behind_by_an_interrupted_eviction_is_collected_at_startup`) |
| **Corrupt or missing objects** | Artifact downloads never serve a rotten object whole. `admin objects verify` and recovery name corrupt and missing objects. A backup records a missing object (`objects_missing`) or a corrupt one (`objects_corrupt`) and carries on; its restore skips what the backup recorded as lost and brings the rest back, with recovery naming the loss. The replicator hashes local bytes before sending, so a rotten or missing local copy is never uploaded under its digest; it is parked and counted once (`local_faults`), is not read again until a growing delay has passed, and never holds back the objects after it. A corrupt remote copy is refused on read-through | `backup.rs` (`verification_catches_rot_and_loss`, `a_restore_goes_on_without_the_objects_the_backup_recorded_as_lost`, `a_damaged_backup_directory_fails_verification_instead_of_crashing_it`, the interrupted-backup test), `replicate.rs` `a_damaged_or_lost_local_object_is_skipped_and_holds_nothing_back`, `a_wall_of_damaged_objects_older_than_a_healthy_one_does_not_stop_replication`, `a_parked_object_is_tried_again_after_its_delay_and_released_once_repaired`, `a_large_object_that_changes_while_it_is_uploaded_is_never_completed`, `objects_are_copied_verified_evicted_and_fetched_back_verified`, `sentinel-api/tests/api.rs` (rotten artifact), `objects.rs` recovery |
| **S3 outage** | The external copy degrades and the backlog grows. Past its budget, admission closes and placement pauses; draining reopens both. Reading an evicted object during the outage fails cleanly with nothing placed locally, and succeeds once the bucket is back | `replicate.rs` `an_outage_fills_the_backlog_closes_admission_and_draining_reopens_it`, `an_evicted_object_is_unreadable_during_an_outage_and_readable_after`; one refused item does not stop the queue (`one_delete_the_bucket_refuses_for_good_does_not_stop_the_queue`, `one_object_the_bucket_refuses_for_good_does_not_stop_the_queue`, `a_refusal_with_no_success_beside_it_is_the_credential_and_nothing_stays_parked`); under disk pressure only replicated objects are evicted, until the disk has room (`disk_pressure_evicts_only_replicated_objects_and_stops_when_the_disk_has_room`, `a_full_backlog_does_not_evict_for_pressure`); `sentinel/tests/s3_offload.rs` against real endpoints. A backup and a restore onto a second directory taken while the credential is refused and then while the endpoint is down keep every local object, record the evicted ones as remote-only, refuse their reads cleanly and place nothing, and read them back once the bucket answers: `replicate.rs` `a_backup_and_restore_during_an_s3_failure_keep_local_objects_and_fetch_evicted_ones_later` |
| **Expired credentials** | An S3 credential that expired or was revoked (403) degrades the external copy with the reason (`last_error`); nothing uploads and nothing is evicted. The first pass after the credential is replaced catches up. Expired API tokens, sessions, OAuth tokens and worker enrolments are refused, and an expired GitHub installation token is replaced | `replicate.rs` `a_refused_credential_degrades_the_copy_until_it_is_replaced`; `tokens.rs`, `local_auth.rs`, `oauth_tokens.rs`, `sentinel-checks/tests/delivery.rs`, `sentinel-link/tests/link.rs` |
| **Schema upgrade interrupted** | Each migration is one transaction. A process killed mid-migration leaves the database at the last committed version, intact, and the next start migrates it. The pre-migration copy is written under `.vNNN.partial` and renamed once durable, so a copy cut short is never listed as a snapshot and is taken again | `sentinel-store/tests/upgrade.rs` `a_process_killed_mid_migration_leaves_the_last_committed_version` (a child process aborts inside the migration's transaction), `a_failed_migration_stays_at_its_last_good_version_and_names_the_rollback` |
| **Recovery onto a replacement host** | The backup carries the controller's link identity (`controller.crt`, `controller.key`). A controller restored into a fresh data directory and started on the address workers dial presents the same fingerprint. The enrolled worker keeps its pin and reconnects as itself, without re-enrolling | `sentinel/tests/cli.rs` `a_worker_reconnects_to_a_controller_restored_onto_a_new_host` (real `sentinel server` and `sentinel worker` processes: backup, the old data directory deleted, restore, restart on the same link address), `a_backup_taken_online_restores_onto_a_new_data_directory_that_serves` |

A restored controller's workers reconcile what they held against it, as after any controller restart ([reconciliation](reconciliation.md)). Work written after the backup is lost from the database, and its files remain as orphans the storage pass collects ([backup](backup.md)).

## Fault scenarios

`bench/b09-harness.py` drives the reliability side of B09 on a real controller and real worker processes: slow and full disks (loop-mounted images, slow ones behind `dm-delay`), shaped links (`tc netem` on the harness's own veth pairs; the real Tailcat relay scenario is recorded as `blocked`), a partition and restarts of the harness's own processes by PID, and a noisy tenant beside a quiet one. Each reliability record carries its checks and their observed values. The faults are confined to b09-named loop devices, namespaces and veth pairs, which the `cleanup` command removes. With `--fleet` (workers on real hosts, [benchmarking](benchmarking.md#b09-reliability-and-performance-scenarios-and-the-regression-gate)) only the performance scenarios run: these faults are never applied to a worker host, and the only things the harness starts or removes there are its own worker processes and `b09-` directories. The performance side and its regression gate (`bench/b09-gate.py`, 10% p95 overhead, noise from the spread between repeats) are in [benchmarking](benchmarking.md#b09-reliability-and-performance-scenarios-and-the-regression-gate). No B09 result is committed yet; until one is, these scenarios are a harness, not evidence.

## What is not covered

- A power cut during a backup's snapshot is covered only by the rename protocol; no `dm-flakey` run has been done against it (the log path has had one, see [storage](storage.md)).
- A same-length bit flip in a backup's shared object store is replaced by the next backup (it rehashes a reused copy) and refused by a restore, but between those two it survives until someone runs `admin backup verify`. Verify on a schedule.
- The kill drills use SIGKILL of a process, which drops its unflushed state but not the page cache; they do not show what a power cut that loses cached writes does. The backup's fsyncs and rename order are what that rests on.
- Garbage collection and the storage sweep are shown interrupted by rolled-back commits and unlink races, not by a killed process; a killed one only leaves what the sweep already collects.
- No drill has restored a 100 GiB deployment. The 16.75 GiB drill, run under idle I/O priority on a shared host, extrapolates to 18 minutes against a 15-minute objective, so the recovery-time objective at that size is unconfirmed ([backup](backup.md#recovery-objectives)).
