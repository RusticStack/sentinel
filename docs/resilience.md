# Failure drills (R07)

Each failure Part 13 promises to survive, what Sentinel does about it, and the test that shows it. All of them run with the regular suites on the verification VPS ([development](development.md#where-tests-run)).

| Failure | What happens | Shown by |
|---|---|---|
| **Sustained disk pressure** | Admission closes below the low watermark and reopens only above the high one. A write is admitted or refused `StorageFull`, nothing else. Charges of refused, abandoned and committed writes all come back, and no staging file is left behind | `sentinel-store/tests/storage.rs` `admission_flapping_under_sustained_writes_leaks_nothing`: eight writers for about ten seconds while free space swings across the marks eight times. Also the hysteresis, reserve and log-floor tests in the same file, and `faults.rs` for logs under closed admission |
| **Interrupted backup** | A backup is staged in `.<id>.partial` and renamed only after `backup.json` is durable, so a kill never leaves something listed as a backup. The next backup removes every staging directory left behind (`partials_removed`), and pruning removes half-copied `.part` objects no kept backup names | `sentinel-store/tests/backup.rs` `an_interrupted_backup_leaves_nothing_the_next_one_does_not_clean` |
| **Interrupted garbage collection** | Reclamation deletes only after its commit and spares bytes re-staged meanwhile. A commit rolled back after the file moved leaves an orphan that the sweep collects after its grace period | `sentinel-store/tests/faults.rs` (rolled-back commits, reclaim unlink races), `storage.rs` `orphan_sweep_removes_only_unowned_files_past_the_grace`, `a_seal_recovers_the_renamed_but_uncommitted_upload` |
| **Corrupt or missing objects** | Artifact downloads never serve a rotten object whole. `admin objects verify` and recovery name corrupt and missing objects. A backup records a missing object (`objects_missing`) or a corrupt one (`objects_corrupt`) and carries on. The replicator hashes local bytes before sending, so a rotten or missing local copy is never uploaded under its digest; it is skipped and counted (`local_faults`) without holding back the objects after it. A corrupt remote copy is refused on read-through | `backup.rs` (`verification_catches_rot_and_loss`, the interrupted-backup test), `replicate.rs` `a_damaged_or_lost_local_object_is_skipped_and_holds_nothing_back`, `objects_are_copied_verified_evicted_and_fetched_back_verified`, `sentinel-api/tests/api.rs` (rotten artifact), `objects.rs` recovery |
| **S3 outage** | The external copy degrades and the backlog grows. Past its budget, admission closes and placement pauses; draining reopens both. Reading an evicted object during the outage fails cleanly with nothing placed locally, and succeeds once the bucket is back | `replicate.rs` `an_outage_fills_the_backlog_closes_admission_and_draining_reopens_it`, `an_evicted_object_is_unreadable_during_an_outage_and_readable_after`; `sentinel/tests/s3_offload.rs` against real endpoints |
| **Expired credentials** | An S3 credential that expired or was revoked (403) degrades the external copy with the reason (`last_error`); nothing uploads and nothing is evicted. The first pass after the credential is replaced catches up. Expired API tokens, sessions, OAuth tokens and worker enrolments are refused, and an expired GitHub installation token is replaced | `replicate.rs` `a_refused_credential_degrades_the_copy_until_it_is_replaced`; `tokens.rs`, `local_auth.rs`, `oauth_tokens.rs`, `sentinel-checks/tests/delivery.rs`, `sentinel-link/tests/link.rs` |
| **Schema upgrade interrupted** | Each migration is one transaction. A process killed mid-migration leaves the database at the last committed version, intact, and the next start migrates it. The pre-migration copy is written under `.vNNN.partial` and renamed once durable, so a copy cut short is never listed as a snapshot and is taken again | `sentinel-store/tests/upgrade.rs` `a_process_killed_mid_migration_leaves_the_last_committed_version` (a child process aborts inside the migration's transaction), `a_failed_migration_stays_at_its_last_good_version_and_names_the_rollback` |
| **Recovery onto a replacement host** | The backup carries the controller's link identity (`controller.crt`, `controller.key`). A controller restored into a fresh data directory and started on the address workers dial presents the same fingerprint. The enrolled worker keeps its pin and reconnects as itself, without re-enrolling | `sentinel/tests/cli.rs` `a_worker_reconnects_to_a_controller_restored_onto_a_new_host` (real `sentinel server` and `sentinel worker` processes: backup, the old data directory deleted, restore, restart on the same link address), `a_backup_taken_online_restores_onto_a_new_data_directory_that_serves` |

A restored controller's workers reconcile what they held against it, as after any controller restart ([reconciliation](reconciliation.md)). Work written after the backup is lost from the database, and its files remain as orphans the storage pass collects ([backup](backup.md)).

## What is not covered

- A power cut during a backup's snapshot is covered only by the rename protocol; no `dm-flakey` run has been done against it (the log path has had one, see [storage](storage.md)).
- A same-length bit flip in a backup's shared object store survives until someone runs `admin backup verify`. Later backups trust an object whose length matches, so they don't reread every object on each run. Verify on a schedule.
