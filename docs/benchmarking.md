# Benchmarking

`sentinel-bench` is a Linux-first benchmark runner in [`crates/sentinel-bench`](../crates/sentinel-bench). It runs one fixed workload repeatedly, measures each run with the monotonic clock, and writes **one JSON line per benchmark run**. It is a development tool, not part of the server/worker binaries.

## Workloads and runtimes

| Workload | Command | Purpose |
|---|---|---|
| `noop` | `true` (`cmd /c exit 0` on Windows) | Reproducible floor: process spawn, container start and teardown with no user work |
| `nonzero-exit` | `sh -c 'exit 3'` | Verifies the runner refuses to record a failed workload |

| Runtime | Measured process | Notes |
|---|---|---|
| `direct` | The workload itself | Host process-spawn floor |
| `podman` | `podman run --rm [--cpus N] [--memory M] <image> <workload>` | Rootless container floor; resource usage is that of the **podman client process**, not the container |

Run from the repository root with the release profile:

```sh
cargo bench-noop --runtime direct --warm-state warm --label <host-id>
cargo bench-noop --runtime podman --image docker.io/library/busybox@sha256:<digest> --warm-state warm --label <host-id> --output bench.jsonl
```

`--warm-state` is required and operator-declared; the runner cannot detect cache state and records how much it could establish (`warm_state_basis`, below). `--warmup` runs are executed but not recorded (default 2); `--samples` defaults to 20. Any non-zero or signalled exit aborts the run with exit status 1 and writes nothing. Always reference images by digest so the record is reproducible.

## Record format (`sentinel-bench/1`)

Top-level fields: `schema`, `bench_version`, `started_at_unix_ms` (wall-clock provenance only), `label`, `workload`, `runtime`, `warm_state`, `argv`, `limits {cpus, memory}`, `source {git_commit, git_dirty}`, `build {commit, dirty, profile, target, debug_assertions, binary_blake3}`, `tools {rustc, podman}`, `host`, `image {reference, digest, id}`, `warm_state_basis`, `interleave {runtimes, order, conditions}` (only for a group), `conditions`, `warmup`, `samples[]`, `summary`.

`host` records hostname, OS, kernel, CPU model, online CPUs, total memory, working directory and its filesystem/mount point, cgroup v2 controllers and user. `source` and `build` name the build, not the checkout: `build.rs` records the commit, the tracked-change state, the profile and the target when the runner is compiled (Cargo reruns the script when `HEAD`, the branch, the index, a source file of any crate under `crates/`, the workspace `Cargo.toml`, `Cargo.lock` or `.cargo/config.toml` change; an edit outside those, such as an environment variable that alters the compile, is not tracked), so a checkout moved to another commit afterwards, or a binary copied to a host without the checkout, still names the commit it was built from, and starting it costs no `git` process. `build.dirty` is true when a tracked file differed from the commit at build time; `build.profile` is Cargo's `PROFILE`; `build.debug_assertions` says whether debug assertions were on, and a `--contract` run refuses such a build, because a debug binary is not a baseline (`cargo bench-noop` builds with `--release`); `build.binary_blake3` is the BLAKE3 of the running executable, hashed once before the first sample (the scripts hash with SHA-256; the runner has no SHA-256 implementation and adds no dependency for one). `source` carries the same commit and dirty state; only a runner built outside a git checkout asks `git -C <the checkout it was built from>` when it starts, and then it refuses to measure or write anything when the commit cannot be read (for example a checkout owned by another user without `safe.directory`). A build-time value git could not give is absent from `build`, never a default. The host label stays optional in the runner (`SENTINEL_BENCH_HOST_LABEL` unset leaves `host.hostname` absent, so local dry runs work); the scripts below refuse to start without it. `tools.rustc` is the compiler that built the runner, captured at build time (Cargo rebuilds the runner when the toolchain changes), so it does not depend on `rustc` being on the runner user's `PATH`; `tools.podman` is read from `PATH` at run time for the Podman runtime. An absent value means the tool was unavailable, never a default.

Each sample has `index`, `elapsed_ns` (monotonic, spawn to reaped), `exit_code`, and on Unix the `wait4` usage of the direct child: `user_cpu_ns`, `system_cpu_ns`, `max_rss_kib`, `block_in`, `block_out`. Unmeasured fields are omitted. `summary` holds `count`, `min_ns`, `median_ns`, `p95_ns` (nearest-rank), `max_ns` and the spread: `mean_ns`, `stddev_ns` (sample, n - 1; absent for one sample) and `mad_ns` (median absolute deviation from the median, which one slow outlier cannot move). With fewer than 20 samples the nearest-rank p95 is the largest sample, so `summary` carries `"p95_is_max": true` and the p95 describes one run, not a tail; report such a record's median and spread, not its p95. Samples are sequential, single-observer measurements; do not add them to any other phase.

**Conditions.** `conditions` is read from the kernel around the measured window (before the first warm-up run and after the last sample): CPU pressure (`some`, avg10 and avg60) at the start and at the end, hypervisor steal time over the window in nanoseconds (`/proc/stat`), and cpu0's `scaling_governor`. A field the kernel does not expose (a VM often has no cpufreq; pressure needs PSI) is absent, never zero. A contract run refuses a start at or over 5 % pressure; the end values say whether the host got busy during the run, which a start check cannot. A run whose end pressure or steal is high is not a baseline, even though it was recorded.

In an interleaved group (below) the runtimes alternate, so one window around the group would charge each of them with the others' load. Each run of the group is probed on its own instead, and a record's `conditions` cover only that runtime's runs (its warm-ups and samples): the stall and steal fields are the sum of the deltas seen while that runtime's runs executed, `*_start` is read just before its first run and `*_end` just after its last, and a counter the kernel did not expose for some run is absent from the whole sum rather than a partial total. The counters are host-wide, so they say what the host was doing during that runtime's runs, not what the runtime caused. The group names this in `interleave.conditions` (`per-runtime`); a group record without that field was taken before it existed and holds one block shared by every runtime of its group.

**Warm state.** `--warm-state` stays operator-declared, and `warm_state_basis` says how much of it the runner could establish: `contract-prepare` (a cold contract condition: the contract's own per-run preparation resets the state, which the runner executes before every run, but does not observe), `warmup-run` (declared warm, and at least one identical unmeasured run completed before the first sample), or `unverified` (everything else: a cold declaration outside a contract, or warm with `--warmup 0`). A warm Podman run whose image is not present locally is refused, since the first sample would pull. Treat `unverified` records as indicative.

**Interleaved comparison.** `--interleave <runtime>` (repeatable) measures the extra runtimes in the same invocation, alternating with `--runtime` sample by sample in ABBA order: the order reverses every sample (A B, B A, A B, ...), so drift in host load, page cache or frequency lands on every runtime alike instead of on whichever ran last. Each runtime gets its own record, all naming the group in `interleave {runtimes, order, conditions}`, and each sample carries `seq`, its position in the whole sequence (with `--runtime direct --interleave scoped`, direct holds seq 0, 3, 4, 7, ... and scoped 1, 2, 5, 6, ...). Compare the runtimes of one group, not records taken in separate invocations at different times; the F05 and B01 comparisons ran back to back as separate invocations and are not interleaved.

**Script records.** Records written by the benchmark scripts rather than the runner (`b02-sentinel.sh`, `b03-latency.py`) carry a `build {commit, dirty, binary_sha256}` and a `host` block too, taken from the checkout named by `SENTINEL_SRC` / `--source`. A script refuses to start, before its first sample, without it: the commit and the tracked-change state must be readable (an unreadable state is not recorded as `null`), and `SENTINEL_BENCH_HOST_LABEL` must be an anonymized label (lower-case letters, digits and hyphens, no address). That rule lives in one place, `bench/benchstamp.py` (which `bench/stamp.sh`, `b03-latency.py`, `b09-harness.py`, `q13-fleet.py` and `microvm/m02_boot.py` use, and `b02-sentinel.sh` and `p14-pilot.sh` call before measuring), and the hygiene test imports its label pattern. Older B02, B03 and B04 records carry neither and are not back-filled.

**Naming the build.** A caller passes the build once: `bench/run-stamped.sh CHECKOUT BINARY b03 ROOT OUT` exports `SENTINEL_SRC` (the checkout the binary was built from) and `SENTINEL_BIN` (hashed into the record) and starts the harness; `bench/stamp.sh` run directly prints the stamp object. `sentinel-bench` stamps itself from the checkout it was built in. `b02-sentinel.sh`, `b03-latency.py`, `p14-pilot.sh`, `b09-harness.py`, `q13-fleet.py` (real runs; its simulated records carry no stamp on purpose), `microvm/m02_boot.py`, `k02-cache-clone.sh`, `f07-storage.sh` and the B05 scripts (`b05-cache.sh`, `b05-workloads.sh`, `b05-timed.sh` and the `b05-cache` driver, which refuses to start without the stamp the scripts pass in `B05_STAMP`) refuse to write without it, and a failed clone mode in K02 or F07 still writes an error line that carries it; `c02-engines.sh`, `k07-recipes.sh`, `k09-before-after.sh` and `r06-idle.sh` stamp the same way (the K09 meta line keeps its own `host` block and gets the `build`). The GitHub-collected baselines (`b01a-github.py`, `b02-github-collect.py`) measure no Sentinel build and carry none.

**Dirty means tracked changes.** `git_dirty` / `dirty` is true only when a tracked file differs from `HEAD` (`git status --porcelain --untracked-files=no`); untracked files are ignored, because a scratch file does not change what was built. A new source file that is not yet added therefore does not make a build dirty: `git add` it, or commit, before measuring.

**Shuffle seed.** `k02-cache-clone.sh`, `f07-storage.sh` and `b03b-ack.py` shuffle the clone-mode order per round from a recorded seed: every record carries `shuffle_seed`, and a round's order is `shuf` seeded with `<shuffle_seed>/<fs>/<round>` (`bench/stamp.sh` `shuffle_lines`), so the order can be reproduced. `SHUF_SEED=…` replays a run; otherwise a fresh seed is made and printed. `position` still records the realised order. `b03b-ack.py` draws a fresh seed (or takes `--seed`), prints it, writes `shuffle_seed` into every record and `seq` (the position in the realised order) into every sample. Records taken before this carry no seed; the two committed `b03b-ack` records used a fixed seed of 7 and no `seq`. `python3 -m unittest bench/test_bench_hygiene.py` replays a seed, checks that an untracked file leaves `dirty` false and a tracked edit sets it, and checks that the stamp text survives being spliced into a record with `sed`.

## B09: reliability and performance scenarios, and the regression gate

`bench/b09-harness.py` runs the B09 scenarios (bursts, 1/3/10 workers, slow or full disks, shaped links (the real Tailcat relay scenario is recorded as blocked), partitions, restarts, a noisy tenant) on one verification host with every worker in its own process and network namespace, and appends `sentinel-bench/b09/1` records: one per repeat for performance scenarios (`kind: perf`, with a `summary.overhead_ns` distribution of at least 20 runs) and one per scenario for reliability scenarios. `bench/b09-git.py` is its Git fixture. Its header lists the faults it injects and how it removes them. No B09 result record is committed yet, so no B09 number is claimed anywhere in these documents.

**The gate.** `python3 bench/b09-gate.py BASELINE.jsonl CANDIDATE.jsonl` compares two such files and allows a 10% p95 overhead regression (`--max-regression`). Per scenario:

- The unit is one repeat's p95 overhead. A side's figure is the **median** of its repeats' p95s and its noise is the **spread** (max minus min) of those same p95s, so noise is measured between repeats and one slow run or one slow repeat decides nothing. A repeat whose p95 is the maximum of fewer than 20 runs, or with no passed run, is not counted.
- `pass`: the candidate median is within the baseline median plus 10%. `fail`: it is beyond that and the difference is larger than the larger of the two spreads. `inconclusive`: beyond 10% but inside the spread; take more repeats. `insufficient`: fewer than three usable repeats on either side (`--min-repeats`), or the scenario is missing from one file. `incomparable`: different workers, mode, runs, link, disk or job, or a baseline recorded with `--handicap-delay-ms`.
- Exit status: 1 for any `fail`, else 2 for any `insufficient` or `incomparable` or unreadable input, else 3 for any `inconclusive`, else 0. Only 0 is a pass; a missing or noisy result is never one.

**Sensitivity.** `--handicap-delay-ms N` on the harness adds N ms of delay each way to the link, recorded in the scenario as `injected_handicap`. `bench/test_b09_gate.py` encodes what that does to a run (overhead grows by 2N ms) and shows that, on a 100 ms baseline with a 4 ms spread, 6 ms each way fails the gate and 4 ms each way passes it. A real sensitivity run is the same candidate recorded twice on the same host, once with a handicap of the size the gate must resolve; it is part of the B09 result and has not been done. Run the unit tests with `python3 bench/test_b09_gate.py`.

**Fleet mode: workers on real hosts.** `run --fleet FLEET.json --scenarios fleet-w3-burst,...` keeps the controller and the Git fixture on the harness host and puts every worker on a host of the fleet file, so the 1/3/10-worker scenarios (`fleet-w{1,3,10}-{steady,burst}`) measure the control plane over real networks and real machines instead of namespaces on one host. Each identity is enrolled through the Q11 flow with its Q12 policy: the harness issues `sentinel admin worker enroll --pool shared --transport direct` with the host's ceilings (`--cpu-millis`, `--memory-bytes`, `--disk-bytes`) and priority, then runs `sentinel worker enroll --api-url ... --secret-stdin` on the host through its `exec` prefix, so the secret travels only on standard input and is kept in memory on the harness side. The identity then runs as a plain process (`nice`, `setsid`) from the host's `work_dir`. Ten workers are several identities per host, spread to the least loaded host first; a host that carries more than one identity must declare ceilings, and each identity is approved an equal share, so together they never exceed what the operator declared for that host. Without enough declared identities, or without ceilings on a shared host, the scenario is recorded `blocked` with the exact reason; nothing is invented. Before it starts, every used host must run the same `sentinel` binary as the kit (sha256 compared) or the scenario is `blocked`.

```json
{"controller": {"address": "192.0.2.10",
                "worker_bootstrap": {"release_url": "https://releases.example.com/sentinel/0.1.0", "release_sums": "/etc/sentinel/SHA256SUMS"}},
 "hosts": [{"label": "x86-a", "exec": ["ssh", "-F", "ssh-config", "host-a"], "sentinel": "/usr/local/bin/sentinel",
            "work_dir": "/var/tmp/b09", "api_url": "https://sentinel.example.com", "arch": "x86_64",
            "identities": 4, "priority": 0, "ceilings": {"cpu_millis": 4000, "memory_bytes": 8589934592, "disk_bytes": 42949672960}}]}
```

`controller.address` is the IP the hosts dial (the link, `listen`, and the Git fixture's certificate name); `worker_bootstrap` is passed into the harness controller's `[worker_bootstrap]` section, whose `api_url` is the hosts' `api_url` (all hosts must use the same one, and it must reach the harness controller's API on `127.0.0.1:47480`: a reverse proxy, or for a loopback `http://` URL a forward the operator keeps open). The `exec` prefix must run as the account that runs rootless Podman on that host. Records keep schema `sentinel-bench/b09/1`: the scenario carries a `fleet` shape (hosts, identities, per-identity ceilings, priority, architecture), so the gate compares fleet results only with fleet results of the same shape, and each repeat adds `fleet_hosts` (kernel, CPU model, CPU count, memory, binary digest), `conditions.hosts` (load and CPU pressure on every worker host at start and end; a repeat does not start until each is below the same 5% limit as the harness host), `runs_by_host` and `summary_by_host`, and every run carries the `host` label of the worker that ran its attempt. `--handicap-delay-ms` is refused in fleet mode (it shapes the harness host's veth links), and so is any other scenario: slow and full disks, partitions and restarts need namespaces and loop devices, which stay confined to the harness host.

**Cleanup.** Before anything starts on a host, a record with its `exec` prefix, working directory, configuration path and (once known) PID and worker id is written under `ROOT/fleet`. Exit, a signal, the end of each scenario and `cleanup --root ROOT` release every record from the record alone: the PID is signalled only while its command line still names that identity's own configuration file, containers labelled with its worker id are removed, and the `b09-` working directory is deleted (a record naming any other directory is refused). Nothing else on a worker host is touched. The controller's side of the identity disappears with the harness controller's data directory. `bench/test_b09_fleet.py` covers the fleet file, the identity plan, the ceiling split and this cleanup (on the verification host, with `env` as the exec prefix).

**Status.** The code and its unit tests exist; no fleet record is committed and no fleet number is claimed, because a run needs the worker hosts, a reachable `api_url` and a quiet window ([TODO.md B09-real-fleet-mode](../TODO.md)).

Limits: in the default mode the workers share one host, so the 3- and 10-worker scenarios measure control-plane fan-out and not the capacity of that many machines, and the 10% rule can only resolve what the repeat spread allows; a noisy host yields `inconclusive`, not a pass. Failure behavior under the same faults is in [failure drills](resilience.md#fault-scenarios).

**Stamp test and exceptions.** `bench/test_bench_hygiene.py` scans every `bench/*.jsonl`: each record must carry `build.commit` (not null) and a `host.hostname` that is an anonymized label (lower-case letters, digits and hyphens, no address). The files that predate the stamp are listed in the test as `LEGACY_UNSTAMPED`, each with its reason: the GitHub-collected and Woodpecker baselines and the legacy Go CI runs measured no Sentinel build, the dry-run files of the paired B11 harness have none, the older B01, B02, B03, B04, C02, F05, F07, K02, K07, K09, M02, Q09, R04, R06 and U01 records were taken before the stamp and are not back-filled, because a commit written after the fact would be invented, and six files record their source in a shape of their own and have no `build` or `host` block: `m01-detection.jsonl` (a short `commit` and a `host` label), `k07-recipes-microvm.jsonl` (neither), `u08-web-baseline.jsonl`, `u09-web-spikes.jsonl` and `u14-web-start.jsonl` (a short `code` hash and a `host_label`, written by `web/bench/web-bench.mjs` and its spike scripts) and `v01-release-profile.jsonl` (`measure-profile.sh`, a `source` block with `git_commit`). Their writers still emit those shapes; moving them to the common stamp changes the record shape and is not done here, and the existing lines stay as measured. The set is exact: a new file without a stamp fails, and a legacy file that becomes fully stamped must leave the list. No committed record has a null commit; a null commit is not an accepted exception. The same test lists the writers that stamp and checks that each still does.

**Benchmark lock.** There is one lock file per host for benchmarks and verification alike: `/var/tmp/sentinel-verify.lock`, or the path in `SENTINEL_VERIFY_LOCK`. `scripts/qualify/qualify.sh`, `b05-cache.sh`, `b05-workloads.sh`, `b09-harness.py`, `microvm/m02_boot.py` and `micro_contract.py` (so every [micro-contract bench](#micro-contract-benches)) take it; none uses a file under `/srv/sentinel`, which is the production tree. A script that runs a command under the lock uses `flock -x -o LOCK command` (`-o` closes the lock descriptor in the child), so a process the command starts and leaves behind cannot keep the lock after the script returns; the Python holders (`b09-harness.py`, `m02_boot.py`, `micro_contract.py`) take it with `fcntl.flock` on a descriptor Python opens non-inheritable, which has the same property, and a lock file the holder cannot open (for example one another account created read-only) is reported by name instead of as a traceback: a `blocked` record from `b09-harness.py`, a refusal with exit 3 from `micro_contract.py`, an exit with the lock path from `m02_boot.py`. The test fails any `flock` on a lock file or a command in `bench/` and `scripts/` (including one held in a shell variable) without `-o`, fails a lock path under `/srv/sentinel`, and checks with a real `flock` that an orphan the locked command leaves behind does not keep the lock; descriptor-form locks the shell owns (`flock 9`) are not command locks. The scripts that still do not take it (`p14-pilot.sh`, `b02-sentinel.sh`, `b03-latency.py`, and `f07-storage.sh` and `k02-cache-clone.sh` when run directly instead of through their contracts) must be started when nothing else holds the lock and the host reports low CPU pressure. A harness smoke run ([below](#harness-smoke)) never takes the lock, and reports itself pending when a measurement holds it. A host-side helper outside this repository that still takes the old `/srv/sentinel/runs/p14.lock` no longer serializes with these scripts; it has to move to the shared file.

## Log-ack batching

The controller acknowledges log frames per burst: each frame is written with `LogStore::append_deferred`, then one `LogStore::sync` (an `fdatasync` of the segment) precedes one `LogAck` ([logs](logs.md)). `crates/sentinel-store/examples/log-ack-bench.rs` measures what that saves, through the real `LogStore` on the file system named by `--dir`: for each burst size (default 1, 8, 64, 256 frames) it stores `--frames` frames (default 4096) of `--frame-bytes` bytes (default 256) into a fresh store, `--rounds` times (default 5), reversing the order of the burst sizes every round. A burst of 1 is an acknowledgement, and so a sync, per frame. Run it through `bench/log-ack.sh`, which adds the `build` and `host` stamp (`SENTINEL_SRC`, `SENTINEL_BIN`, the example binary built from that checkout) and appends the line to `bench/log-ack.jsonl`.

Record `sentinel-bench/log-ack/1`: `frames`, `frame_bytes`, `rounds`, `order` (the burst sizes in the order each round ran them) and `results[]`, one entry per burst size with `burst_frames`, `syncs_per_run`, `elapsed_ns` (one per round, monotonic), `median_elapsed_ns`, `min_elapsed_ns`, `max_elapsed_ns`, `median_ns_per_frame`, `frames_per_s_median` and `sync_ns {count, median, p95, p95_is_max, max}` over every sync of every round (`p95_is_max` is true when fewer than 20 syncs were pooled; the per-round `elapsed_ns` carries no percentile). The spread of the per-run figures is in `elapsed_ns`; the sync percentiles pool every sync call of every round. A record is a baseline only from a quiet host with the stamp's host block naming the filesystem under `--dir` (a smoke run on a shared host proves the harness, not the saving). **No record is committed yet**: the figure `docs/logs.md` calls unmeasured stays unmeasured until `bench/log-ack.jsonl` exists.

## Checks lane delivery latency

`crates/sentinel-checks/examples/checks-lane-bench.rs` measures how long a run's checks wait between being enqueued and reaching GitHub. It builds a real `Store` on the file system named by `--dir`, starts the real `Lane` with the real `GithubChecks` publisher, and points the publisher's App at a fake GitHub endpoint on loopback (installation lookup, token mint, repository lookup, check-run create and update, with the same answers `tests/delivery.rs` scripts). A sample records `burst` runs back to back (`runs::create_run`, the provenance row and `checks::record_run`, the writes a push makes) and waits for the endpoint to receive every queued check of every run (an aggregate plus one per job, so two per run). The clock starts when the write of that run begins and stops at the endpoint's receive time for the first check, and again for the last. Each (round, burst) gets a fresh store, endpoint and lane, and one unmeasured run goes first: its latency is reported as `cold_first_run_ns` (installation lookup and token mint) and not pooled with the steady state. Burst sizes default to 1 and 8, `--runs` (default 16) runs per sample, `--rounds` (default 5) rounds, the order of the burst sizes reversing every round (ABBA). `--github-ms` adds a fixed delay to every reply of the fake endpoint, `--idle-ms` overrides `Config::idle` (the lane's production default is used otherwise).

What it measures and what it does not: the Sentinel side of the path (the commit notifier waking the lane, the guarded read, signing the App JWT and minting the token once, the HTTP request, the guarded write-back), on loopback with an endpoint that answers at once. It says nothing of GitHub's own latency or rate limits, and a TLS handshake is not in it (the endpoint is plain HTTP, as in the tests). Run it through `bench/checks-lane.sh`, which adds the `build` and `host` stamp (`SENTINEL_SRC`, `SENTINEL_BIN`, the example built from that checkout) and appends the line to `bench/checks-lane.jsonl`.

Record `sentinel-bench/checks-lane/1`: `rounds`, `runs`, `checks_per_run`, `github_delay_ms`, `lane_idle_ms`, `order`, `p95_is_max` (true below 20 pooled runs) and `results[]`, one per burst size with `burst_runs`, `runs_per_round`, `cold_first_run_ns` (one per round), and `enqueue_to_first_check_ns`, `enqueue_to_all_checks_ns` and `enqueue_write_ns`, each `{count, min, median, p95, max}` over every run of every round. **No record is committed yet**: a run on the verification VPS proves the harness, and a baseline needs a quiet host.

## S3 hashing and signing

`crates/sentinel-s3/examples/s3-hash-bench.rs` times what a put costs on the CPU before a byte leaves: `client::body_hashes` (the signed SHA-256 payload hash and `Content-MD5` from one 64 KiB-chunk walk, as `put_object` and `upload_part` call it), `sigv4::sha256_hex` and `client::content_md5` alone, the two-pass alternative (`sha256_then_md5`) the one-walk design replaced, and `sigv4::authorization` (Signature V4 signing of a PutObject's headers, independent of the payload). No network, no service, no allocation of the payload inside the timed region. Payload sizes default to 4 KiB, 64 KiB, 1 MiB and 16 MiB (`--sizes`, bytes); each case repeats until it has hashed `--sample-mib` MiB (default 64, at least one call), `--rounds` rounds (default 7) with the case order reversing every round (ABBA), and signing runs `--sign-iterations` (default 20,000) calls per round. Run it through `bench/s3-hash.sh` (stamp as above, `bench/s3-hash.jsonl`).

Record `sentinel-bench/s3-hash/1`: `rounds`, `sample_mib`, `order`, `results[]` (`bytes`, `case`, `ns_per_call` one per round, `median_ns_per_call`, `min_ns_per_call`, `max_ns_per_call`, `mib_per_s_median`) and `sign {iterations_per_round, ns_per_call, median_ns_per_call, min_ns_per_call, max_ns_per_call}`. The figures are CPU and memory bandwidth of the host named in the stamp; they are not comparable across hosts. **No record is committed yet.**

## Backup rehash cost

`backup::verify` rehashes the snapshot and every object and manifest it names ([backup](backup.md#verifying)); `backup::create` does the same while it copies. `crates/sentinel-store/examples/backup-rehash-bench.rs` measures that cost at configurable object counts: for each of `--counts` (default 100 and 1000) it builds a real store with that many distinct objects of `--object-bytes` bytes (default 1 MiB), takes one backup, then times `backup::verify` over `--rounds` rounds (default 5) in an order that reverses every round (ABBA), and, in the same round, a bare BLAKE3 read of the same object files in the backup. The bare read is the floor the rehash cannot beat; the difference (`median_overhead_ns`) is the snapshot hash, SQLite's `integrity_check` and the per-row work. Every verification must pass and check exactly the expected number of objects, or the bench fails rather than report a time. Setup is not timed. The datasets exist twice on disk (objects and the backup copy) and all counts coexist, so the bench refuses a combination above `--max-gib` (default 8) before writing anything, and removes everything it created under `--dir`. Run it through `bench/backup-rehash.sh` (stamp as above, `bench/backup-rehash.jsonl`).

Record `sentinel-bench/backup-rehash/1`: `object_bytes`, `rounds`, `order`, `cache` (always `warm-unless-dataset-exceeds-memory`: the bench does not drop the page cache, so a figure for a dataset smaller than memory is a warm-read figure; the cold-disk figure needs a dataset larger than memory) and `results[]` with `objects`, `dataset_bytes`, `verify_ns` and `floor_ns` (one per round), `median_verify_ns`, `min_verify_ns`, `max_verify_ns`, `median_floor_ns`, `median_verify_ns_per_object`, `median_overhead_ns` and `verify_mib_per_s_median`. The R04 drill's one-off verify figure (`bench/r04-backup-drill.jsonl`) is a different dataset and is not a series with this. **No record is committed yet.**

## Micro-contract benches

The in-process benches (log-ack, checks-lane, s3-hash, backup-rehash, auth-cost, store-cost, spawn-cost, the `sentinel-bench` no-op interleave, `f07-storage`, `k02-cache-clone`, the ignored measurement tests and M06) are frozen by a **micro contract**, `bench/contracts/micro/<id>.json`, format `sentinel.bench-micro-contract/1`. It sits beside `sentinel.bench-contract/1` (container lanes run by `sentinel-bench --contract`) and shares its `format`, `id`, `revision`, `reference_host` and the 5 percent start-pressure bound; an in-process bench has no image, source or lane to pin. A contract names the `harness` (an `example` binary, or a `script`, with the `build` command), `run.args` (the frozen arguments), `run.smoke_args` (and `smoke_env`) for the tiny run, the `ordering` (`abba`, `shuffle` or `single`, with `seed` null for a bench that has no random choice, stated explicitly, or `{env, recorded_as}` for one that shuffles from a seed), `quiet_start.max_cpu_pressure_avg60`, and the `record` (`schema`, `out`, `own_stamp` for `sentinel-bench`, which stamps itself, and `from_stdout` for a script harness that prints its records on stdout and has the runner stamp them; the other script harnesses, `f07-storage.sh` and `k02-cache-clone.sh`, write their own stamped records and the runner only takes the lock and checks the host).

`bench/micro-run.sh bench/contracts/micro/<id>.json [--smoke] [--out FILE] [--dir DIR] [-- extra bench args]` is the only runner (the per-bench `bench/<id>.sh` scripts are three-line wrappers around it). A measured run does these things in this order, and measures nothing when one refuses: validate the contract (exit 2 names the field); stamp the build and host with `benchstamp.py` (a commit and an anonymized `SENTINEL_BENCH_HOST_LABEL` are required); check `reference_host` when the contract names one; take the shared lock (see [Benchmark lock](#b09-reliability-and-performance-scenarios-and-the-regression-gate)) and record the wait; refuse unless CPU pressure avg60 is below the contract's bound; run the bench; and append the stamped records only when the bench exits 0 and every line carries the contract's schema. A record gains `contract {id, revision, sha256}`, `ordering`, `conditions {start, end}` (pressure, load average, steal) and `lock {path, waited_ns}`. The file is appended to and never truncated. Exit codes: 2 for a contract or argument problem, 3 for a host, quiet-host or label refusal, 75 for "pending" (below; a bench that exits 75 itself, as a test does when it skipped, is pending too and appends nothing), otherwise the bench's own status. `python3 bench/micro_contract.py check <contract>` validates one without running it.

**Smoke.** `--smoke` runs the same bench with `run.smoke_args` (about ten seconds; `f07-storage` and `k02-cache-clone` about a minute) under `nice -n 19 ionice -c3`, with scratch under `/var/tmp`. It takes no lock and no quiet host, so it can run beside other work, but it exits 75, **pending**, when CPU pressure avg10 is above 25 or a measurement holds the lock, and it refuses an `--out` inside `bench/`. Its records carry `"smoke": true` and the hygiene test rejects a committed record that does. A smoke run proves the harness runs and its record has the shape the contract names; it is never a baseline.

**Unmeasured is absent.** A field a bench could not measure is absent from its record, never zero, and a bench whose operation did not do what it names (a login that was not rejected, a checkpoint that did not run) fails instead of reporting a time.

## Auth and credential cost

`crates/sentinel-store/examples/auth-cost-bench.rs` times the paths [local authentication](local-authentication.md) and [API credentials](api-credentials.md) price: Argon2id `hash`, and `verify` of the right and of a wrong password (`sentinel_auth::password`); session validation (`local_auth::authenticate`) on a reader connection already checked out (`session_validate_conn`, the query alone), through `Store::read` (`session_validate_store_read`, which adds the reader checkout) and for an unknown token (`session_validate_miss`); the four login outcomes (`login_accepted`, `login_rejected` under a policy whose lock-out threshold cannot be reached, `login_locked`, `login_unknown_username`); and API-credential validation (`token_validate_hit`, `_unknown`, `_expired`, through `Store::read`) and issuance (`token_issue`, a writer transaction and its audit row). The store opens with `Durability::Full`, as the server does; the store logic sees a fixed instant, so a run does not depend on the date.

Each round runs every operation once, `--iterations` calls for the cheap ones and `--argon-iterations` for the Argon2 and login ones, and the operation order reverses every round (ABBA). The credentials, the picks among them (seeded by `--seed`, which the record carries) and the names are prepared before a timer starts; every outcome is checked after the timer stops; three untimed warm-up calls per operation come first (`warmups` in the record). The clock is `Instant`, and `timer_floor_ns` records its own cost, because the cheapest operations are a few ticks. Record `sentinel-bench/auth-cost/1`: `seed`, `rounds`, `iterations`, `argon_iterations`, `sessions`, `tokens`, `durability`, `argon2 {algorithm, version, m_kib, t, p}` (read back from the stored PHC string, not assumed), `order`, and `results[]` with `op`, `calls_per_round`, `samples`, `round_median_ns`, `min_ns`, `median_ns`, `p95_ns`, `p99_ns`, `p95_is_max`, `p99_is_max` and `max_ns`; the login and `token_issue` entries add `audit_rows_added`, because an unknown or locked login coalesces its audit rows and the cost of that path includes how many it wrote. Run it through `bench/auth-cost.sh` (contract `auth-cost`); `crates/sentinel-store/tests/auth_cost_harness.rs` runs the built example at tiny sizes and checks the record. **No record is committed yet**: the figures in the two documents above are WSL2 development numbers and stay labelled so until a quiet reference-host record replaces them.

## Store cost

`crates/sentinel-store/examples/store-cost-bench.rs` measures three maintenance paths on a real `Store` under `--dir`, one fresh store per mode. `reapply` runs `retention::reapply_step` to completion over `--rows` released attempts once per batch size of `--batches` and once unbatched (a batch of the whole table); each batch is a writer transaction, so the longest step is the longest the single writer is held, and the record carries the step count, the total, the longest step and the `EXPLAIN QUERY PLAN` text of the bound and update statements. `checkpoint` times `Store::checkpoint` after `--wal-rows` rows of writes, with no reader and with each count of `--readers` read transactions that began before the writes and stay open; a blocked checkpoint is `partial` after the store's own 200 ms budget, and the record counts both outcomes. `capacity` times `dispatch::free_capacity` for a worker with one live attempt beside each of `--history` released attempts, to show whether the read grows with history. The big tables are built by copying one real attempt row, whatever the schema's columns are, so a migration that adds a column does not break the bench. `--max-gib` refuses a combination whose estimated size is above it before anything is written. Record `sentinel-bench/store-cost/1`; run it through `bench/store-cost.sh` (contract `store-cost`). **No record is committed yet.**

## Spawn cost

`crates/sentinel-git/examples/spawn-cost-bench.rs` measures what `sentinel_git::die_with_parent` ([executor](executor.md)) costs a helper spawn. The hook is a `pre_exec` closure, so a `Command` that has it is spawned by `fork` where one without is spawned by `posix_spawn`, and `fork` costs more the more memory the parent has resident. The bench spawns and waits for `true` from a parent with 0, 64 and 512 MiB resident (`--resident-mib`, touched page by page) in three variants: `plain`, `pre_exec_noop` (the `fork` path alone) and `die_with_parent` (adding the `prctl` and the `getppid` check). The sizes and variants reverse their order every round. Record `sentinel-bench/spawn-cost/1`; run it through `bench/spawn-cost.sh`. **No record is committed yet.** The `PR_SET_PDEATHSIG` behavior itself (a killed parent kills the helper) is still not covered by a test of its own.

## Ignored measurement tests

Some measurements are `#[ignore]`d tests that print their own report: the 10k-job load (`q09-fleet-load`, `sentinel-store` `fleet_load`), the queue listing (`queue-explain`), the backup and restore drill (`backup-drill`, with `SENTINEL_DRILL_DIR` and `SENTINEL_DRILL_BIG`; the 100 GiB objective needs three times that in free disk), the cache transfer cost (`remote-cost`, with `SENTINEL_REMOTE_COST_DIR`) and the live Tailcat helper (`tailcat-live`, which needs a pinned Tailcat build in `SENTINEL_TAILCAT_LIVE` and rootful Podman). `bench/run-ignored.sh PACKAGE TEST_TARGET TEST_NAME`, the script harness of those contracts, runs one under `cargo test --release --locked -- --ignored --nocapture --exact`, keeps the stdout lines that start with `{` as `reports`, and prints one `sentinel-bench/ignored-test/1` record with the outcome and the monotonic time of the whole `cargo test`, which the runner then stamps and appends. It removes `SENTINEL_BENCH_OUT` from the test's environment, because the load tests append an unstamped line to that file. It prints nothing and exits non-zero when the test failed or did not run exactly once, and exits 75 (pending) when the test skipped itself, since a skipped test measured nothing. `--smoke` only checks that the test target lists the test as ignored. **No record is committed yet**; `tailcat-live` and the 100 GiB drill are contract-complete and run in Wave 2.

## B05 matrix and its smoke profile

`bench/b05-cache.sh` runs the B05 cache-usefulness matrix and `bench/b05-workloads.sh` the real-toolchain workloads (see [cache](cache.md)). Both stamp every record with `bench/stamp.sh`, take the shared lock, shuffle the order of their cells from `SHUF_SEED` (recorded as `shuffle_seed`, with the cell's `position` and `pass`; `PASSES` repeats the matrix), and count a failed cell: the matrix exits 1 and names the failed shapes instead of ending on the cleanup command's status. The **smoke profile** (`--profile smoke`) runs the same cells at tiny sizes, in a scratch tree, with no lock and no quiet host (it exits 75 when the host is busy), refuses an `OUT` inside `bench/`, leaves out `reflink-up` and `reflink-down`, and marks every record `"smoke": true`. `B05_DATA` moves the workload data directory and `B05_TOOLS` names a directory of toolchain stand-ins whose `bin/` is put first on `PATH`; `bench/fake/b05/` holds stubs for `go`, `cargo`, `rustc`, `node`, `npm`, `npx`, `mvn`, `java` and `pip` that log their calls, create the directories a real run would, and fail the way a real one does offline with an empty cache. `bench/test_b05_matrix.py` runs the matrix and the workloads end to end against them and asserts the cells and languages that ran, the shuffle seed and positions, the smoke marking, that the offline step really is offline, that a failing cell and a failing toolchain turn the run red (`FAKE_FAIL`, `FAKE_FAIL_SHAPE`), and that nothing is left behind. The stand-ins prove the harness, never a result; real B05 numbers need real toolchains and a quiet host.

## B09 rehearsal

`B09_REHEARSAL=1` runs `bench/b09-harness.py` against a fake controller and worker (`bench/fake/b09/`: a `sentinel` shim for `fake-sentinel.py`, and stubs for `b09-git.py` and `seed-membership.py`) and a single `shim` script installed under the names of the privileged tools (`ip`, `tc`, `losetup`, `dmsetup`, `mount`, `umount`, `runuser`, `nsenter`, `chown`, `fallocate` and the others the harness calls). The shim logs every call to `FAKE_LOG` and keeps what the harness created in `FAKE_STATE`, so the harness's own cleanup finds real objects to remove and the tests assert that none remain. The harness refuses to start a rehearsal unless the shims answer, `B09_BENCH_HOME` and `FAKE_STATE` are set, and neither `--out` nor `--root` is inside `bench/`; it needs no root, listens on loopback ports from `B09_PORT_BASE`, caps its waits (`B09_TIMEOUT_CAP`) and skips the settle sleeps. Every rehearsal record carries `simulated: true` and `rehearsal: true`, and `bench/b09-gate.py` refuses such a record with exit 2: **a rehearsal is never evidence**. Knobs of the fake (`FAKE_DEFECT=lose-run-on-restart|never-reconnect`, `FAKE_429_EVERY`, `FAKE_SLOTS`, `FAKE_RUN_MS`, `FAKE_TIME_SCALE`) inject the defects the assertions must catch, and `bench/test_b09_rehearsal.py` checks that each one flips the named assertion. `disk-full-*` is recorded blocked in a rehearsal, because a shimmed mount is a plain directory and the filler would fill the real file system. The rehearsal also found a real harness defect: a call made while a restarted controller was still refusing connections raised instead of waiting for it; `call()` now retries refused or dropped connections for up to two minutes (capped by `B09_TIMEOUT_CAP`), but only in a rehearsal: a real run fails at once on a refused connection, so a crashed controller is never waited on inside a timed window such as the intake ack, and no POST is sent twice.

## Harness smoke

`bench/smoke.sh [--quick]` is the one entry point for the harness checks on a Linux verification host: every Python unit test under `bench/` (`--quick` leaves out the B05 matrix and B09 rehearsal tests, the slow ones), the Q13 fleet driver's self-test, and `micro-run.sh --smoke` for each contract whose binary is built. It prints PASS, `SKIP(pending)` (a busy host or a held lock), `SKIP(no binary)` or FAIL per item and a summary that counts the skips apart from the passes; only a FAIL turns it red. Contracts that compile a test binary (the ignored tests and M06) are included only with `SMOKE_COMPILE=1`. Nothing it writes is a measurement.

## Reproducing

1. Prepare rootless Podman for a non-root user per [Development](development.md#linux-executor-work) and pull the image by digest.
2. Build with `cargo release-linux` (or `cargo build --release -p sentinel-bench`) and copy `sentinel-bench` to a native-filesystem directory owned by that user.
3. As that user, run the direct baseline, then `podman system prune -f`, one `--warm-state cold --warmup 0 --samples 1` run, then warm runs with and without limits, all with `--output` to one file.
4. Commit the record under `bench/` and summarize it here with the host identity and any caveats.
