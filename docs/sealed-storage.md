# Sealed storage (S01)

Sentinel uses RustCrypto XChaCha20-Poly1305 for recoverable values. Each seal uses a fresh 192-bit OS-random nonce. Ciphertext format 2 is `02 | key ID (u32 big endian) | nonce (24 bytes) | ciphertext and tag`; the version and key ID are included in authenticated associated data together with the row ownership context. Authentication failure, unknown key IDs, malformed blobs and unknown versions all fail closed without printing plaintext. The existing format 1 (`01 | nonce | ciphertext and tag`) remains readable with key ID 0 for legacy 32-byte key files. New writes use format 2.

Existing second-factor seeds bind to their user ID; source credentials bind to tenant ID, repository ID and source version. `secret_context` provides a distinct, length-delimited tenant, optional repository, name and version context for S02's secret records. It prevents a ciphertext moved between owners, names or versions from opening. The database stores ciphertext only; no general plaintext read API exists.

The master key is `<data_dir>/master.key` unless supplied explicitly to the host-local key command. A new key file is versioned (`SNTLKEY2`, active ID, count, ID/key entries), owner-only on Linux and capped at 32 keys. A legacy raw 32-byte file loads as ID 0. The key is outside SQLite and must be excluded from database-only backups. On Linux the controller refuses a non-regular or group/world-accessible key file. Keep the containing directory private too. `admin key create` refuses an existing path.

## Rotation, backup and restore

Stop the controller and all host-local admin writers. Take a consistent database snapshot and secure copy of the current key file as one recovery point. Run `sentinel admin key rotate --data-dir /absolute/data --backup /absolute/secure/old-master.key` (use `--key-file` if configured). The command takes the controller's database ownership lock when a database exists, refusing rotation while the controller runs. It creates the backup exclusively, stages and syncs a new key file, then atomically replaces the active file. It retains every retired key so existing source credentials and TOTP enrollments remain readable; new seals use the new ID. Restart the controller to load the new file. Keep both the new key file and pre-rotation backup in protected storage.

Restore the database snapshot and **its matching key file** together while the controller is stopped. A pre-rotation key file cannot decrypt values written after rotation. Replacing only the key or deleting retired entries permanently loses the affected values. Restore key permissions to owner-only and restart. Test restore with an actual sealed credential and second-factor seed in an isolated copy before relying on the backup. No automatic pruning or online re-encryption occurs in S01.

The key file contains plaintext key material even though the database does not. Store and transfer it as a secret; never put it in a repository, log, or unprotected database backup. Key rotation limits future exposure but does not revoke a previously copied key that can still decrypt its older ciphertexts. A lost or exposed key requires credential rotation and second-factor re-enrollment; deleting old key entries requires proving every dependent ciphertext was re-encrypted or retired.
