# Sealed storage (S01)

Sentinel uses RustCrypto XChaCha20-Poly1305 for recoverable values. Each seal uses a fresh 192-bit OS-random nonce. Ciphertext format 2 is `02 | key ID (u32 big endian) | nonce (24 bytes) | ciphertext and tag`; the version and key ID are included in authenticated associated data together with the row ownership context. Authentication failure, unknown key IDs, malformed blobs and unknown versions all fail closed without printing plaintext. The existing format 1 (`01 | nonce | ciphertext and tag`) remains readable with key ID 0 for legacy 32-byte key files. New writes use format 2.

Existing second-factor seeds bind to their user ID; source credentials bind to tenant ID, repository ID and source version. `secret_context` provides a distinct, length-delimited tenant, optional repository, name and version context for S02's secret records. It prevents a ciphertext moved between owners, names or versions from opening. The database stores ciphertext only; no general plaintext read API exists.

The key also keys the stored request fingerprints of secret writes: a BLAKE3 `derive_key` subkey of the active key MACs each retry record, so the database alone cannot confirm a guessed secret value. The subkey is derived once when the key loads.

## The key file

The master key is always `<data_dir>/master.key`. The controller, `admin key` and `admin source` all use that one path; there is no option to point any of them elsewhere, so the file the operator rotates is the file the controller reads. A new key file is versioned (`SNTLKEY2`, active ID, count, ID/key entries), owner-only on Linux and holds at most 32 keys. A legacy raw 32-byte file loads as ID 0. The key is outside SQLite and must be excluded from database-only backups (back up `metadata.sqlite` and `master.key` as separate artifacts, and store the key as a secret). The file is opened once, refusing a symbolic link, and the opened handle must be a regular file owned by the controller's user with no group or other access. `admin key create` refuses an existing path.

At start the controller refuses to run (exit 2) when the database holds any sealed value (a secret version, a second-factor seed or a source credential) and `master.key` is missing, unreadable, or does not open the newest sealed value of each table; the last case catches a key restored from a different backup than the database. With no sealed values and no key, it starts without secret storage.

## Rotation, backup and restore

Stop the controller and all host-local admin writers. Take a consistent database snapshot and secure copy of the current key file as one recovery point. Run `sentinel admin key rotate --data-dir /absolute/data --backup /absolute/secure/old-master.key`. The command takes the controller's database ownership lock when a database exists, refusing rotation while the controller runs. It creates the backup exclusively (an exact copy of the old file), stages and syncs a new key file beside the key as `master.key-<id>-pending`, then atomically replaces the active file. A pending file left by an interrupted rotation is never active and is removed by the next rotation. The new file retains every earlier key so existing values remain readable; new seals use the new ID. Restart the controller to load the new file. Keep both the new key file and pre-rotation backup in protected storage.

Rotation alone does not retire an exposed key. To remove old keys, run `sentinel admin key reseal --data-dir /absolute/data` with the controller stopped: it re-encrypts every sealed value that names an older key (secret versions, revoked ones included; second-factor seeds; source credentials) under the active key with the same ownership context, 256 rows per writer transaction. Each batch commits on its own, and values already on the active key are skipped without decryption, so an interrupted run is simply run again. A value that does not open stops the run with nothing lost. `--retire --backup /absolute/secure/pre-retire.key` then checks that no stored value still names another key and writes a key file holding only the active key, after an exclusive backup of the file as it was. The database's triggers allow sealed bytes to change only forward (to format 2 under a strictly newer key ID); nothing else about a version or a confirmed seed can change. After retiring, the file holds one key again, so the 32-key limit never blocks rotation. A full file refuses rotation with a message naming reseal and retire.

Restore the database snapshot and **its matching key file** together while the controller is stopped. A pre-rotation key file cannot decrypt values written after rotation, and a pre-retire backup is the only file that opens values sealed before that reseal. Restore key permissions to owner-only and restart; a mismatched key is refused at start. Test restore with an actual sealed credential and second-factor seed in an isolated copy before relying on the backup.

The key file contains plaintext key material even though the database does not. Store and transfer it as a secret; never put it in a repository, log, or unprotected database backup. Key rotation limits future exposure; reseal and retire make an old key useless for the current database, but a copy of an older database snapshot can still be opened with the old key. A lost or exposed key still calls for credential rotation and second-factor re-enrollment.
