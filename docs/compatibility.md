# Schema and API compatibility policy (C08)

**S01 sealed storage.** New recoverable values use ciphertext format 2 with an authenticated key ID and ownership context; format 1 remains readable with legacy key ID 0. New master key files use the bounded `SNTLKEY2` keyring; existing raw 32-byte files remain readable and are converted on offline rotation. An old binary cannot read format-2 ciphertexts or the new key file. Upgrade controller/admin together, keep the matching key with every database backup and follow [sealed storage](sealed-storage.md) for rotation and restore. No SQLite or worker-protocol version changes.

Sentinel carries several independently versioned contracts. Each has one owner, one version marker and one rule for what a change may do. Nothing is versioned implicitly: if a shape is not listed here it is internal and may change with any commit.

**Secret write surface (S03–S04, migration 39).** Secret routes are additive under `/api/v1`; old clients may ignore them. Writes use raw value bytes, compare-and-set versions and idempotency keys. Migration 39 adds bounded metadata-only replay records. Env-file import accepts the documented literal format and commits all rows in one SQLite writer transaction; this format is a CLI/API contract documented in [secrets](secrets.md).

**Secret delivery (S05–S06, run spec 6, migration 40, protocol 10).** Run spec format 6 adds optional job `registry_auth`, step environment-secret names and secret-file targets; readers still decode formats 3–5 through their shadow layouts. Migration 40 marks jobs that require worker secret delivery so dispatch will not offer them to workers that lack protocol 10 or `SECRET_DELIVERY` bit 9. Protocol 10 appends `SecretBegin`/`SecretChunk`; each transfer is attempt- and fence-bound, ordered, and capped at 1 MiB. The controller resolves only declared bindings and records versioned use in the same writer transaction that checks the acknowledged attempt and opens the sealed values. Workers reject missing, extra, malformed or conflicting targets before execution. Every new attempt, including a rerun, receives the then-current active version. Secret values are not added to the run spec blob or SQLite plaintext; the worker keeps them in private per-attempt files outside workspaces, caches and artifacts, redacts before spool persistence, and reaps crash leftovers. Since the Part 10 audit fixes, a step that receives environment targets runs behind a `/bin/sh` wrapper that sources them from `/run/sentinel-env` (images already need `/bin/sh`), and a secret-bearing step runs in a container cleared of every process earlier steps left running; no wire message or stored shape changed, so the protocol stays 10. Upgrade controllers and workers together for secret-using jobs; older workers remain eligible for jobs with no secret targets. See [secrets](secrets.md), [protocol](protocol.md#protocol-10-secret-delivery) and [executor](executor.md#the-image-pull-k05).

**MCP resource audience (migration 41).** OAuth grant, authorization-code, and device-code rows gain an immutable `resource` column (1 = `{issuer}/api/v1`, 2 = `{issuer}/mcp`). Existing `audience` columns and rows remain API=1 for compatibility with prior constraints; new access-token validation uses the resource audience. MCP authorization, code exchange, and refresh must carry the exact MCP resource indicator. Upgrade the controller and OAuth clients together; migration 41 preserves existing API grants and tokens. The HTTP transport pins protocol revision `2025-11-25`, requires a bearer token and protocol version on session requests, caps request/response bodies, and stores only session digests ([MCP](mcp.md#streamable-http-x05)).

**MCP OAuth client registration (migration 42, X06).** Existing `oauth_clients` rows remain API clients (`resource = 1`, registration kind 0). New rows are public MCP clients (`resource = 2`) created by DCR (kind 1) or CIMD (kind 2); they cannot be first-party, loopback-wildcard, device-capable, or have scope bits outside 1|2|4|64. CIMD metadata URLs are unique and bounded at 2,048 bytes. A partial index supports listing/capacity checks; the hard deployment limit is 512 registered rows. Insert/update triggers retain the MCP-only policy, and grant/code/device-code insert triggers require the resource to match the enabled client's resource. New OAuth metadata fields `registration_endpoint` and `client_id_metadata_document_supported` are additive; new OAuth errors `invalid_client_metadata` and `invalid_redirect_uri` are additive to the form error contract. Existing API grants/tokens and the first-party CLI are unchanged. The HTTP API rejects clients whose supplied resource does not match their registration. See [OAuth X06](oauth.md#mcp-client-registration-and-metadata-discovery-x06).

**OAuth client lifecycle and run control audit (migration 43, `043_oauth_client_lifecycle.sql`; X06/X05 audit fixes).** `deployment_policy` gains `oauth_client_registration` (0 off, 1 Client ID Metadata Documents only — the default for new and upgraded deployments — 2 also anonymous DCR). This is a behavior change: an upgraded deployment stops accepting `POST /oauth/register` (`403 access_denied`) and stops advertising `registration_endpoint` until an operator runs `sentinel admin policy set --oauth-client-registration open`; clients already registered keep working. `oauth_clients` gains `registrant` (a 16-byte digest of the registering address), and the insert trigger now counts only enabled registrations toward the 512 bound; indexes on `oauth_grants`, `oauth_codes` and `oauth_device_codes` by `client_id` make reclamation and client deletion key searches. Registrations that hold no grant or code are deleted by maintenance after 24 hours, evicted at capacity after 15 minutes, and bounded to 16 per address. Registered loopback redirects are stored without their port and match on any port (RFC 8252 §7.3); rows stored by migration 42 with a port still match exactly and on their port-free form. `operation_audit` is a new append-only, tenant-owned table recording run cancel, job cancel and job rerun with the account, the authentication kind and the OAuth grant and client. RFC 8414 metadata only ever gains optional members: `registration_endpoint` is now omitted when DCR is off and `client_id_metadata_document_supported` may be `false`, and `sentinel_protocol::oauth::Metadata` reads both as optional, so a newer CLI signs in to a controller from before migration 42. Streamable HTTP MCP: an unsupported `MCP-Protocol-Version` is now `400` (was `426`) with the same `unsupported_version` body, an absent one is accepted as the session's negotiated revision, a missing `Mcp-Session-Id` is `400` (was `404`), and `initialize` with another revision answers with `2025-11-25` instead of `-32602`. Tool annotations changed (`openWorldHint: false` everywhere, `dispatch` and `rerun_job` not destructive). The server configuration gains `trusted_proxies`; its default (loopback only) no longer trusts `X-Forwarded-For` from private-network peers, so a proxy on another host must be listed. No worker protocol change.

**Secret hardening (migration 44, `044_secret_hardening.sql`; Part 10 audit).** Existing `secret_idempotency` rows are deleted: they held an unkeyed digest of the written value, and new rows hold a keyed MAC that cannot be computed from an old row. A retry of a write made before the upgrade executes again under its `If-Match` version and answers `conflict` if the first write committed. `secret_audit` is rebuilt with the same rows plus a nullable `name` and a nullable `secret_id` (only for a delivery refusal with no resolved secret, result `denied` or `missing`), and becomes append-only by trigger. `secret_version_immutable` no longer covers `sealed`; the new `secret_version_reseal` trigger lets sealed bytes change only to format 2 under a strictly newer key ID, and `totp_update` allows the same forward reseal of a confirmed seed. An older release reading a marker ≥ 44 finds the same table shapes plus one column. The HTTP additions (allowlist, binding and revocation routes) and the `idempotency_mismatch` code on secret routes are additive; the master key file path is fixed at `<data_dir>/master.key` (the admin `--key-file` option is removed).

**Web interface (migration 45, `045_web_ui.sql`; Part 12).** Migration 45 adds indexes only — `provenance_by_ref`, `provenance_by_pr` (partial), `runs_by_sha`, and three partial indexes over `check_publications` by state — so an older controller keeps working on the upgraded database. API changes are additive: `GET /tenants`, `GET /tenants/{slug}/sync`, `GET /attempts/{id}/steps`, `POST /step-up`, the `/admin/*` routes, the tenant `members`, `repos` (create), `source`, `grants` and `audit` routes, the run list's `ref`, `pr`, `sha` filters and `trigger`, `ref`, `pr` fields, the log page's `step_done`, `/me`'s `stepped_up` and `mfa`, `/health`'s `github_sign_in`, and `/workers`' capacity, reservation, label and drain fields. Behaviour changes: the controller no longer serves a page at `/` (`not_found`; the web interface is the separate `sentinel-web` process); GitHub check `details_url` is `{public_url}/runs/<id>` instead of `{public_url}/#/runs/<id>`, and the web interface still opens links in the old form; the parked long-poll budget is 32 (8 per user) instead of 3 (2), parked polls no longer hold a handler permit, and a parked poll ends early when its reader loses access (`not_found`) or its client hangs up; an organization's last administrator can no longer be demoted or removed (`conflict`), where before nothing prevented it. The GitHub sign-in finish page hands the CSRF secret over through `localStorage` instead of `sessionStorage`. Upgrade the controller and `sentinel-web` together; clients that parse `/workers`, run lists or `/me` strictly must accept the new fields ([web interface](web-ui.md), [API](api.md)).

**Retention and quotas (migration 46, `046_retention.sql`; R01).** Migration 46 moves `tenant_quotas` into `storage_policies` (one row per tenant or repository: quota, log retention, artifact retention; the quota rows carry over) and drops `tenant_quotas`; adds `storage_defaults` (the controller's `[storage]` limits, written at every start), `repo_usage`, `tenant_usage.log_bytes`, the attempt columns `log_bytes`, `log_expires_ms` and `log_expired_ms` with their partial indexes and triggers, an `artifacts` insert trigger that caps a new row's `retain_until_ms` at the effective artifact retention, and `uploads_aborted`. The recreated `attempt_update` trigger also refuses to clear `log_expired_ms`. An older controller is refused like any newer database (it would still read `tenant_quotas`). Behaviour changes: log retention is now decided in the database — a released attempt's log is stamped with its size and deadline and deleted once the row says it expired, so a log directory no attempt row names is removed by the maintenance pass rather than kept until it ages out; tenant usage and quotas count stamped log bytes beside object bytes; a pipeline's `retain` above the effective artifact retention (default 90 days, where before up to 365 were kept) is shortened; `run_artifact_bytes` and `attempt_log_bytes` replace the fixed 16 GiB and 256 MiB; unset watermarks and the worker and remote-cache budgets are sized from the data file system (they equal the old fixed values on 64 GiB for the watermarks and on 1 TB for the budgets); aborted upload rows are deleted a week after they expire. API changes are additive: `GET /admin/storage`, `PUT /admin/tenants/{slug}/storage`, `GET /tenants/{slug}/storage`, `PUT /tenants/{slug}/repos/{name}/storage`, the tenant list's `log_retention_ms` and `artifact_retention_ms`, and a log page's or search's `expired_ms`; `usage_bytes` now includes log bytes. New configuration keys are optional ([configuration](configuration.md), [retention](retention.md)).

**External S3 copy (migration 47, `047_s3.sql`; R02/R03).** Migration 47 adds `objects.remote_ms` and `objects.evicted_ms` (the recreated `objects_immutable_update` trigger lets only those two change, `remote_ms` once, and never evicts without a copy), the `objects_unreplicated` and `objects_evictable` indexes, `object_totals` (local and unreplicated bytes, kept by triggers), `s3_uploads`, `s3_deletes` with the triggers that fill it on object delete and log expiry, `attempts.log_remote_ms` with `attempts_log_unreplicated` and a trigger resetting it when a copied log's state changes. Without `[s3]` nothing reads or writes these beyond the triggers' bookkeeping. An older controller is refused like any newer database. API changes are additive: `GET /admin/storage` gains `s3` (`null` without `[s3]`), and `GET /queue` gains `placement_paused` (`disk_below_watermark` or `external_copy_backlog` while admission is closed, else `null`) and the reason code `storage` for a job that would otherwise be placed. New configuration: the optional `[s3]` section ([s3](s3.md)).

**Backups (`sentinel.backup/1`; R04).** A backup directory's layout and `backup.json` are a versioned contract: `format` names it, and a reader refuses another. The snapshot inside a backup carries its own `schema_migrations`, so a newer controller restores an older backup and migrates it as it would any older database; an older controller cannot restore a newer backup (the snapshot is a newer database). No schema change: backups need no migration. API changes are additive (`GET|POST /admin/backups`), as is the optional `[backup]` section and the `admin backup` and `admin restore` commands ([backup](backup.md)).

**Upgrades and rollback (migration 48, `048_upgrades.sql`; R05).** Migration 48 adds `schema_migrations.readable_by` — the oldest schema whose binary may keep running on the database after each migration — backfilled as each version's own number except 45 (indexes only, readable by 44), and records it for every later migration from `schema::READABLE_BY`; and `workers.software`, the software string a worker announced at its last hello. Migration 48 itself is readable by 47: an older binary ignores both columns. A binary opening a newer database now runs on it when every migration it does not know declares a `readable_by` it reaches, and refuses it otherwise ([upgrades](upgrades.md)). Before any pending migration the controller and host-local `admin` commands copy the database to `metadata.sqlite.vNNN` (newest two kept), and a failed migration is reported with that copy. API changes are additive: `GET /version`, and `protocol` and `software` per worker on `GET /workers`. New command: `admin upgrade check`. **Rule for later migrations:** declare `readable_by` below the migration's own version only for additions no older statement reads or writes, and say so here.
