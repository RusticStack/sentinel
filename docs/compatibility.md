# Schema and API compatibility policy (C08)

Sentinel carries several independently versioned contracts. Each has one owner, one version marker and one rule for what a change may do. Nothing is versioned implicitly: if a shape is not listed here it is internal and may change with any commit.

| Contract | Marker | Where | Consumers |
|---|---|---|---|
| Pipeline schema | `schema: N` in `.sentinel.yml` (currently 1) | `sentinel-pipeline` | repositories |
| Run spec blob | leading format byte (currently 4; reads 3–4) | `sentinel-pipeline::run`, `run_specs.format` | store, workers |
| Cache manifest | `sentinel.cache` magic + format `u8` (currently 1) | `sentinel-cache::manifest` | workers |
| Cache file listing | `sentinel.files` magic + format `u8` (currently 1) | `sentinel-cache::manifest` | workers |
| Cache miss reasons | `Miss::as_str` vocabulary | `sentinel-cache::outcome` | workers, reports |
| Metadata database | `schema_migrations.version` (currently 35) | `sentinel-store` | controller |
| Manifest file | `SNMF` magic + format `u16` (currently 1) | `sentinel-store::objects` | controller |
| API error | `schema: "sentinel.error/1"` | `sentinel-protocol` | CLI, MCP, UI, workers |
| Explain output | `schema: "sentinel.explain/1"` | `sentinel-pipeline::explain` | CLI, agents |
| Event cursor | text prefix `c1` | `sentinel-protocol::cursor` | API clients (`GET /attempts/{id}/logs` `next`/`cursor`) |
| Worker protocol | `protocol_min..=protocol_max` in `Hello` (currently 1..=9) | `sentinel-protocol::negotiate` | workers |
| Log segment index | `SNLI` magic + format `u16` (currently 1) | `sentinel-store::logs` | controller |
| Compressed log segment | `SNLZ` magic + format `u16` + codec `u8` (currently 1, zlib) | `sentinel-store::logs` | controller |
| Log end marker | `SNLE` magic + format `u16` (currently 1) | `sentinel-store::logs` | controller |
| Capabilities | bit positions in `Capabilities` | `sentinel-protocol` | workers, scheduler |
| OAuth token text | prefixes `sntl_at_`, `sntl_rt_`, `sntl_ac_`, `sntl_dc_` + 64 hex (72 chars) | `sentinel-auth::oauth` | CLI, agents, secret scanners |
| OAuth scopes | stored bit positions of `Scopes` (bits 0–9) and their names | `sentinel-core::auth` | grants, tokens, clients |
| OAuth audience | stored `Audience` code (1 = API; 2 reserved for MCP) | `sentinel-core::auth` | grants, codes, tokens |
| OAuth error | RFC 6749 `{"error", "error_description"}` at `/oauth/*` | `sentinel-protocol::oauth` | OAuth clients |
| CLI profiles | `schema: "sentinel.profiles/1"` in `profiles.json` | `sentinel` CLI | the CLI on one machine |
| CLI exit codes | 0–8 ([CLI](cli.md#exit-codes)) | `sentinel::client::Exit` | scripts, agents |

## Rules

**Pipeline schema.** A file names the schema it was written for and is accepted only by builds that implement that exact version. Within a version, changes may only widen what is accepted (new optional keys, new functions, relaxed limits). Rejecting something that was previously accepted, changing the meaning of an accepted construct, or tightening a limit requires a new schema number; the old number stays supported for at least two minor releases and its removal is announced in the changelog. Unknown keys are always errors, so a file cannot silently depend on a feature its declared schema does not have.

**Run spec.** The blob is written once per run and read by every attempt. The format byte identifies the postcard layout. Layout changes, including trailing optional fields, increment it unless old/new reader fixtures explicitly prove compatibility in both supported directions; optional fields do not imply default-on-EOF behavior. Readers reject unknown bytes rather than guess. A controller upgrade never rewrites stored specs; runs created under an old format finish under the code that can read it, which is why old readers are kept for one release after a bump.

**Attempt summary.** The worker's per-attempt measurement blob (W04) is versioned by a leading format byte like the run spec. Format 1 is the original layout and stays decodable forever, through a shadow struct that leaves the added fields absent. Format 2 — always written from K04 — adds `checkout_fetch_ns`, `checkout_materialize_ns` and `checkout_route` for the mirror-aware checkout ([mirrors](mirrors.md)); a decoded format-1 blob reports them as `None`, never zero. Format 3 — always written from K08 — adds `image_present` and the bounded per-entry `caches` record set (`CacheRecord`, at most `MAX_CACHE_RECORDS`; [cache](cache.md)); decoded format-1 and format-2 blobs report them as `None`/empty. Readers reject an unknown format byte rather than guess.

**Database.** Migrations are append-only and forward-only; there is no down migration. A release may add migrations; it must be able to open a database at any version produced by the previous release. Columns are never dropped in the same release that stops writing them. `PRAGMA user_version` is not used; `schema_migrations` is the only truth.

Readers reject a database newer than their highest known migration. Migration 4 preserves version-3 tables and blobs, adds identity/grants, and rejects inconsistent ownership rather than silently repairing it. Migration 5 adds local credentials, sessions, the append-only authentication audit and the single-row bootstrap latch; stored password records are PHC strings carrying their own parameters, so a parameter upgrade rehashes on next login instead of invalidating accounts. Migration 6 adds scoped, expiring API credentials, stored as digests with immutable scope; migration 7 adds single-use, expiring external sign-in state; migration 8 adds account status, the deployment admission policy, one-time invitations and forge installations, and relaxes the credential trigger so a pending account may hold the credential it registered with (authentication still requires an active account); migration 9 names sessions, adds step-up freshness, and adds sealed TOTP seeds and hashed recovery codes. Sealed values carry a version byte and are readable only with the deployment's `master.key`. Migration 10 adds a per-session step-up failure counter ([Part 03 audit](part-03-audit.md)); migration 11 adds the per-tenant authorization epoch, worker pools and pool grants ([tenancy](tenancy.md)); migration 12 adds the once-written image digest and platform on job rows that execution admission requires ([storage](storage.md), [Parts 01–02 audit](parts-01-02-audit.md)); migration 13 adds worker enrollments and worker identities ([worker link](worker-link.md)); migration 14 adds job resource needs, worker capacity and the attempt-as-reservation columns and indexes ([storage](storage.md)); migration 15 adds the write-once attempt summary and recreates the attempt trigger to cover it; migration 16 adds the job's `timeout_ms` and the partial indexes the expiry and queue-timeout sweeps use; migration 17 adds tenant-owned source bindings, their append-only audit, and GitHub App account/permission/lifecycle columns on `installations` ([sources](sources.md)); migration 18 adds per-repository intake hook secrets and the durable `webhook_deliveries` queue with its dedup key, admission/retention indexes and immutability trigger ([intake](intake.md)); migration 19 adds the terminal `dispatched` delivery state and the run it produced, the pull-request terms of a delivery, and the write-once per-run provenance row ([intake](intake.md)); migration 20 adds the Checks outbox: one coalesced row per run scope or refused event, with the publication cursor that makes retries and stale writes safe ([checks](checks.md)); migration 21 adds the forge's suite handle and the durable create-started marker to that outbox, plus `github_events` control receipts (delivery-ID keyed, digest-checked) and the sequence-fenced `github_refresh` queue the reconcile lane drains ([checks](checks.md#rerequests-and-lifecycle-reconciliation-g05)); G07's migration 22 adds `poll_configs` (per-repository opt-in ref polling with its durable schedule and failure state) and `poll_observations` (the last-advertised ref tips), both cascading with their repository and rebuilt/removed on binding changes ([intake](intake.md#ref-polling-g07)); D01's migration 23 adds `objects` (the reference commit for content-addressed bodies under `objects/`) and `manifests` (versioned reference lists under `manifests/`), both tenant-scoped and update/delete-proofed by triggers ([storage](storage.md#objects-and-manifests-d01)). The manifest file format itself (`SNMF` magic + format `u16`) is a stored-bytes contract: a layout change increments it, and readers reject unknown magic, formats, kinds, entry paths and trailing bytes. Migration 24 adds `uploads`: the durable resumable-upload session row (tenant owner, declared length and digest, received byte ranges, expiry, state) backing `incoming/` staging files ([storage](storage.md#resumable-uploads-reads-and-materialization-d02)); the ranges blob is an internal layout, not a wire contract. D03's migration 25 adds `artifacts` (one terminal `captured`/`absent`/`failed` row per declared artifact on an attempt, pointing at a `manifests` version when captured; [storage](storage.md#artifact-records-d03)), the run spec format moves to **3** because compiled artifacts now carry `required`, and the worker protocol maximum raises to **4** for the `ArtifactBegin`/`ArtifactFile`/`ArtifactData`/`ArtifactEnd`/`ArtifactAbsent` messages and their `ArtifactGrant`/`ArtifactVerdict` answers; a protocol-3 worker is still welcome — its declared artifacts simply resolve `absent`. D04 raises the worker protocol maximum to **5** for `LogEndAck`, the controller's answer to `LogEnd` once the `end` marker is durable; workers on protocol ≤ 4 keep the send boundary and drop the spool once `LogEnd` is handed to the session. On disk, D04 moves logs from `logs/<attempt>.log` to segmented `logs/<run>/<job>/<attempt>/` directories — the record stream inside each segment is the unchanged `sentinel-protocol::logs` encoding, while `index` (`SNLI` format 1), `seg-NNNNNN.z` (`SNLZ` format 1, codec 1 zlib) and `end` (`SNLE` format 1) are new stored-bytes contracts; pre-D04 flat files keep reading through the legacy path, which means an older release cannot read a D04 log directory but a D04 release reads both. D05's migration 26 adds `attempts.log_state` (`pending`/`incomplete`/`complete`, monotonic by trigger — a regression is rejected) and widens log scope on the link: `Log`/`LogEnd` are now accepted from any attempt the worker owns, released or not, so a retransmission after terminal publication still heals an `incomplete` row to `complete`; artifact publication and reports stay held-only. The wire messages are unchanged — the scope change is a controller-side semantic, not a protocol bump. D06's migration 27 adds `tenant_quotas` and `tenant_usage` (kept by triggers over `objects` and open `uploads`), `manifest_refs` with `manifests.refs_indexed`, `object_leases`, and an artifact-retention index; it drops the `objects`/`manifests` delete guards so reclamation can retire rows, while the recreated `manifest_update` trigger still forbids every change but the one-way `refs_indexed` 0→1 flip. Pre-D06 manifests stay unindexed and exempt their tenant from object reclaim until `index_refs` backfills the edges; an older release reading a marker ≥ 27 is unaffected — the dropped guards are semantics, not a shape the older reader relies on. Two `sentinel.error/1` codes join the contract — `storage_full` (507, retryable) and `quota_exceeded` (403) ([protocol](protocol.md)); a pre-D06 client treats them as unknown codes, which the error contract already requires tolerating, and `[storage]` in the configuration is a strict server-only section ([configuration](configuration.md)). The heartbeat's `Pong` gained a `cancel` list (W06) and the worker an `Abandon` message (W07). G01 raises the worker protocol maximum to **2**: `Source` (bound credential, sent after `Context` and before `Spec`) is the only addition, and a protocol-1 worker is served `NoSpec` for a bound attempt rather than a spec it cannot fetch with. Since no worker of the W01 shape was ever deployed, protocol 1 remains the minimum and the negotiated shape is otherwise unchanged. G03 raises the maximum to **3** and with it the minimum *effective* level for any spec: `Context` gains the event facts (`event`, `event_ref`, `base_ref`, `pr_number`, `event_key`), so a worker below protocol 3 is served `NoSpec` rather than a message it cannot decode (the G01 source gate is subsumed). No deployed worker exists, so protocol 1 stays the announced minimum and the range is 1..=3. The same task widens the pipeline schema within version 1: `on:` may now be a mapping whose kinds carry optional `branches`/`tags` patterns, the run spec layout changes with it (`CompiledPipeline.on` becomes a typed `Triggers`), so the spec format byte moves to **2**, and migration 19 rebuilds `webhook_deliveries` with the terminal `dispatched` state and the run it produced, adds `pr_deliveries` (cascading with its delivery) and the write-once `run_provenance` row ([intake](intake.md)). G04 is additive: migration 20 adds the Checks outbox table, and `<data_dir>/github-app.json` gains optional `public_url` and `api_url` fields (absent means no `details_url` and the public GitHub endpoint). The outbox is provider-independent; the GitHub publisher is the first implementation ([checks](checks.md)). The HTTP API under `/api/v1` ([API](api.md)) is versioned by its path: additive fields are compatible, a removed or renamed field or a changed status for an error code is a new path version. `FailureClass` gained `Runtime = 11` (`infra_failed`); stored codes 0–10 are unchanged. The worker link's frame format (`u32` length + postcard) and its messages are a versioned contract negotiated through C03's protocol version — still protocol 1, since no worker of the W01 shape was ever deployed: `Hello` gained `capacity`, `Ping` carries `held` and `Pong` answers with `lease_until_ms`/`stop`, and `Ack`/`Decline`/`Offer` are new; W03 adds `Report`, `NeedSpec`, `Spec`/`NoSpec` and `job_index` on the offer, W04 adds `Context` before the spec chunks and an optional encoded `AttemptSummary` on a terminal `Report`, and W05 adds `Log`/`LogEnd`/`LogAck`/`LogRefused`; the log record encoding (`sentinel-protocol::logs`, shared by the worker spool and the controller's log files) is its own versioned on-disk contract (`sentinel-protocol::summary`, format byte 1, at most 32 KiB, its own versioned contract), still before any deployed worker; from here on any change to these shapes bumps the protocol version. Run specs cross the link as the stored bytes (format byte included), chunked, so the spec format's own versioning governs them. The `Rejection` mirror must stay wire-flat because postcard cannot encode tagged enums. The core state machine gained the `OfferLapsed` edge (`leased → queued`, controller only, fence unchanged); no persisted state code changed. The `github` provider key in `external_identities` is part of a stored primary key: changing it orphans existing links. See [authorization](authorization.md), [local authentication](local-authentication.md), [API credentials](api-credentials.md) [GitHub sign-in](github-sign-in.md), [admission](admission.md) and [step-up](step-up.md).

**C06 resolver hardening.** The pipeline schema and run-spec layout remain version 1: no compiler-accepted schema shape is tightened, and static regular-file hash records retain their exact bytes. Runtime filesystem admission now rejects unsafe paths and exhausted traversal/read budgets explicitly. Non-Linux direct resolver calls return `UnsupportedPlatform`; offline CLI operations continue to leave hashes unresolved. Terminal `**` now includes recursive regular files. These worker-resolver behaviors are documented in [hash files](hash-files.md); future persisted cache contracts must version any change to digest record bytes.

**Part 09 OAuth (migration 30).** Migration 30 is additive: `oauth_clients` (seeded with the first-party `sentinel-cli`), `oauth_client_redirects`, `oauth_grants`, `oauth_codes`, `oauth_device_codes`, `oauth_refresh_tokens` and `oauth_access_tokens`, with triggers that fix every grant's terms at issuance (only `last_used_ms` and a one-way revocation move), keep access tokens within their grant, make code consumption, device decisions and refresh rotation one-way, and refuse `platform:admin` for anyone not a super admin, `tenant:admin` for a service principal, a service grant outside its home tenant, a repository outside the narrowed tenant, and scopes beyond the client's ceiling. Nothing existing changes shape. Stored values that are now contracts: scope bits (`runs:read` 1, `runs:write` 2, `logs:read` 4, `artifacts:read` 8, `cache:read` 16, `cache:write` 32, `secrets:metadata` 64, `secrets:write` 128, `tenant:admin` 256, `platform:admin` 512 — allocated once, never reused), audience codes (1 API, 2 reserved for MCP), grant kinds (1 authorization code, 2 device, 3 service), device status (0 pending, 1 approved, 2 denied, 3 redeemed), revocation reasons (1 logout/revoke endpoint, 2 refresh replay, 3 code replay, 4 account suspended/rejected/password reset, 5 membership removed, 6 tenant suspended, 7 owner or administrator) and audit events 48–56 (`OAuthGrantIssued` … `ServiceGrantIssued`, then `ServiceAccountCreated` 56 for a new service principal). Token prefixes are a compatibility surface like `sntl_`: only digests are stored, so changing one invalidates tokens in clients' hands, not rows. `/oauth/token`, `/oauth/revoke` and `/oauth/device_authorization` answer the RFC 6749 error shape; `/api/v1/*` keeps `sentinel.error/1`, and a missing scope there is `forbidden` with `details.scope` plus `WWW-Authenticate: Bearer error="insufficient_scope"` ([OAuth](oauth.md)). A credential lacking the permission a route needs is now refused by that scope check (`403 forbidden`) before the resource lookup, where it previously surfaced as `not_found` from the repository predicate; sessions and `sntl_` credentials otherwise keep exactly their authority (`Scopes::from_permissions`). The CLI's `profiles.json` carries `schema: "sentinel.profiles/1"`; a change to its shape is a new schema string. CLI exit codes 0–8 ([CLI](cli.md#exit-codes)) are stable; the legacy `sentinel api` commands now share them, so a conflict exits 5 and a busy or unreachable controller 6 where both used to be 1.

**Part 09 command surface (O05).** Additive `/api/v1` changes: `GET /runs/{id}/wait`, `GET /attempts/{id}/logs/search`, `GET /attempts/{id}/summary`, `?before=` paging with a `next` cursor on the run list, and `tenant` (the owning slug) on the artifact list and detail answers. One behavior change: `GET /attempts/{id}/logs?wait=1` now shares a controller-wide cap of four parked long polls with `/runs/{id}/wait` (three since the storage hardening below, which also reserves two handler permits); a fifth parked poll is answered at once with `429 rate_limited` and `details.retry_after_ms` where it used to park. A client that treated `wait=1` as always parking must back off and retry, as `sentinel log show --follow` and `sentinel wait` do. Log search also finds a literal split across two frames of one step and stream, which the first O05 build did not ([API](api.md)). The O05 follow-up closes the remaining boundaries additively: the search answer gains `next_carry` (the scan state at `next_after`, opaque hex) and the request an optional `carry`; a client that passes it back finds a split literal exactly once across sealed segments and request cuts, and a client that ignores it keeps the earlier behavior (the state rebuilt from `after`'s segment, which now includes a segment `after` seals). The carry's layout (format byte 1) is internal to one controller build's paging, like a cursor: an unknown format is `invalid_request` and the client restarts the search. Three answer details change within the path version: a request never scans past 4 MiB (it used to finish the frame that crossed it), a line continued into a later frame is reported once rather than once per frame, and a match that began in an earlier frame's text starts at the match.

**Foundation hardening (migration 31).** Migration 31 (`031_foundation_hardening.sql`) adds one trigger, `run_spec_immutable`: a stored run spec can no longer be updated, even by raw SQL; nothing ever updated it, so no shape changes and an older release reading the database is unaffected. The migration list is now checked to be contiguous from 1 at compile time, and `migrate` refuses an entry that is not the database's version plus one. `RunSpec::decode` now enforces the run-spec rule below that readers reject unknown bytes: a blob with bytes after its layout is `Decode` in formats 3 and 4 (the controller never wrote such blobs). One `sentinel.error/1` code joins the contract: `outcome_unknown` (503, `retryable: false`, `details.retry_with_idempotency_key: true`) for a write the controller stopped waiting for but that may still commit, which used to be answered as a retryable `429 rate_limited` and so invited a duplicate from any client that retried unkeyed POSTs. A client that does not know the code treats it as an unknown code (below); the Sentinel CLI retries it only for requests it already considers safe to repeat (GET, PUT, DELETE, keyed POSTs) and exits 6. `sentinel_protocol::ErrorCode` gained `Unknown` (`#[serde(other)]`), so Rust consumers of the published type parse newer codes instead of failing. CLI behavior: a closed standard output now ends a command quietly with exit 0 instead of a panic with exit 101 (outside the 0–8 table), and the client no longer adds its own retries to a `rate_limited` answer that names `details.retry_after_ms` ([CLI](cli.md#exit-codes)).

**Parts 03/09 authentication re-audit (migration 32).** Migration 32 (`032_auth_hardening.sql`) is additive: `mfa_totp.failures` and `mfa_totp.locked_until_ms` (defaults 0) hold the per-account second-factor lockout ([step-up](step-up.md)); an older release ignores them, so a lockout it did not write is not enforced by it. No stored value changes meaning; the new lockout is audited under the existing `SessionRevoked` event with detail `second factor locked`. Behavior changes made for security, with no wire shape changed: `POST /api/v1/login` now requires `content-type: application/json` (else `invalid_request`) and refuses a foreign `Origin` (`forbidden`); `GET /api/v1/tenants/{slug}/repos` and the service-account routes answer `not_found` for a tenant the caller has no part in, where they answered an empty list or `forbidden`; a credential the store is too busy to check is `rate_limited`, no longer `unauthenticated`; the session cookie's `Max-Age` is the absolute session lifetime; and the `resource_metadata` of a `401` challenge is the RFC 9728 §3.1 location, which differs from before only for a `public_url` with a path. Invitations are now voided when their creator loses the authority they delegate, and `registration::reject` of an approved account requires step-up. The CLI's `profiles.json` (still `sentinel.profiles/1`) gains an optional per-profile `key`, the OS-store key recorded at sign-in; profiles without it keep the old key, and an older CLI, which ignores `key`, cannot find a credential a newer CLI stored under a recorded key (sign in again).

**Intake hardening (migration 33).** Migration 33 (`033_intake_hardening.sql`) is additive: it replaces the unused `deliveries_due` index with `deliveries_open (state, received_ms) WHERE state IN (0, 1)` and adds `deliveries_dispatched`, `github_events_by_age` and `check_publications.create_seq`. A check run created after it carries `external_id = <row id>:<create generation>` on GitHub; rows created before it keep their bare id, and rerequests accept both. A poll delivery's `poll:` id now also digests the cursor state it moves, so ids of new poll deliveries differ from what an older release would have computed for the same transition (they were never an external contract). Two `/api/v1` behavior tightenings: manual dispatch on an unbound repository answers `400 invalid_request` for any remote that is not an unauthenticated canonical `https://` URL, where local paths, `file://`, `ssh://`, `git://` and `http://` were previously accepted; and `admin intake purge` reports `receipts_purged` beside `purged`. Delivery outcome reasons gain `tenant_suspended` (resolution), `access_removed`, `destination_refused`, and the retry reasons `source_changed`, `store_unavailable`, `store_fault` ([intake](intake.md)).

**Storage hardening (migration 34).** Migration 34 (`034_storage_hardening.sql`) adds `object_unreferenced` (kept by triggers over `objects` and `manifest_refs`; backfilled from existing rows) with its age index, and the partial indexes `manifests_unindexed` and `uploads_object`; an older release reading a marker ≥ 34 is unaffected — the table and indexes are additive and the older reclaim query does not read them. Two stored-bytes contracts join: a live controller log directory may hold `holes` (`SNLH` format 1: the persisted hole list, removed with the directory; an older release ignores it and forgets a sealed-segment hole as before), and a worker spool may hold `declared` (the highest declared-gap sequence as decimal text, replaced atomically; an older worker ignores it and forgets a refused tail across a restart, as before). Additive `/api/v1` changes: the log answer gains `next_after` and `next` (a `c1` cursor), and the request an optional `cursor`. Behavior changes within the path version: a malformed `after`, `limit` or `step` on `GET /attempts/{id}/logs` is `400 invalid_request` instead of silently meaning 0/default/all; a log page stops at 1 MiB of frame payload (and 16 MiB decoded) with `next_after` — a client that assumed "fewer than `limit` frames means the end" must follow `next_after`, as `sentinel log show` now does; long polls share **three** subscriber slots (was four), at most **two** per user (a person or service account, across all its credentials: one user can no longer park every slot), and transfers **three** slots (was four), a download's slot being held until its body is written, so two of the eight handler permits always remain for other requests; object downloads authorize through repository grants (a tenant member without a grant on a referencing repository, and a platform admin without membership, now get `404`); a whole-object download whose stored bytes fail their digest ends short instead of completing; an upload's declared `len` is capped at 4 GiB; and touching an expired upload retires it durably.

**Fleet scheduling fixes (migration 35).** Migration 35 (`035_fleet_scheduling.sql`) adds `jobs.repo_id` (backfilled from `runs`), `jobs.pull_request` (backfilled from `run_provenance`, then kept by an `AFTER INSERT` trigger on it) and `attempts.repo_id` (backfilled from `jobs`); replaces `jobs_ready_tenant` with `jobs_ready_repo`, `jobs_conc` with a per-repository `jobs_conc`, `attempts_held_by_worker` with a covering version and `attempts_held_by_tenant` with the covering `attempts_held_by_repo`; adds `jobs_ready_pr`, `jobs_waiting` and `workers_revoked`; and drops the dead `jobs_fair`, `jobs_ready_run`, `provenance_pr`, `jobs.wait_code` and `jobs.wait_detail` (never written or never read). An older release reading a marker of 35 is refused like any newer database. Every store connection registers the deterministic SQL function `sentinel_labels_subset`; a tool that opens `metadata.sqlite` directly must call `sentinel_store::register_functions` before preparing a placement statement. Three behavior changes: a concurrency group is now held per (tenant, repository, key), as the docs already said, where placement used to key it per tenant; a group no longer lets two queued runs block each other (the older goes first); and `cancel_in_progress` supersedes a run created in the same millisecond. `GET /queue` gains the additive reason code `ready`, and its `total` now counts every waiting job of the tenant while only the page is explained ([API](api.md)). No wire change.

**Error and explain shapes.** Fields may be added; existing fields keep their type and meaning; `code` values are never renamed or reused, and new codes are additive. A breaking change is a new schema string. The error document's `schema` is a marker type (`ErrorSchema`) that deserializes only from `sentinel.error/1`, so a Rust client treats an unknown error schema as unparseable; `Explanation` is serialize-only and carries its `sentinel.explain/1` schema as a plain string, so consumers of the explain output must check `schema` themselves. Clients must tolerate unknown error codes: `ErrorCode` parses one as `ErrorCode::Unknown`, and the answer's HTTP status and `retryable` field are then authoritative. HTTP status codes are derived from `code` and follow it.

**K01 cache scopes.** Run spec format 4 adds `class` to each cache entry; format 3 blobs still decode through their own layout and upgrade every entry to `dependencies`, the only class a `class`-less schema 1 document could produce — `run_specs.format` accepts 3–4 and the format byte, not trailing-byte luck, selects the layout. Worker protocol 6 adds `Context2`: the run's tenant and the `Trust` class derived once from recorded provenance (`pull_request` → pull-request scope, everything else → protected). Workers at 1–5 still receive `Context` and scope to pull-request state; an undecodable trust byte is a protocol error, never a guess. The cache manifest and `files` blob are new formats at version 1, each a magic + format byte + reserved byte + bounded postcard body; every read failure is a typed miss, and the `Miss` name strings are the stable report vocabulary. See [cache](cache.md).

**K02 cache restore.** The miss-reason vocabulary gains `unavailable` — a transient filesystem or lease failure on the restore path, distinct from `corrupt` because the bytes may be fine and the miss is worth retrying; no existing string changes. On-disk layouts are untouched: restore only reads `current`, `manifest`, `files` and `payload/<i>/`, and adds `lease/` markers under the documented lease format. Capability bit 5 (`REFLINK`) was already allocated in the K01 protocol work; workers now actually advertise it, and only when the cache root's filesystem answered a `FICLONE` probe.

**K03 cache publication.** No format or wire change: the manifest and `files` blob stay at version 1, and nothing publication writes is read by a peer. The `SkipReason` strings (`busy`, `canceled`, `empty`, `unchanged`, and — since the cache audit fixes — `refused`) are stable log vocabulary alongside `Miss`; a reader that predates `refused` treats it like any unknown summary string. On-disk layout additions under an entry — `writing/` staging with its `.lock` marker, `lease/` markers, the `current` pointer — are described in [cache](cache.md) and are safe for older readers to ignore and for GC of any K03+ build to reap.

**K06 compiler state.** No format or wire change: the manifest and `files` blob stay at version 1, `Compat::Compiler` keeps its single `flags` field, and no `Miss` or `SkipReason` string changes. K06 pins a serving contract that was already implied and proves it with tests: a bare `class: compiler` declaration namespaces by the rendered key's stem (everything before the last `-`), which selects the entry directory and is re-verified inside it, while `flags` remains `""` — the reserved channel for a recipe-pinned namespace token (K07). Entries sealed by earlier builds recorded the same empty `flags`, so they keep serving. The `cc-<mode>-<hash>` key shape is a pipeline-side convention, not a schema field. A compiler-cache hit is bytes restored, never a cached verdict — every declared step still runs. See [cache](cache.md).

**K08 cache metrics.** AttemptSummary moves to format 3 (above): dual decode keeps formats 1–2 readable, and the added `CacheRecord` strings reuse existing stable vocabularies — `Miss::as_str`, `SkipReason::as_str`, `"hit"`/`"sealed"`/`"failed"` — plus the `Costly` names (`copied_all`, `slow`). No worker-protocol or on-disk change: the availability snapshot travels inside the existing summary blob and the process-local `Notice` channel, so the protocol range stays 1..=6 and no capability bit is allocated. The `image_present` flag is recorded only — `podman pull`'s exists fast path semantics are unchanged.

**Cursors.** Opaque to clients. `GET /attempts/{id}/logs` is the first route on the wire with the versioned `Cursor` (`c1`): its answer carries `next`, bound to the tenant, the attempt-log stream and the attempt, and the request accepts it back as `cursor` (a malformed, foreign or other-attempt cursor is `400 invalid_cursor`; `after` and `cursor` together are refused). The numeric `after=` sequence on the log routes and the run list's `before=` (returned as `next`) remain route query syntax governed by the API path version, not by this rule. The version byte changes when the layout does; old cursors are then rejected as `invalid_cursor` and the client restarts from the beginning of the stream, which is always safe because event sequences are dense and idempotent to re-read.

**Protocol 7 (Q05/Q07/Q08).** Additive only: every pre-existing message keeps its shape and enum index, and a 6-negotiated session is byte-for-byte what it was. The additions are new *variants* — `Profile`, `BulkHello`, `Transport`, the cache transfer messages — never new struct fields, because a postcard struct decodes exactly the field list its reader knows: adding a trailing field to `Hello` would make an older worker's hello undecodable and `#[serde(default)]` could never fire. A protocol-6 worker is still served exactly as before: it sends no profile, so its disk is 0 and its labels are empty, and jobs that require disk or labels simply never place there while unconstrained jobs place normally. Protocol 7 adds a second connection (bulk) to a session; a worker that negotiated it may still send bulk-class messages on the control connection, so an environment that blocks the second connection degrades in latency, never in correctness. Capability bit availability is unchanged: protocol 7 allocates no new bit.

**Protocol 8 (cache audit fixes: P07-2, P07-6, P08-C2).** Additive like 7: one new client variant appended last (`CacheCancel { attempt }`), one new `Trust` wire code (`2`, `unprotected`, JSON/scope-path name `unprotected`) that only a protocol-8 `Context2` carries, and one relaxed rule — a later `Profile` on the same session is an availability refresh instead of a protocol error. A protocol-6/7 worker is sent `pull_request` (code 1) for an unprotected job, never a code it cannot decode; the controller's cache gate admits that downgrade for it. `CacheRefused` code `7` (`aborted`) is now sent, as the terminal answer to a cancel; a protocol-7 worker never cancels and never receives it. Manifests sealed under `unprotected` carry trust code 2 in their postcard body; an older build reads such a generation as `corrupt` (a miss), and it only ever exists in the new `unprotected` scope directory an older build never looks in. The trust derivation itself changed (`Trust::derive`, docs/cache.md): manual runs, wildcard-admitted refs and unbound repositories that used to be `protected` are `unprotected`, so their first build after the upgrade is a cold cache — the intended isolation, not a format break. The summary's `publish` vocabulary gains `refused`; the remote bundle stream, manifest and `files` formats are unchanged.

**Protocol 9 (B04: P08-C8).** No message changes shape. One value gains a meaning on a 9-negotiated session only: a `CacheOffer` whose `digest` is all zero (`remote::DIGEST_AT_END`) states its digest in `CachePushEnd` instead, so the worker reads the generation once and hashes it on the way out; the controller stages it under the attempt's name and verifies the stated digest against its running hash before storing under it. A controller at 7 or 8 never negotiates that meaning: a 9 worker then keeps naming the digest up front, and a controller refuses an all-zero digest (`store`) from a session below 9 rather than staging what it could never verify. `CachePush` is also sent from a borrowed buffer now (`PushRef`); its encoding is byte-for-byte the owned message (unit-tested), so no peer can tell. The remote bundle stream, manifest and `files` formats are unchanged; the worker-local staging of a hydration moved from `writing/remote.part` to the staging generation `writing/remote.stage/`, which is worker-private — an older build's leftover `remote.part` is removed and its transfer restarts cold.

**Part 04 audit (execution hardening).** No message changes shape and it needs no protocol version of its own (the range was 1..=8 only because of protocol 8 above); what changed are semantics, each safe against the other side's older build. Negotiation now happens on every hello and its result is stored (`workers.protocol`/`capabilities`), so a worker is welcomed at what it offers now, never at its enrollment-time version; a newer worker refuses a `Welcome` outside its hello's range. The lease length is part of the protocol: `limits::LEASE_MS` (30 s) is what a renewal grants, and a worker measures its deadline as that duration from the moment it sent the renewing `Ping`, on its own monotonic clock — `Pong.lease_until_ms` stays on the wire for older workers but is not compared with a newer worker's wall clock; lowering `LEASE_MS` needs a protocol bump. `Decline` may now also hand back an acknowledged attempt that never started (its spec never arrived); an older controller refuses that decline as before and the lease expires, which is what it did anyway. `NoSpec` is definitive — a transient controller fault is retried or left unanswered, never answered `NoSpec` — and a newer worker settles it at once as `Failed(Preparation)` instead of dropping the attempt; against an older controller that still sends `NoSpec` on overload, the job ends `infra_failed` immediately rather than after the lease. `LogRefused` is sent only for permanent causes; a transient fault closes the connection so the worker rewinds and resends, and a newer worker no longer carries a refusal across a reconnect. A worker `Failed(Canceled)` for a job with no cancel requested is stored as `Failed(Runtime)`. The borrowed `Log` encoding the worker now uses is byte-for-byte the `ClientMessage::Log` encoding (unit-tested). No migration.

**Worker protocol.** The controller serves an inclusive range. A new message *variant* is additive; a new or changed struct field — optional or not — and anything else bumps the maximum and, after one release of overlap, the minimum. Postcard decodes exactly the field list its reader knows, so an "optional" trailing field makes older peers undecodable and `#[serde(default)]` never fires (see Protocol 7 above). A worker outside the range receives a typed rejection naming which side must upgrade. Capability bits are allocated once and never reused; unknown bits from newer workers are masked, not rejected.

**Limits.** Every numeric limit in `sentinel-protocol::limits` and the pipeline crate may be raised without a version change and lowered only with one, since lowering can reject previously valid input.

## Verification behind this policy

The C08 test suites exercise the failure modes the policy relies on:

- **Malformed input** (`sentinel-pipeline/tests/robustness.rs`): every truncation of every fixture and thousands of deterministic single-byte mutations compile or fail with a structured error within 500 ms; aliasing bombs, 10,000-deep nesting, 200 KB scalars, NUL, BOM, CRLF and 20,000-key mappings are rejected at their limit.
- **Duplicate requests** (`sentinel-store/tests/verification.rs`): the same key and body executes once and replays the same run; a different body is rejected; another tenant's identical key is unrelated; keys expire after 24 hours, and expired records are purged in bounded batches while live keys keep replaying. Decisions are taken inside the mutation's transaction.
- **Transaction rollback**: an idempotency record followed by a failing run creation leaves zero rows in every table.
- **Conflicting updates**: eight threads racing to lease one job produce exactly one lease and one attempt row; the rest see a typed transition error.
- **Crash and reopen**: a child process performs 25 acknowledged runs and transitions with `synchronous=FULL` and then aborts; the parent reopens the database, passes `integrity_check`, and finds every acknowledged row. This proves the ordering half of the acknowledgement policy from [storage](storage.md) — nothing is acknowledged before it has committed — against a real process death. It does not prove durability: the operating system's page cache survives a process abort, so the test would also pass with `synchronous=NORMAL` or `OFF`. That `synchronous=FULL` makes an acknowledged commit survive power loss or a kernel crash rests on SQLite's documented fsync behavior and is not tested here; testing it needs a fault-injecting VFS or real power-loss testing.
