# Schema and API compatibility policy

**Sealed storage.** New recoverable values use ciphertext format 2 with an authenticated key ID and ownership context; format 1 remains readable with legacy key ID 0. New master key files use the bounded `SNTLKEY2` keyring; existing raw 32-byte files remain readable and are converted on offline rotation. An old binary cannot read format-2 ciphertexts or the new key file. Upgrade controller/admin together, keep the matching key with every database backup and follow [sealed storage](sealed-storage.md) for rotation and restore. No SQLite or worker-protocol version changes.

Sentinel carries several independently versioned contracts. Each has one owner, one version marker and one rule for what a change may do. Nothing is versioned implicitly: if a shape is not listed here it is internal and may change with any commit.

**Secret write surface (migration 39).** Secret routes are additive under `/api/v1`; old clients may ignore them. Writes use raw value bytes, compare-and-set versions and idempotency keys. Migration 39 adds bounded metadata-only replay records. Env-file import accepts the documented literal format and commits all rows in one SQLite writer transaction; this format is a CLI/API contract documented in [secrets](secrets.md).

**Secret delivery (run spec 6, migration 40, protocol 10).** Run spec format 6 adds optional job `registry_auth`, step environment-secret names and secret-file targets; readers still decode formats 3–5 through their shadow layouts. Migration 40 marks jobs that require worker secret delivery so dispatch will not offer them to workers that lack protocol 10 or `SECRET_DELIVERY` bit 9. Protocol 10 appends `SecretBegin`/`SecretChunk`; each transfer is attempt- and fence-bound, ordered, and capped at 1 MiB. The controller resolves only declared bindings and records versioned use in the same writer transaction that checks the acknowledged attempt and opens the sealed values. Workers reject missing, extra, malformed or conflicting targets before execution. Every new attempt, including a rerun, receives the then-current active version. Secret values are not added to the run spec blob or SQLite plaintext; the worker keeps them in private per-attempt files outside workspaces, caches and artifacts, redacts before spool persistence, and reaps crash leftovers. A step that receives environment targets runs behind a `/bin/sh` wrapper that sources them from `/run/sentinel-env` (images already need `/bin/sh`), and a secret-bearing step runs in a container cleared of every process earlier steps left running; no wire message or stored shape changed, so the protocol stays 10. Upgrade controllers and workers together for secret-using jobs; older workers remain eligible for jobs with no secret targets. See [secrets](secrets.md), [protocol](protocol.md#protocol-10-secret-delivery) and [executor](executor.md#the-image-pull).

**Operator-granted job egress (worker configuration).** The worker key `job_network` (`"none"`, the default, or `"egress"`) is new and refused for the server role. With `"egress"` job containers get outbound network through rootless pasta and the worker adds the label `egress` to its profile. No wire message, run spec or stored shape changed; an older worker refuses a configuration file that sets the key. See [executor](executor.md#job-network). For microVM guests (TODO M05) the same key gives the guest one network interface behind an nftables policy; see the microVM network entry below.

**Job runtime (run spec 7, migration 54, capability bits 10–16).** Pipelines may state `runs_on.os` (`linux`, `windows`) and `runs_on.isolation` (`container`, `microvm`, `native`). A spec that states neither is still written as format 6, byte for byte, so workers that predate format 7 keep running it; only a spec that states one is format 7, and readers decode formats 3–7: 3–6 through their shadow layouts as before, 7 as the current layout. The controller also accepts every readable format where it used to require the current one when reading a stored spec. Migration 54 adds `jobs.runtime`, the capability bits a job requires (0 when it states neither); older binaries cannot open that database, since they would place a microVM or Windows job on any worker. Workers state `KVM` (bit 10), `KVM_NESTED` (11), `ISOLATION_CONTAINER`, `ISOLATION_MICROVM`, `ISOLATION_NATIVE` (12–14), `OS_LINUX` and `OS_WINDOWS` (15–16); older controllers mask them away. Placement gives a job that states nothing to a worker that states no runtime bits (an older worker) or states `OS_LINUX`, and a job that states one only to a worker with every bit it requires, so an older worker never receives a spec it cannot read. A new worker key, `isolation` (`"auto"`, `"container"`, `"microvm"`), picks the default executor and is refused for the server role. No wire message changed. See [pipeline schema](pipeline-schema.md) and [plan 16.8](../plan.md#168-microvm-execution-on-kvm-hosts).

**One-click GitHub App setup (migration 56, `056_github_app.sql`; U17).** Adds `github_app` (at most one row: the App registered through GitHub's manifest flow — id, slug, name, owner, owner id, page, OAuth client id, creator and time in plain columns; the private key, client secret and webhook secret sealed with `master.key` under a context naming the column and the App id; a trigger allows only a forward reseal) and `github_app_states` (digest-only one-time states, purpose 1 manifest or 2 installation, bound to the account, the session id and, for an installation, the tenant; `used_ms` never returns to NULL; indexes by account and by expiry). **Not declared readable by 55**: an older binary's `admin key reseal --retire` and start-up key check do not know the three sealed columns and could retire the key that opens them, and an older controller would silently ignore the stored App; roll back with the pre-migration copy (`metadata.sqlite.v055`) or a backup ([upgrades](upgrades.md)). Nothing changes on upgrade: no row exists until a platform administrator runs the flow, and a deployment configured by `github-app.json`, `github-webhook.json` or `github-sign-in.json` keeps working exactly as before — the files take precedence and the new routes answer `409` (`details.reason: "files"`). New audit events 76 `github-app-created` (detail `app <id> <slug>`) and 77 `github-app-state-refused` (detail `<manifest|installation> <unknown|foreign|replayed|expired>`, at most five per account in ten seconds); installation binding reuses 26 `installation-bound` (and 57 `platform-override` for an administrator acting outside the tenant). New error code `upstream_failed` (502, not retryable; clients that predate it read `unknown`, [protocol](protocol.md#structured-errors)). Additive API: `GET /api/v1/github/app`, `POST /api/v1/github/app/manifest`, `POST /api/v1/github/app/conversion`, `POST /api/v1/github/app/installation`, `POST /api/v1/tenants/{slug}/github/installation-url` ([GitHub App](github-app.md#http-contract)). Behaviour changes: the GitHub App, its webhook secret and GitHub sign-in may now come from the database and take effect without a restart (the components share one set-once holder; the hook route reads its secret with one atomic load); the maintenance tick purges expired states. `sentinel_intake::Resolver::new` and `Poll::start` take `impl Into<sentinel_github::app::Current>` (an `Option<Arc<App>>` still converts), and `sentinel_api::Options` gains `github_app`. No worker protocol, run spec or pipeline change.
**Link admission state (migration 59, `059_link_admission.sql`).** Adds `link_known_sources(source, seen_ms)` (the 16-byte address keys that authenticated a worker within the last day, loopback never stored, capped at 4,096 rows and pruned by the writer that refreshes them) and `worker_enrollment_refusals(window_ms, peer, recorded, suppressed, summarized)` (hourly counters of refused enrollments per hashed peer, pruned after seven days, at most 64 peers plus one shared row per hour) with a partial index over unsummarized hours. Both tables are additive and nothing reads them but the controller, but the migration is **not** listed in `READABLE_BY`: an older binary is not offered to keep running on the new schema. Behaviour changes with it, none on the wire (worker protocol unchanged, still 1..=10): a wrong enrollment secret writes at most 5 audit rows per peer and 50 per hour and is otherwise counted (a summary row follows in the next hour), an enrollment secret that would redeem skips the guessing rate limiter, and an unenrolled identity arriving from loopback is refused `Unavailable` when the handshake pool is past its unreserved part. See [worker link](worker-link.md).
**Public body slots behind a trusted proxy and the setup status budget (no schema change).** Clients a trusted proxy forwards together hold at most 3 of the 4 public body slots (`sentinel_api::PROXY_BODIES`), each for at most 5 seconds including the slot wait (`PROXY_BODY_TIME`); direct clients keep 10 seconds and always have one slot. A forwarded body that cannot get its share in that time is turned away as before (`rate_limited`, `503 temporarily_unavailable` on the OAuth routes), so a slow upstream that streams a login or webhook body for longer than 5 seconds now fails where it used to be allowed 10. `GET /api/v1/setup` gains a per-client admission budget while setup is open (burst 10, one more per 2 s, 20 per second across clients; `429 rate_limited` with `details.retry_after_ms`), and an open answer is cached for one second, so a closure by the host-local `admin bootstrap` can show up to a second late. A closed answer is unchanged and unbudgeted. The five-wrong-tokens lock is unchanged; `sentinel admin bootstrap` is documented as its escape. No wire format, error shape, migration or worker protocol change ([API](api.md#client-keys-behind-a-reverse-proxy), [admission](admission.md#first-run-setup)).

**Auto-join generation and client keys behind a proxy (migration 61, `061_auto_join_generation.sql`).** Adds `auto_join_state(id, generation)` (one row, starting at 1) and `users.auto_join_gen` (`NOT NULL DEFAULT 0`). `auto_join::set_rules` compares the rules it is given, after the same refusals as before, with the stored ones and rewrites them and raises the generation only when the effective set differs, so the controller's rewrite at every start no longer moves it. A session is issued with one conditional `UPDATE users SET auto_join_gen = …` that matches only an eligible person (admitted, active, verified address) whose column differs from the generation, and `auto_join::apply` runs only when it changed the row: at the first eligible sign-in after the upgrade (every existing person is behind generation 1) and after a rule-set change, no longer in every `issue_session` transaction. Verifying an address still calls `apply` directly. Visible effect: an organization that stops being refusable (a suspension lifted, a GitHub binding removed) without the rule set changing admits people at their next verification or the next rule change, not at every sign-in. Not declared readable by an older schema: an older controller rewrites the rules without raising the generation, so a person it never re-checked would stay behind the rule change. Roll back from the pre-migration copy, as `readable_by` defaults. Behaviour with no schema change: a request from a trusted proxy that sends no valid `X-Forwarded-For` is keyed by the proxy's connection (address and source port) for the per-client rate limits, the sign-in lockout pair and the public-body slot, where it was keyed by the proxy's address alone and all clients behind it shared one key; client registrations per registrant keep the address key. A proxy that names the client is unaffected. No wire format, error shape or worker protocol change ([API](api.md#client-keys-behind-a-reverse-proxy), [admission](admission.md#domain-auto-join)).

**Removal tombstones and held GitHub organization names (migration 60, `060_removal_tombstones.sql`).** Adds `membership_removals(tenant_id, user_id, removed_ms)`, one row per person and organization, written by `auth::remove_membership` in the removing transaction and consulted only by `auto_join::apply`, which no longer re-adds a person who has one (an administrator's explicit add is unaffected and the next removal rewrites the row). Adds the partial expression index `installations_by_github_login` on `lower(account_login)` for GitHub installations; behaviour: `POST /orgs` answers `409` for a name equal to the login of an account the App is installed on (platform administrators exempt), where it used to create the organization. Not declared readable by an older schema: an older controller removes members without writing a tombstone and so would silently reopen the rejoin, and it does not hold GitHub names; roll back from the pre-migration copy, as `readable_by` defaults. No wire format, error shape or worker protocol change ([admission](admission.md), [tenancy](tenancy.md)).

**Session grant provenance and MFA start audit (migration 55, `055_session_grant_provenance.sql`).** `oauth_grants.created_session` is an immutable nullable 16-byte session identifier with no foreign key, so service-grant provenance survives session expiry and purge; existing rows stay NULL. A partial `(created_by, created_session)` index supports exact-session and per-user revocation. New session-minted service grants revoke by that identifier, including during logout-all after the session row is gone; only legacy NULL rows use the former timestamp-window fallback. Not declared readable by 54 because older issuance statements do not populate the provenance needed by the new revocation rules. Audit event 75 `mfa-enrollment-started` records each successful browser or host-local enrollment start without seed or URI detail; conflicts add no row. No wire format or worker protocol change ([OAuth](oauth.md), [step-up](step-up.md)).

**Minted-grant revocation index and artifact reapply scope (migration 57, `057_minted_grants_unattributed.sql`).** Adds the partial index `oauth_grants_by_unattributed_minter` (`oauth_grants(created_by, created_ms) WHERE kind = 3 AND created_session IS NULL AND revoked_ms IS NULL`), which the timestamp-window revocation of service grants without session provenance (`oauth::REVOKE_MINTED_LEGACY`) searches instead of every unexpired grant. Index only: declared readable by 56 (`READABLE_BY`), so a binary at schema 56 keeps running on the result; no stored shape, wire message or statement of an older binary changes. A repository-scoped artifact reapply step now probes each artifact's run by primary key (`EXISTS`) instead of building a set of the repository's runs per batch; the cursor and the result are unchanged ([storage](storage.md#statement-plans), [retention](retention.md#reapply-plans)).

**Delivery authentication and the secret gate (migration 58, `058_delivery_authentication.sql`).** Adds `webhook_deliveries.authentication` (`INTEGER NOT NULL DEFAULT 0`, `CHECK IN (0, 1, 2)`: 0 observed by the controller, 1 generic hook secret presented, 2 forge signature verified), written with the delivery by the intake adapter and immutable (the recreated `delivery_terms_immutable` trigger refuses a change). Rows from before the migration are backfilled from their provider (`github` 2, `generic` 1, anything else 0), which is exact because the ingest paths accepted a delivery only after that check. The secret gate no longer tests `trigger != 'manual'`: a run receives secrets only when its provenance names a delivery with `authentication` 1 or 2 (and the trigger is not `manual`), so polled runs, and any run whose provenance does not name an authenticated delivery, receive none. Behavior change: runs created by ref polling no longer receive bound secrets, and the delivery refusal text is now `secret NAME: withheld from a run without a verified webhook delivery`. Declared readable by 57 (`READABLE_BY`): a binary at schema 57 inserts deliveries without the column, which records 0 and only withholds secrets. `intake::NewDelivery` gains a required `authentication` field (library API); no wire message, error code or pipeline schema changes ([secrets](secrets.md#who-may-cause-a-delivery)).

**Log lookups by line and wall time (no migration, no format change).** `sentinel-store::logs` gains `seek_line` and `seek_time`, which read the `lines` and `ms` fields the `SNLI` format 1 index already carried; the index, segment and end-marker formats are unchanged and a log written before this change is looked up the same way. Both answer with a plain sequence number, so the event cursor (`c1`), the log page and the API are unchanged; no route exposes the lookups yet. The writer's line count is unchanged (it now counts with `memchr`). See [logs](logs.md#on-the-controller-segments-index-and-the-end-marker).

**Log first-hole record (additive file; no migration, no change to the `SNLI`, `SNLH`, `SNLE` or segment formats).** Each attempt's log directory may gain a 14-byte `jump` file (`SNLJ` | format `u16` = 1 | `u64` first missing sequence), written once, at the log's first sequence jump and before the jumping frame is stored (temporary file, fsync, rename, directory fsync), and re-derived by decoding on reopen when an uncovered segment shows a jump. `LineSeek.exact` is now also false for a line that starts at or after that sequence, because a hole filled later leaves no other trace (the hole list and the end marker keep only unfilled ranges) and the line counts stored order; lines before the first jump stay exact. A file that exists but cannot be decoded reads as `0` (nothing is exact). An in-order log never gets the file. Older binaries never open it (`segs` parses only `seg-N` names and temporary files are swept by their suffix), so a rolled-back controller reads such logs as before; a writer from before this entry that continues one of these logs opens and heals holes without updating the record, which only matters for a hole it opened after the first one. Logs written before this entry have no record: a live one takes its lowest open hole as the first hole on reopen, and a finished or sealed one cannot say whether it ever healed a hole, so `exact` is promised only for logs written after the change. No route exposes the lookups yet (D04 will); the event cursor and API are unchanged. See [logs](logs.md#on-the-controller-segments-index-and-the-end-marker).

**Descriptor-relative `Objects::materialize` (no format change).** On Unix, `materialize` resolves the destination once and creates every component relative to the directory descriptor before it without following symlinks, so a destination changed during the extract by someone who cannot already write the destination cannot redirect a write. That is the whole defence: the destination itself must be a private directory on every platform (mode 0700, owned by the caller, not under a shared or world-writable directory), because the walk still follows symlinks in the destination's ancestors, enters a subdirectory a foreign user pre-created, and creates directories 0777 and files 0666 (less the umask) before the entry's mode is applied, which is skipped for mode 0. No controller path calls it; a new caller creates the destination itself. The error contract is the same (`InvalidInput("materialize path")` for a symlink or file where a directory belongs, `InvalidInput("materialize target")` for an existing target); no stored shape changed ([storage](storage.md#resumable-uploads-reads-and-materialization)).
**Controller-owned worker enrollment policy (migration 62, `062_worker_enrollment_policy.sql`; audit events 90 and 91).** Adds to `worker_enrollments` the approved host ceilings (`cpu_ceiling_millis`, `memory_ceiling_bytes`, `disk_ceiling_bytes`, each NULL or positive), the operator `priority` (-100..100, 0 neutral) and `tailcat` (1: redemption must present the worker's Tailcat node key; 0: direct TLS only); to `workers` the same ceilings and priority, `node_key` (the 32 bytes behind `nodekey:<64 hex>`, immutable once set, unique over live and revoked rows alike so a retired key is never admitted again) and `uninstall_ms` (set once, never cleared); and a partial index over pending uninstalls. The triggers `worker_enrollment_update` and `worker_update` are recreated: enrollment terms (ceilings, priority, `tailcat`) and the worker's node key are immutable through raw SQL, and ceilings and priority on a *worker* change only through `workers::set_policy`. Redemption copies the enrollment's ceilings and priority onto the worker in the transaction that spends the enrollment; an enrollment whose `tailcat` flag disagrees with whether a node key was presented is refused as a value (`WorkerEnrollmentRefused`) and stays unspent, and a node key or fingerprint already bound to any worker is `Conflict`, also leaving it unspent. `dispatch::report_capacity` now stores the reported size under the worker's ceilings (an unreported disk takes the disk ceiling), so a ceiling is a hard limit, and a reduction never kills accepted attempts: it only drives the free room negative. Additive store API, none removed: `workers::issue_enrollment_with`, `redeem_bound`, `authenticate_bound`, `admitted_node_keys`, `set_policy`, `request_uninstall`, `uninstalling`, `settle_uninstalls`, `parse_node_key`; `issue_enrollment`, `enroll` and `redeem` keep their signatures and mean neutral policy and no node key. Audit events 90 `worker-uninstall-requested` and 91 `worker-uninstalled`. Not declared readable by 61: an older controller would redeem enrollments without binding the node key or copying the policy and would report capacity without the ceilings, so it is refused like any newer database; roll back with the pre-migration snapshot (`metadata.sqlite.v055`) or a backup ([upgrades](upgrades.md)). No wire change. This entry is the enrollment-store half of Q11; the enrollment API and bootstrap script, and migration 63's node-key authorization and allow-list feed (the entries that follow), complete the controller side ([worker link](worker-link.md#approved-policy-the-bound-node-key-and-uninstall), [storage](storage.md)).

**Deadline clock, report durability, disk admission and bounded maintenance (no migration, no format bump, no protocol change).** Behaviour changes, none of which alter a stored shape or a wire message. (1) Lease, acknowledgement, queue-timeout, execution-overrun and idempotency decisions are taken on the controller's deadline clock (`UnixMillis::steady()`: wall clock at the first read, then monotonic), and the columns they compare against hold values of it, so a wall-clock step no longer expires leases or queue waits ([core contracts](core-contracts.md#timestamps)); a restart re-anchors from the wall clock and startup reconciliation behaves as before. (2) A worker acknowledgement or report the store refused transiently (writer unavailable, a write of unknown outcome, reader overload, a busy database) is no longer dropped as stale: the controller keeps it (at most 256, at most 5 minutes), retries it first in every dispatch pass, and leaves its attempt out of lease expiry meanwhile; a worker keeps a sent terminal verdict in its heartbeat's held list until the controller stops counting the attempt (the `stop` list of its next answer), which keeps the lease renewed, and sends it again every 5 s. Duplicates are stale at the controller and change nothing; a controller restart while a verdict is waiting still settles the attempt by expiry, as for any report that never arrived ([worker link](worker-link.md)). (3) A terminal report whose summary is over 32 KiB (`MAX_SUMMARY_BYTES`, also the column's check) now keeps its verdict and records no summary, and the session is no longer closed for it; before, the store rolled the whole report back and the lease then failed the job. (4) Scratch disk: for a worker that negotiated the profile protocol (7 and later), `disk_bytes = 0` means none offered, so no job that declares scratch disk (every compiled job does) is placed on it; workers older than 7 cannot report disk and keep their CPU-and-memory admission; a hello below protocol 7 clears the stored disk figure along with the labels and warm images. This is what `Profile::disk_bytes` and the worker's `profile_disk` always documented. (5) Re-stamping retention after a policy change is batched: `retention::set` commits the policy and the first 512 rows and returns a `Reapply` cursor, and `retention::finish_reapply` continues it one bounded write at a time (the API and `sentinel admin tenant storage` do); a crash between the two leaves later rows with their previous deadlines until the policy is set again. `Store::checkpoint` waits at most 200 ms for readers and returns `Checkpointed::Partial` when a reader kept part of the log.

**Manual-remote HTTPS admission and canonical-only OAuth redirect URIs (no migration, no format bump, no protocol change).** Two admission checks are stricter than the earliest builds; neither alters a stored shape or a wire message. (1) `POST …/runs` on an unbound repository admits only an unauthenticated `https://host[:port]/path` remote in the canonical grammar of a source binding whose host is a public DNS name; a local path, `file://`, `ssh://`, scp syntax, `git://`, plain `http://`, `ext::`, userinfo, IP literals in any notation, bare hostnames and private-use suffixes now answer `400 invalid_request` ("invalid manual source remote"), and the worker re-applies the policy and pins the resolved addresses, so a spec that bypassed the API is refused there too. A client or script that dispatched manual runs against an internal or non-HTTPS remote must bind the repository to a source, or the operator must list the exact authority in `SENTINEL_MANUAL_DESTINATIONS` on both the controller and every worker ([sources](sources.md)). (2) `POST /oauth/register` and Client ID Metadata Documents accept a redirect URI only in canonical spelling: an HTTPS domain URI that the URL parser would not rewrite (no stripped tabs or line breaks, no uppercase host, no bare host without a path), matched exactly, or an HTTP loopback URI on `127.0.0.1`, `[::1]` or `localhost` (stored without its port, matched on any port with the same host and path); non-loopback HTTP, userinfo, query and fragment are refused. A client that registered a non-canonical spelling and compares redirect strings itself must register the canonical form ([OAuth](oauth.md)). Skew: both checks run in the controller (and, for manual remotes, the worker); a mixed-version fleet differs only in that an older worker may still fetch a remote the newer controller would have refused at admission, and clients already registered keep the redirects they have. Rollback to an older binary restores the looser admission and needs no data change.
**Per-host accounting (Q12; no migration, no wire shape change).** Behavior changes only. (1) The `host_id` a worker states in its `Profile` is now a digest of `/etc/machine-id` joined with the kernel boot id (the machine id alone when the boot id cannot be read; the boot id alone, under its own domain, when there is no machine id; all zeros only when neither exists), and the store records it scoped by the identity's architecture (`dispatch::scope_host`). The field keeps its type and meaning (identities stating the same value are one physical host); what changes is that clones of one image and identities of different architectures no longer share a host, a container without a machine id now shares one with its kernel's other identities, and the value changes at every reboot. A controller older than this change keeps comparing the stated values as before; a worker older than this change states the machine id alone and is accounted as before. (2) A worker whose operator states no `disk_bytes` re-sends its measured scratch disk in a repeated `Profile` (protocol 8 and later, the message that already refreshes images and cache bytes) when it moved by 256 MiB or a sixteenth; a controller that ignores a repeated profile keeps the connect-time figure. See [storage](storage.md#fleet-placement) and [worker link](worker-link.md).

**Per-job storage enforcement (Q12; no migration, no wire shape change).** A rootless-container job that writes more than its declared `resources.disk` into the workspace and its `/tmp` together is stopped by the worker's storage guard and fails with the existing class `command_failed` (step outcome `failed`) and a verdict naming the limit; no failure class, step outcome or summary shape is added. **MicroVM end-to-end parity (agent protocol 3, image marker format 2; no migration, no summary or wire change).** The host-to-guest agent protocol (`sentinel_protocol::agent`, never exposed beyond the worker and its own initramfs) moves from version 2 to 3: `Request::Wipe { dirs }` empties the per-step secret directories, `Request::WaitIdle { timeout_ms }` is answered by `Reply::Idle(bool)` and lets a polite cancel tell a graceful end from a forced one, `Request::MemoryLimit { bytes }` caps the memory cgroup the steps run in, and `Exec` gains `user` (the image's `USER`, empty for root). The guest image marker (`<key>.json`) moves to `format` 2 by adding `user`: a format 1 marker is a cache miss and the image is rebuilt once. A guest now has 64 MiB more memory than the job reserves (the machine shape, and so every snapshot's name, changes with it; the scope that caps the VMM already allowed 256 MiB of overhead). The Firecracker configuration gains a custom CPU template that masks `vmx`/`svm`; it is part of every snapshot's name, so snapshots taken before are misses and are rebuilt. Worker behavior that changes with it: a step in a microVM runs as the image's `USER`, receives its secrets per step and loses them after it, runs without core dumps and with `no_new_privs`, and a cancel that the executor receives before the run spec cancels the attempt instead of being dropped (this last fix also applies to containers). The pipeline schema (1), the run spec (7), the migrations (54, none added), the worker link protocol, the capability bits (10-16) and the attempt summary (format 4) are unchanged.

**GitHub check link base and rerequest receipts (no migration, no wire or stored-shape change).** Behaviour changes. (1) `github-app.json` `public_url` must be an origin: a path, query or fragment now stops startup with `public URL must be an origin without a path`, where before it was accepted and produced dead links; remove the path (the web interface is served at the root of its origin). (2) A check's `details_url` is published only when its base is an `http(s)` origin with no path; a server `public_url` with a path prefix (still valid for the API and the OAuth issuer) therefore publishes checks without a link unless `github-app.json` names the web interface's origin. (3) A rerequest receipt can now record the outcome `source_not_allowed` (additive; a receipt reader must accept an outcome it does not know), when every candidate of the head was refused by its repository binding. A candidate that is refused no longer fails the whole event. See [checks](checks.md#details-link-contract) and [configuration](configuration.md).

**External copy, mail outbox and recovery hardening (no migration, no protocol change).** Additive reporting only. `GET /admin/storage` `s3` gains `parked_items`, `parked_objects`, `parked_bytes` and `last_refusal`, and `local_faults` now counts each object once instead of once per pass. `/metrics` gains `sentinel_s3_local_faults_total`, `sentinel_s3_parked_items`, `sentinel_s3_parked_bytes`, `sentinel_mail_outbox{state}` and `sentinel_mail_oldest_pending_seconds`. `sentinel admin objects recover` and the restore report gain `evicted_leftovers`, and startup recovery now removes the local file of an object whose row is marked evicted. The controller logs `s3_items_parked`, `mail_degraded` (with a `cause`) and `mail_recovered`. A mail `401`, or a `403` named for the key or the sender domain, no longer gives up the message: the row is kept and the lane pauses ([configuration](configuration.md#email-delivery)). Nothing the database, the worker link, the run spec or the pipeline schema carries changes; the `sentinel-s3` client gains `Client::read_object` and the `READ_CHUNK_BYTES` and `MIN_SEND_BYTES_PER_SEC` constants, and `Failure::Service` and the `Health` and `Cause` types are in-process.

**Store maintenance: backup modes, backup completeness and skipped rows (no migration, no format change; Wave 0 part C).** Additive: the readiness code `backup_incomplete` (the last scheduled backup recorded missing or corrupt objects), the gauge `sentinel_backup_last_objects_lost`, the counter `sentinel_maintenance_rows_skipped_total`, the log event `maintenance_rows_skipped`, `target_open_to_others` in the scheduler's `last_backup` and in `admin backup create`'s report, and `data_dir_open_to_others` in `admin restore`'s; `sentinel.backup/1` and `backup.json` are unchanged. Behavior: a backup directory, its staging directory and every file in it are created with mode 0700 and 0600 (they followed the umask), and a restore creates its data directory and files the same way; an existing directory keeps its mode and is reported. The scheduler's first backup after a start waits what is left of the interval since the newest backup in the target instead of a whole interval (it runs at once with no readable backup), and a maintenance pass kept out by a backup is retried at the next tick instead of after `sweep_interval`. A full batch of upload and lease sweeps, artifact expiry, reclaim, log stamps, log expiry or aborted-upload purges is followed by up to 15 more batches in the same pass. A row whose id column does not decode is passed over and counted by the log stamp and expiry reads and the replication queue reads (it used to fail the whole batch); a backup still refuses to complete on one. The reference index already passed over a manifest file it could not read or decode and now counts it too, under the table `manifests` and the tenant, so the counter also rises for a manifest file that is unreadable (a transient read error included); an undecodable tenant or kind in that table still fails the batch. The counter and the latest-row record are process-wide and rise every time a batch meets a row, including each round of a catch-up and each tick of the replicator, so a persistently damaged row climbs the counter repeatedly. A dedup seal of an unreferenced object restarts that object's 24-hour reclaim grace.

**Administrator lists of enrollments and hosts (no migration, no wire message or stored shape change).** Additive read routes for platform administrators: `GET /api/v1/admin/worker-enrollments?pool&before&limit` (enrollments newest first, `next_before` the last entry's `created_ms` or `null`; terms and state only, never a secret or a Tailcat address) and `GET /api/v1/admin/workers?pool` (every live worker with `connected`, `software`, `transport`, `uninstall_requested_ms` and `host` with the `host_view` fields already named in the worker-policy entry above: `approved`, `reported`, `effective`, `reserved`, `over_cap`; never a fingerprint, node key or enrollment secret; it takes only `pool`, so it is not paged). Both need `platform:admin` and no step-up, and write nothing; fields are added, never removed or retyped. An older controller lacks the routes ([API](api.md), [worker enrollment](worker-enrollment.md)).

**Platform administrators are not tenant members (no migration, no wire message or stored shape change).** Behaviour tightening. `auth::require_tenant_member`, which gates beginning an upload and the status, chunk, commit and abort routes of an upload (`/tenants/{slug}/uploads`, `/uploads/{upl}`), the tenant check of `GET /queue` and read access to tenant-scope secret metadata, no longer admits a platform administrator who has no membership; before, such a session passed with no step-up, reason or audit row, reserved staging space against the tenant's quota and listed its tenant-level secret names. It now answers `not_found` like any other non-member (`GET /queue` for such a tenant is `not_found`, where it was an empty list). A platform administrator who is a member is unchanged, and reaching a tenant without a membership stays the audited override of [step-up](step-up.md#platform-scope-is-not-data-access). The write side of tenant secrets already required an administrator membership. No documented behaviour changes.

**Oversized consent and device forms (no migration, no wire message or stored shape change).** `POST /oauth/authorize` with a form over `MAX_OAUTH_FORM_BYTES` now answers `413 invalid_request` in the OAuth error shape (and `503 temporarily_unavailable` when no public body slot frees up) instead of an HTML `400`; the signed-in `POST /device` answers `413` as an HTML page instead of `400`. Any other unreadable form keeps the HTML `400`. These are browser pages, not a client contract ([API](api.md#body-limits), [OAuth](oauth.md)).

**Bench record build block, shuffle seed and B05 stamp (no migration, no protocol change).** Additive changes to benchmark records, read by no running Sentinel; no marker changed. `sentinel-bench/1` gains an optional `build` object (`commit`, `dirty`, `profile`, `target`, `debug_assertions`, `binary_blake3`): the values are fixed when the runner is compiled, and an unknown value is absent. `source` keeps its keys and now holds the build-time commit and tracked-change state (a runner built outside a git checkout still asks the checkout when it starts); a `--contract` run now refuses a build with debug assertions. `sentinel-bench/b03/1` records of `b03b-ack.py` gain `shuffle_seed` and a per-sample `seq`. The B05 records (`b05-*`, no schema marker) now carry the common `build` and `host` stamp (`bench/stamp.sh`), the driver's hardware block moves from `host` to `hw`, and `build.dirty` is a boolean instead of a string; no B05 record is committed, so none is rewritten. `sentinel-bench/q13/1` records of a real run and `sentinel-bench/m02/1` records gain `build`, and `m02`'s `host.hostname` is now always an anonymized label. Existing committed records are not rewritten. No field was removed or renamed in a marker that exists ([benchmarking](benchmarking.md#record-format-sentinel-bench1)).
