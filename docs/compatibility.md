# Schema and API compatibility policy

**Sealed storage.** New recoverable values use ciphertext format 2 with an authenticated key ID and ownership context; format 1 remains readable with legacy key ID 0. New master key files use the bounded `SNTLKEY2` keyring; existing raw 32-byte files remain readable and are converted on offline rotation. An old binary cannot read format-2 ciphertexts or the new key file. Upgrade controller/admin together, keep the matching key with every database backup and follow [sealed storage](sealed-storage.md) for rotation and restore. No SQLite or worker-protocol version changes.

Sentinel carries several independently versioned contracts. Each has one owner, one version marker and one rule for what a change may do. Nothing is versioned implicitly: if a shape is not listed here it is internal and may change with any commit.

**Secret write surface (migration 39).** Secret routes are additive under `/api/v1`; old clients may ignore them. Writes use raw value bytes, compare-and-set versions and idempotency keys. Migration 39 adds bounded metadata-only replay records. Env-file import accepts the documented literal format and commits all rows in one SQLite writer transaction; this format is a CLI/API contract documented in [secrets](secrets.md).

**Secret delivery (run spec 6, migration 40, protocol 10).** Run spec format 6 adds optional job `registry_auth`, step environment-secret names and secret-file targets; readers still decode formats 3–5 through their shadow layouts. Migration 40 marks jobs that require worker secret delivery so dispatch will not offer them to workers that lack protocol 10 or `SECRET_DELIVERY` bit 9. Protocol 10 appends `SecretBegin`/`SecretChunk`; each transfer is attempt- and fence-bound, ordered, and capped at 1 MiB. The controller resolves only declared bindings and records versioned use in the same writer transaction that checks the acknowledged attempt and opens the sealed values. Workers reject missing, extra, malformed or conflicting targets before execution. Every new attempt, including a rerun, receives the then-current active version. Secret values are not added to the run spec blob or SQLite plaintext; the worker keeps them in private per-attempt files outside workspaces, caches and artifacts, redacts before spool persistence, and reaps crash leftovers. A step that receives environment targets runs behind a `/bin/sh` wrapper that sources them from `/run/sentinel-env` (images already need `/bin/sh`), and a secret-bearing step runs in a container cleared of every process earlier steps left running; no wire message or stored shape changed, so the protocol stays 10. Upgrade controllers and workers together for secret-using jobs; older workers remain eligible for jobs with no secret targets. See [secrets](secrets.md), [protocol](protocol.md#protocol-10-secret-delivery) and [executor](executor.md#the-image-pull).

**Operator-granted job egress (worker configuration).** The worker key `job_network` (`"none"`, the default, or `"egress"`) is new and refused for the server role. With `"egress"` job containers get outbound network through rootless pasta and the worker adds the label `egress` to its profile. No wire message, run spec or stored shape changed; an older worker refuses a configuration file that sets the key. See [executor](executor.md#job-network).

**Job runtime (run spec 7, migration 54, capability bits 10–16).** Pipelines may state `runs_on.os` (`linux`, `windows`) and `runs_on.isolation` (`container`, `microvm`, `native`). A spec that states neither is still written as format 6, byte for byte, so workers that predate format 7 keep running it; only a spec that states one is format 7, and readers decode formats 3–6 through their shadow layouts as before. The controller also accepts every readable format where it used to require the current one when reading a stored spec. Migration 54 adds `jobs.runtime`, the capability bits a job requires (0 when it states neither); older binaries cannot open that database, since they would place a microVM or Windows job on any worker. Workers state `KVM` (bit 10), `KVM_NESTED` (11), `ISOLATION_CONTAINER`, `ISOLATION_MICROVM`, `ISOLATION_NATIVE` (12–14), `OS_LINUX` and `OS_WINDOWS` (15–16); older controllers mask them away. Placement gives a job that states nothing to a worker that states no runtime bits (an older worker) or states `OS_LINUX`, and a job that states one only to a worker with every bit it requires, so an older worker never receives a spec it cannot read. A new worker key, `isolation` (`"auto"`, `"container"`, `"microvm"`), picks the default executor and is refused for the server role. No wire message changed. See [pipeline schema](pipeline-schema.md) and [plan 16.8](../plan.md#168-microvm-execution-on-kvm-hosts).

**Session grant provenance and MFA start audit (migration 55, `055_session_grant_provenance.sql`).** `oauth_grants.created_session` is an immutable nullable 16-byte session identifier with no foreign key, so service-grant provenance survives session expiry and purge; existing rows stay NULL. A partial `(created_by, created_session)` index supports exact-session and per-user revocation. New session-minted service grants revoke by that identifier, including during logout-all after the session row is gone; only legacy NULL rows use the former timestamp-window fallback. Not declared readable by 54 because older issuance statements do not populate the provenance needed by the new revocation rules. Audit event 75 `mfa-enrollment-started` records each successful browser or host-local enrollment start without seed or URI detail; conflicts add no row. No wire format or worker protocol change ([OAuth](oauth.md), [step-up](step-up.md)).

**Default failure view bounded as a whole.** `GET /attempts/{id}/failure` without `budget` now bounds the whole body at 8 KiB instead of only its text, by dropping the oldest tail frames, trimming the front of the oldest kept one (`cut:true`, a new optional frame field), shortening long diagnostic messages (`message_cut:true`, a new optional diagnostic field) and only then dropping diagnostics, as the 64 KiB ceiling already did. Requests that pass `budget` are unchanged. A client that wants the larger default body asks for `budget=8192`. See [API](api.md).

**Pushed cancellation (protocol 11).** Protocol 11 appends `ServerMessage::Cancel { attempts }` (1 to 1,024 attempt ids). A controller sends it to a protocol-11 session as soon as a cancel commits through the API, a manual dispatch or an intake run that supersedes a running one, instead of leaving the cancel for the next heartbeat; the heartbeat's `Pong.cancel` still repeats every pending cancel, so a lost push changes nothing. A worker refuses the message below protocol 11 and treats it exactly as a `Pong.cancel` entry. Nothing stored changed. A protocol-10 worker keeps the heartbeat delivery; upgrade workers to get the shorter cancel-to-termination time. See [cancellation](cancellation.md#cancellation-is-desired-state) and [protocol](protocol.md#protocol-11-pushed-cancellation).

**MCP resource audience (migration 41).** OAuth grant, authorization-code, and device-code rows gain an immutable `resource` column (1 = `{issuer}/api/v1`, 2 = `{issuer}/mcp`). Existing `audience` columns and rows remain API=1 for compatibility with prior constraints; new access-token validation uses the resource audience. MCP authorization, code exchange, and refresh must carry the exact MCP resource indicator. Upgrade the controller and OAuth clients together; migration 41 preserves existing API grants and tokens. The HTTP transport pins protocol revision `2025-11-25`, requires a bearer token and protocol version on session requests, caps request/response bodies, and stores only session digests ([MCP](mcp.md#streamable-http)).

**MCP OAuth client registration (migration 42).** Existing `oauth_clients` rows remain API clients (`resource = 1`, registration kind 0). New rows are public MCP clients (`resource = 2`) created by DCR (kind 1) or CIMD (kind 2); they cannot be first-party, loopback-wildcard, device-capable, or have scope bits outside 1|2|4|64. CIMD metadata URLs are unique and bounded at 2,048 bytes. A partial index supports listing/capacity checks; the hard deployment limit is 512 registered rows. Insert/update triggers retain the MCP-only policy, and grant/code/device-code insert triggers require the resource to match the enabled client's resource. New OAuth metadata fields `registration_endpoint` and `client_id_metadata_document_supported` are additive; new OAuth errors `invalid_client_metadata` and `invalid_redirect_uri` are additive to the form error contract. Existing API grants/tokens and the first-party CLI are unchanged. The HTTP API rejects clients whose supplied resource does not match their registration. See [OAuth X06](oauth.md#mcp-client-registration-and-metadata-discovery).

**OAuth client lifecycle and run control audit (migration 43, `043_oauth_client_lifecycle.sql`).** `deployment_policy` gains `oauth_client_registration` (0 off, 1 Client ID Metadata Documents only — the default for new and upgraded deployments — 2 also anonymous DCR). This is a behavior change: an upgraded deployment stops accepting `POST /oauth/register` (`403 access_denied`) and stops advertising `registration_endpoint` until an operator runs `sentinel admin policy set --oauth-client-registration open`; clients already registered keep working. `oauth_clients` gains `registrant` (a 16-byte digest of the registering address), and the insert trigger now counts only enabled registrations toward the 512 bound; indexes on `oauth_grants`, `oauth_codes` and `oauth_device_codes` by `client_id` make reclamation and client deletion key searches. Registrations that hold no grant or code are deleted by maintenance after 24 hours, evicted at capacity after 15 minutes, and bounded to 16 per address. Registered loopback redirects are stored without their port and match on any port (RFC 8252 §7.3); rows stored by migration 42 with a port still match exactly and on their port-free form. `operation_audit` is a new append-only, tenant-owned table recording run cancel, job cancel and job rerun with the account, the authentication kind and the OAuth grant and client. RFC 8414 metadata only ever gains optional members: `registration_endpoint` is now omitted when DCR is off and `client_id_metadata_document_supported` may be `false`, and `sentinel_protocol::oauth::Metadata` reads both as optional, so a newer CLI signs in to a controller from before migration 42. Streamable HTTP MCP: an unsupported `MCP-Protocol-Version` is now `400` (was `426`) with the same `unsupported_version` body, an absent one is accepted as the session's negotiated revision, a missing `Mcp-Session-Id` is `400` (was `404`), and `initialize` with another revision answers with `2025-11-25` instead of `-32602`. Tool annotations changed (`openWorldHint: false` everywhere, `dispatch` and `rerun_job` not destructive). The server configuration gains `trusted_proxies`; its default (loopback only) no longer trusts `X-Forwarded-For` from private-network peers, so a proxy on another host must be listed. No worker protocol change.

**Secret hardening (migration 44, `044_secret_hardening.sql`).** Existing `secret_idempotency` rows are deleted: they held an unkeyed digest of the written value, and new rows hold a keyed MAC that cannot be computed from an old row. A retry of a write made before the upgrade executes again under its `If-Match` version and answers `conflict` if the first write committed. `secret_audit` is rebuilt with the same rows plus a nullable `name` and a nullable `secret_id` (only for a delivery refusal with no resolved secret, result `denied` or `missing`), and becomes append-only by trigger. `secret_version_immutable` no longer covers `sealed`; the new `secret_version_reseal` trigger lets sealed bytes change only to format 2 under a strictly newer key ID, and `totp_update` allows the same forward reseal of a confirmed seed. An older release reading a marker ≥ 44 finds the same table shapes plus one column. The HTTP additions (allowlist, binding and revocation routes) and the `idempotency_mismatch` code on secret routes are additive; the master key file path is fixed at `<data_dir>/master.key` (the admin `--key-file` option is removed).

**Web interface (migration 45, `045_web_ui.sql`).** Migration 45 adds indexes only — `provenance_by_ref`, `provenance_by_pr` (partial), `runs_by_sha`, and three partial indexes over `check_publications` by state — so an older controller keeps working on the upgraded database. API changes are additive: `GET /tenants`, `GET /tenants/{slug}/sync`, `GET /attempts/{id}/steps`, `POST /step-up`, the `/admin/*` routes, the tenant `members`, `repos` (create), `source`, `grants` and `audit` routes, the run list's `ref`, `pr`, `sha` filters and `trigger`, `ref`, `pr` fields, the log page's `step_done`, `/me`'s `stepped_up` and `mfa`, `/health`'s `github_sign_in`, and `/workers`' capacity, reservation, label and drain fields. Behaviour changes: the controller no longer serves a page at `/` (`not_found`; the web interface is the separate `sentinel-web` process); GitHub check `details_url` is `{public_url}/runs/<id>` instead of `{public_url}/#/runs/<id>`, and the web interface still accepts the old form; the parked long-poll budget is 32 (8 per user) instead of 3 (2), parked polls no longer hold a handler permit, and a parked poll ends early when its reader loses access (`not_found`) or its client hangs up; an organization's last administrator can no longer be demoted or removed (`conflict`), where before nothing prevented it. The GitHub sign-in finish page hands the CSRF secret over through `localStorage` instead of `sessionStorage`. Upgrade the controller and `sentinel-web` together; clients that parse `/workers`, run lists or `/me` strictly must accept the new fields ([web interface](web-ui.md), [API](api.md)).

**Retention and quotas (migration 46, `046_retention.sql`).** Migration 46 moves `tenant_quotas` into `storage_policies` (one row per tenant or repository: quota, log retention, artifact retention; the quota rows carry over) and drops `tenant_quotas`; adds `storage_defaults` (the controller's `[storage]` limits, written at every start), `repo_usage`, `tenant_usage.log_bytes`, the attempt columns `log_bytes`, `log_expires_ms` and `log_expired_ms` with their partial indexes and triggers, an `artifacts` insert trigger that caps a new row's `retain_until_ms` at the effective artifact retention, and `uploads_aborted`. The recreated `attempt_update` trigger also refuses to clear `log_expired_ms`. An older controller is refused like any newer database (it would still read `tenant_quotas`). Behaviour changes: log retention is now decided in the database — a released attempt's log is stamped with its size and deadline and deleted once the row says it expired, so a log directory no attempt row names is removed by the maintenance pass rather than kept until it ages out; tenant usage and quotas count stamped log bytes beside object bytes; a pipeline's `retain` above the effective artifact retention (default 90 days, where before up to 365 were kept) is shortened; `run_artifact_bytes` and `attempt_log_bytes` replace the fixed 16 GiB and 256 MiB; unset watermarks and the worker and remote-cache budgets are sized from the data file system (they equal the old fixed values on 64 GiB for the watermarks and on 1 TB for the budgets); aborted upload rows are deleted a week after they expire. API changes are additive: `GET /admin/storage`, `PUT /admin/tenants/{slug}/storage`, `GET /tenants/{slug}/storage`, `PUT /tenants/{slug}/repos/{name}/storage`, the tenant list's `log_retention_ms` and `artifact_retention_ms`, and a log page's or search's `expired_ms`; `usage_bytes` now includes log bytes. New configuration keys are optional ([configuration](configuration.md), [retention](retention.md)).

**External S3 copy (migration 47, `047_s3.sql`).** Migration 47 adds `objects.remote_ms` and `objects.evicted_ms` (the recreated `objects_immutable_update` trigger lets only those two change, `remote_ms` once, and never evicts without a copy), the `objects_unreplicated` and `objects_evictable` indexes, `object_totals` (local and unreplicated bytes, kept by triggers), `s3_uploads`, `s3_deletes` with the triggers that fill it on object delete and log expiry, `attempts.log_remote_ms` with `attempts_log_unreplicated` and a trigger resetting it when a copied log's state changes. Without `[s3]` nothing reads or writes these beyond the triggers' bookkeeping. An older controller is refused like any newer database. API changes are additive: `GET /admin/storage` gains `s3` (`null` without `[s3]`), and `GET /queue` gains `placement_paused` (`disk_below_watermark` or `external_copy_backlog` while admission is closed, else `null`) and the reason code `storage` for a job that would otherwise be placed. New configuration: the optional `[s3]` section ([s3](s3.md)).

**Backups (`sentinel.backup/1`).** A backup directory's layout and `backup.json` are a versioned contract: `format` names it, and a reader refuses another. The snapshot inside a backup carries its own `schema_migrations`, so a newer controller restores an older backup and migrates it as it would any older database; an older controller cannot restore a newer backup (the snapshot is a newer database). No schema change: backups need no migration. API changes are additive (`GET|POST /admin/backups`), as is the optional `[backup]` section and the `admin backup` and `admin restore` commands ([backup](backup.md)). The `objects.recopied` and `manifests.recopied` counts in `backup.json` are additive (readers ignore unknown keys), and the `DIR/.lock` advisory lock file that serializes `create` and `prune` is not part of the layout readers see; `format` stays `sentinel.backup/1`.

**Upgrades and rollback (migration 48, `048_upgrades.sql`).** Migration 48 adds `schema_migrations.readable_by` — the oldest schema whose binary may keep running on the database after each migration — backfilled as each version's own number except 45 (indexes only, readable by 44), and records it for every later migration from `schema::READABLE_BY`; and `workers.software`, the software string a worker announced at its last hello. Migration 48 itself is declared readable by 47, because no statement of a schema-47 binary reads or writes either column; that declaration takes effect from the first release after 48. Releases before 48 predate the mechanism and refuse every newer database, so none of them runs on a schema-48 database. A binary opening a newer database now runs on it when every migration it does not know declares a `readable_by` it reaches, and refuses it otherwise ([upgrades](upgrades.md)). Before any pending migration the controller and host-local `admin` commands copy the database to `metadata.sqlite.vNNN` (newest two kept), and a failed migration is reported with that copy. API changes are additive: `GET /version`, and `protocol` and `software` per worker on `GET /workers`. New command: `admin upgrade check`. **Rule for later migrations:** declare `readable_by` below the migration's own version only for additions no older statement reads or writes, and say so here.

**Monitoring (no migration).** Additive routes: `GET /ready` (public, codes only), `GET /metrics` and `/api/v1/metrics` (platform administration; the Prometheus text format 0.0.4) and `GET /admin/diagnostics` (`sentinel.diagnostics-bundle/1`, whose `format` names it; fields are added, never removed or retyped, within that version). Metric names and label sets are a contract within a minor release: a family may be added, and a renamed or removed one is listed here first. The worker adds the optional `metrics_listen` key (loopback only); worker protocol unchanged at 10 ([monitoring](monitoring.md)).

**Credential issuance, platform override and grant scoping (no migration).** Behaviour changes, none of which alter a stored shape. (1) Creating a service account, allowing it a repository and issuing it a grant need a browser session that stepped up within the policy window, re-checked in the writing transaction, from everyone including tenant administrators; a bearer or OAuth token is refused with `forbidden` and `details.step_up`. So `sentinel service-account create|allow|grant` always fail from the CLI until a step-up-capable client offers them (breaking; `grants` and `revoke` are unchanged). (2) `GET /grants` needs `tenant:admin` unless the token lists its own grant, and `DELETE /grants/{id}` needs it unless the token revokes its own grant; before, any scope sufficed. (3) A local sign-in name in `PUT|DELETE /tenants/{slug}/members/{user}` and the repository-grant route resolves only among the tenant's members; adding a non-member takes their `usr_` id (a name that used to add a non-member is now `not_found`). (4) Revoking an account's sessions (`logout-all`, password change and recovery, suspension, demotion, second-factor lockout) revokes the service grants that account minted since its oldest unrevoked session began, and revoking one session by name revokes those minted since that session began; reissue them after a step-up. Additive: the optional `reason` body field (1-100 characters) on the member, repository-grant and service-account routes, required of a platform administrator who does not administer the tenant, who also needs step-up for those changes; audit event 57 `platform-override` (the reason) and 58 `member-added` (an account added to a tenant it was not yet a member of, besides `membership-set`). Old clients that omit `reason` keep working as tenant administrators. No worker protocol change ([step-up](step-up.md), [API](api.md), [OAuth](oauth.md)).

**Retention re-application indexes (migration 49, `049_reapply_indexes.sql`).** Adds `attempts_log_reapply` (`attempts(tenant_id, id)` over stamped, unexpired logs) and `artifacts_reapply` (`artifacts(tenant_id, id)`), so each batch of a retention re-application reads only the tenant's own rows in row order. Indexes only: declared readable by 48, no stored shape, wire message or statement of an older binary changes. A repository-scoped step now cuts its batch over the tenant's candidate rows and filters the repository inside that range, so it may touch fewer than 512 rows; the cursor and the result are unchanged.

**Deadline clock, report durability, disk admission and bounded maintenance (no migration, no format bump, no protocol change).** Behaviour changes, none of which alter a stored shape or a wire message. (1) Lease, acknowledgement, queue-timeout, execution-overrun and idempotency decisions are taken on the controller's deadline clock (`UnixMillis::steady()`: wall clock at the first read, then monotonic), and the columns they compare against hold values of it, so a wall-clock step no longer expires leases or queue waits ([core contracts](core-contracts.md#timestamps)); a restart re-anchors from the wall clock and startup reconciliation behaves as before. (2) A worker acknowledgement or report the store refused transiently (writer unavailable, a write of unknown outcome, reader overload, a busy database) is no longer dropped as stale: the controller keeps it (at most 256, at most 5 minutes), retries it first in every dispatch pass, and leaves its attempt out of lease expiry meanwhile; a worker keeps a sent terminal verdict in its heartbeat's held list until the controller stops counting the attempt (the `stop` list of its next answer), which keeps the lease renewed, and sends it again every 5 s. Duplicates are stale at the controller and change nothing; a controller restart while a verdict is waiting still settles the attempt by expiry, as for any report that never arrived ([worker link](worker-link.md)). (3) A terminal report whose summary is over 32 KiB (`MAX_SUMMARY_BYTES`, also the column's check) now keeps its verdict and records no summary, and the session is no longer closed for it; before, the store rolled the whole report back and the lease then failed the job. (4) Scratch disk: for a worker that negotiated the profile protocol (7 and later), `disk_bytes = 0` means none offered, so no job that declares scratch disk (every compiled job does) is placed on it; workers older than 7 cannot report disk and keep their CPU-and-memory admission; a hello below protocol 7 clears the stored disk figure along with the labels and warm images. This is what `Profile::disk_bytes` and the worker's `profile_disk` always documented. (5) Re-stamping retention after a policy change is batched: `retention::set` commits the policy and the first 512 rows and returns a `Reapply` cursor, and `retention::finish_reapply` continues it one bounded write at a time (the API and `sentinel admin tenant storage` do); a crash between the two leaves later rows with their previous deadlines until the policy is set again. `Store::checkpoint` waits at most 200 ms for readers and returns `Checkpointed::Partial` when a reader kept part of the log.

**Job conditions and rerun semantics (no migration, no format bump).** The pipeline schema stays 1 and the run spec format stays 6: a job `if` was already accepted by the schema and stored in the spec, and is now evaluated by the controller at the schedule phase (see [pipeline schema](pipeline-schema.md#expressions-c06)). Two behaviors tighten and are the only observable changes: every `if` is typed at compile time (a comparison across types, a boolean operator over a non-boolean or a non-boolean result is now a compile error that older compilers accepted and failed at evaluation), and `cpu` strings reject a sign and more than three decimals. Core gains the controller-only event `ConditionFailed` (blocked to `infra_failed`, class `preparation`); the event is never persisted or sent on the wire, and no stored code changes. A job with an `if` is created `blocked` rather than `queued`, which no reader depends on; runs created before this change keep their rows. The run row's existing `cancel_requested` column is now written (run cancel, tenant suspension; cleared by a rerun or a check-run rerequest), and the worker and controller artifact mode mask narrows from `0o7777` to `0o777` (the `mode` field stays a `u32`; setuid, setgid and sticky are dropped), so no worker protocol version changes.

**Account security routes (auth flows; no migration).** Additive routes under `/api/v1`, all browser-session only: `GET /me/security`, `POST /mfa/enroll`, `POST /mfa/enroll/confirm`, `POST /mfa/recovery-codes`, `POST /password` and `POST /identities/github/link`. Old clients may ignore them; the `sentinel-web` account page consumes them. New host-local commands `sentinel admin mfa enroll`, `confirm` and `codes` (operator access to the database file and `master.key`; audit rows marked host-local, no session stamped). Behaviour changes: a wrong current password on `POST /password` counts against the session (five revoke it) and never against the second factor; with a second factor enrolled a password change needs a fresh step-up, asked for before the password is judged; a wrong enrollment confirmation code counts against the session, and a confirmed enrollment spends that code's time step. A GitHub-only account can now establish a step-up path by enrolling TOTP. The GitHub link flow holds its attempt (state digest, account, session digest) in memory for ten minutes, at most 256, so a controller restart abandons an unfinished link and the user starts it again; nothing is stored, so no schema changes. No worker protocol change ([API](api.md), [step-up](step-up.md), [GitHub sign-in](github-sign-in.md), [local authentication](local-authentication.md)).

**Verified email identity, email invitations and the mail outbox (migration 50, `050_email_identity.sql`).** Migration 50 adds `users.email` and `users.email_verified_ms` (a partial unique index over **verified** addresses only, and triggers that keep a stored address canonical: lower case, printable ASCII, a service account never holds one), `invitations.email` (the `invitation_update` trigger is replaced so the term is immutable like the others), and the tables `email_verifications` (digest-only, single-use, 24 h tokens, optionally carrying an email-bound invitation), `mail_outbox` (a durable queue whose body is sealed with `master.key` and deleted when the row settles) and `mail_settings` (one row the controller rewrites at every start). Not declared readable by 49: an older binary inserts `users` and `invitations` rows without knowing these columns and would not maintain the new tables, so an older controller is refused like any newer database; roll back with the pre-migration snapshot (`metadata.sqlite.v049`) or a backup ([upgrades](upgrades.md)). Existing accounts are untouched: no address, so sign-in is unchanged. Behaviour changes: `POST /login` accepts a verified email address in `username` (an identifier with an `@`, which no username can hold, is an address); `GET /me` gains `email` and `email_verified`; registration by address is a new way to create an account but uses the same [registration policy](admission.md#registration-policy), so a deployment that is `invite-only` (the default) or `closed` gains no open door. Additive API: `POST /register`, `POST /email/verify`, `POST /email/resend`, `POST /me/email`, `POST /me/email/resend`, `POST /invitations/accept` and `POST|GET /tenants/{slug}/invitations`, `DELETE /tenants/{slug}/invitations/{inv}`; audit events 59 `email-verification-requested`, 60 `email-verified` and 61 `mail-abandoned` (the detail names the message kind and a reason, never an address). Uniqueness is among verified addresses so a claim can never lock an address's owner out; an email invitation is refused for an organization with a bound GitHub installation, at creation and again at redemption. New configuration is optional and server-only: the `[mail]` section (`api_key_file`, `from`) and `SENTINEL_RESEND_API_KEY_FILE` and `SENTINEL_EMAIL_FROM`, which need `public_url` and, for queued delivery, `master.key`; without them nothing is queued and `sentinel admin account email-link`, `account email-verify`, `invite create --email` and `mail status` serve the operator ([admission](admission.md#email-identity-and-email-invitations), [configuration](configuration.md#email-delivery), [API](api.md), [local authentication](local-authentication.md)). A body sealed under a master key retired before it was sent cannot be opened and is given up (the message lives until it expires: 24 hours for a verification, the invitation's lifetime otherwise). The controller's periodic maintenance also deletes expired and spent tokens and week-old settled mail, with or without Resend. No worker protocol change.


**Email invitation and address rules (no migration).** `POST /tenants/{slug}/invitations` and `DELETE .../invitations/{id}` now apply the platform-override rule: a platform administrator who is not an administrator-member needs fresh step-up and a `reason` (new optional field on the create body, optional body on the revoke), audited as `platform-override`. `POST /me/email` and `POST /invitations/accept` answer `202` whether the address is taken, throttled or queued (the `429` on `POST /me/email` and the `Accepted::Throttled` outcome are gone); `POST /me/email/resend` keeps its `429`.

**GitHub-backed organization membership (migration 51, `051_github_membership.sql`).** Adds `tenants.membership_source` (0 app-managed, the default and the value of every existing tenant; 1 GitHub-backed, only for an organization tenant), the nullable `memberships.synced_ms` and `repo_grants.synced_ms` (NULL = managed here; a value is when GitHub last confirmed the row, and only the membership lane reads it), the `github_member_checks` queue (`tenant_id`, `user_id`, `next_ms`, `checked_ms`, `attempts`, `cursor`, `seq`) and the partial index `tenants_github_backed`, with triggers that allow a derived row only in a GitHub-backed organization tenant and refuse backing a personal namespace. Not declared readable by an older binary: an older controller would let an administrator write manual memberships into a GitHub-backed tenant, so a rollback past 51 needs the pre-migration copy ([upgrades](upgrades.md)). Nothing changes on upgrade: no tenant is converted and no row is derived until an administrator converts a tenant. Behaviour changes apply only to converted tenants: manual membership, role, removal and repository-grant changes for human accounts, invitations to the tenant and redemption of an earlier one are refused (`forbidden`, or `invitation unusable` on redemption); unlinking GitHub removes the person's derived memberships; a sign-in, a link and signed `organization`, `membership`, `member` and `team` deliveries queue checks. New audit events 70 `github-member-joined`, 71 `github-member-role-changed`, 72 `github-member-removed` and 73 `tenant-backing-changed` (numbers are persisted and stable). Additive API: `PUT /api/v1/tenants/{slug}/membership-source`, and `source` and `synced_ms` on the members list; additive CLI `admin source github-backing`; optional `github-app.json` keys `member_recheck_secs` and `member_grace_secs`. The GitHub App needs the organization permission **Members: read** (and the four events) for converted tenants; without it every check is *unknown* — existing members keep access for the grace period, then lose it, and nobody new is admitted. Wire formats, the run spec and the worker protocol are unchanged.

**First-run setup and self-service organizations (migration 52, `052_setup.sql`).** Adds `setup_token` (one row: the digest of the one-time token, its expiry, a failure count and a lock deadline), `instance_settings` (one row, written once by the wizard: instance name and base URL) and `tenants.created_by` (the account that created an organization through the self-service route; NULL for every earlier tenant) with a partial index. Declared readable by 51: an older binary neither reads nor writes any of it, never issues a token and never fills `created_by`; the only effect of running one is that a first-run wizard cannot be completed by it (the `bootstrap` latch it honors is unchanged). Behaviour changes: a controller that starts with no super admin issues a setup token, writes it to `<data_dir>/setup-token` (owner-only) and logs it once as `setup_required`, replacing any earlier token; `sentinel admin bootstrap` now also deletes the token row; the wizard and the CLI share the existing `bootstrap` latch, so no "first visitor" can win. `tenant_creation = approved-users` now also lets an approved account create organizations (it only meant a personal namespace before), within 3 an hour and 10 in all per account; an administrator who needs more uses the platform's own creation. The reserved organization names (`sentinel_store::organizations::RESERVED_SLUGS`) apply to organizations created through the new route and the wizard only; existing tenants keep their names. Additive API: `GET|POST /api/v1/setup`, `POST /api/v1/setup/mail-test`, `POST /api/v1/orgs`, `GET /api/v1/tenants/{slug}/settings`; the `quota_exceeded` code on `POST /orgs`; `sentinel_api::Options` (read-only auto-join rules for the settings route). No audit event numbers change (setup reuses `bootstrap`, `policy-changed`, `namespace-created`, `membership-set`). No worker protocol change ([admission](admission.md#first-run-setup), [API](api.md), [development](development.md#operator-first-run)).

**Resend replaces SMTP (no migration).** Mail is delivered only through the Resend HTTP API. The earlier optional SMTP delivery is removed: the `[mail]` keys `host`, `port`, `tls` and `credentials_file` and the `SENTINEL_SMTP_*` environment variables no longer exist (a configuration file that still has the keys is refused at start, naming the unknown key; stale `SENTINEL_SMTP_*` variables are ignored, so a deployment that relied on them sends no mail until `SENTINEL_RESEND_API_KEY_FILE` and `SENTINEL_EMAIL_FROM` are set, and meanwhile the host-local `sentinel admin` commands mint links as for any deployment without delivery). No SMTP setting was ever persisted: the store holds only the outbox and the one `delivery enabled` flag, which the controller rewrites at each start, so no migration is needed and the outbox rows already queued are delivered through Resend unchanged. `POST /api/v1/setup/smtp-test {token, host, port, from, to, tls?, username?, password?}` is replaced by `POST /api/v1/setup/mail-test {token, to}` (answers `sent`, or `failure` `not_configured`, `invalid_settings`, `transient` or `permanent` with a short `reason`), and `GET /api/v1/setup` gains `mail_configured`; the mail test connects only to the fixed Resend host, which also ends the old test's reachability of arbitrary host and port. `sentinel_store::email::retry` takes a `retry_after_ms` argument (0 for none). No audit event changes.

**Email-domain auto-join (migration 53, `053_auto_join.sql`).** Adds the table `auto_join_domains(domain, slug)`: the validated `SENTINEL_AUTO_JOIN_DOMAINS` rules in force, rewritten whole by the controller at every start (like `mail_settings`) and read inside the transactions that verify an address or open a session. It holds configuration, not membership: no stored shape of any existing table changes and an older binary neither reads nor writes it, so migration 53 is declared readable by 51 (`READABLE_BY`); an older controller simply never joins anyone by domain. New audit event 74 `domain-auto-joined` (the detail names the organization and the role, never an address; numbers are persisted and stable). Behaviour changes only where the operator sets the variable: a verified address in a listed domain joins the mapped app-created organization as a reader when it is verified or at sign-in, and the first match for an organization that does not exist creates it and administers it; GitHub-backed organizations, personal namespaces and suspended ones are never joined. A malformed entry is dropped with a startup warning by position and never stops the controller. No wire format, API route or worker protocol changes ([configuration](configuration.md#domain-auto-join), [admission](admission.md#domain-auto-join)).

**Namespace kind in the tenant list and a member's GitHub standing (no migration).** Additive response fields: each row of `GET /tenants` gains `kind` (`personal`, `organization`) and `membership` (`app`, `github`), read from the tenant row the query already joins; `GET /tenants/{slug}/settings` gains, for a GitHub-backed organization only, `github_sync` `{confirmed_ms, check_due, unanswered}` about the caller's own membership (when GitHub last confirmed it, whether a check is waiting to run, how many passes in a row GitHub could not answer). No stored shape changes and no field is removed or retyped; old clients ignore the new fields. `sentinel-web` uses them for the namespace switcher and the organization page.

**Repository-visible queue and suspended-account email admission (no migration).** `GET /queue` now applies the caller's ordinary repository-read grants to both the returned jobs and `total`, before pagination; platform administration alone still grants no ambient repository access. The response shape is unchanged, but a caller without access to every repository sees fewer jobs and a smaller total. Verification links, resends and host-local verification now refuse suspended accounts, so confirmation cannot redeem an invitation or trigger domain auto-join while the account is suspended; pending applicants may still prove their address before operator approval. No stored shape or worker protocol changes.

**Zero-disk operator signal (no migration).** Additive API behavior: `GET /workers` emits `disk_bytes: 0` in `capacity` and `free` for workers negotiating protocol 7 or later, while legacy workers continue to omit disk when unreported. Additive metric: `sentinel_workers{state="no_disk"}` counts those profile-protocol workers reporting zero disk, making inability to accept jobs alertable. No stored shape or worker protocol change ([API](api.md), [monitoring](monitoring.md), [worker link](worker-link.md)).

**B11 contract and paired-sample harness (no migration, no protocol change).** Three new markers, none read by a running Sentinel: `sentinel.b11-contract/1` (the frozen gate rules in `bench/contracts/b11-blacksmith.json`, separate from `sentinel.bench-contract/1`), `sentinel.b11-samples/1` (one header naming the contract id and revision, then one paired execution per line) and `sentinel.b11-report/1`. The harness refuses a contract or samples file with another marker, and samples taken under another contract revision. A change to the statistic, the sample minimum, the confidence, the seed or the pass rules is a new contract revision and never rewrites records taken under an earlier one. Additive record change in `sentinel-bench/1`: a record of an interleaved group now carries `interleave.conditions` (`per-runtime`) and its `conditions` cover only that runtime's runs; group records without the field hold one block shared by the group. No field was removed or renamed, so a consumer that ignores the new field reads the same keys ([benchmarking](benchmarking.md#record-format-sentinel-bench1), [benchmark contracts](benchmark-contracts.md#the-frozen-b11-contract-and-harness)).

**B11 collector record (no migration, no protocol change).** One new marker, read by no running Sentinel: `sentinel-bench/b11/1`, one execution per JSON line written by `bench/b11-collect.py` (`collect`, and `replay` for the dry run) and joined by its `pairs` mode into the existing `sentinel.b11-samples/1`. Keys: `contract` (id, revision, lane, condition), `repository` (`pilot/<lane>`), `warmup`, `pair` (absent for a warm-up), `order`, `side`, `sha`, `trigger`, `required_complete`, `trigger_to_required_ns`, `job_ns` and `phases` (absent when under the clock's resolution), `resolution_ns`, `outcome`, `censored`, `checks`, `provenance` (anonymized `label`, `host`, `build`, the `envelope`, `cache_state` and the collector's commit) and, for a dry run, `dry_run` with `dry_run_source`. The record carries no repository, remote, account or address; those live in the git-ignored collector config (`sentinel.b11-collector-config/1`, `bench/b11-config.example.json`). The contract and the samples format are unchanged, so no B11 contract revision was needed. A change to a key's meaning is a new marker version ([benchmark contracts](benchmark-contracts.md#the-b11-collector)).
